**`stage3a_theory_version`** (this run has `--ext empirical`)**:** Set to the `theory_version` that Stage 3a last fully covered. Before advancing at Gate 4, the orchestrator must verify this equals the current `theory_version`; if it is stale, re-run Stage 3a on the new content (see `docs/stage_3a_empirical.md` "Re-fire on theory revision" and `docs/stage_2.md` Stage 2b step 5 mirror rule).

**`stage2_mechanism_version`** (consumed only under `--mode empirical-first`)**:** Set to the `theory_version` for which the Stage 2 Gate 2 **mechanism-plausibility** audit (`mechanism-auditor`) last returned PLAUSIBLE. Before advancing at Gate 4, the orchestrator must verify this equals the current `theory_version`; if it is stale, re-run the Stage 2 Gate 2 audit on the revised mechanism before proceeding (see `docs/stage_2.md` "Gate 2: Mechanism Plausibility" and `docs/stage_3a_empirical.md` "Re-fire on theory revision" — both sections render only under `--mode empirical-first`). This is the empirical-first analogue of the theory-first `stage2b_theory_version` Gate-4 block and sits parallel to `stage3a_theory_version`: a downstream mutate (Gate 4 REVISE → Stage 2, Stage 6 Major Revision → theory-generator) must re-pass the mechanism gate, not just re-run the empirics. **Outside `--mode empirical-first`** (a theory-first `--ext empirical` run) this field is initialized to `null` and never updated — `mechanism-auditor` is pruned and Gate 2 is the math audit — so the staleness rule that consumes it does not fire; it is the mirror of `stage2b_theory_version`'s null/no-op status under empirical-first.

**`identification_plan_revision_round`** (this run has `--ext empirical`)**:** Counts identification-auditor REVISE rounds on the current empirical plan (Stage 3a step 3). Increments on each `identification-auditor` REVISE verdict that triggers a plan re-write; resets to 0 on (a) PASS, (b) FAIL routing to a different strategy from the menu, (c) entry to a new Stage 3a pass on a revised theory (per `docs/stage_3a_empirical.md` "Re-fire on theory revision"). **Hard cap: 3.** On the 4th REVISE, the orchestrator treats the plan as FAIL and routes per the FAIL branch of step 3. Without this counter the cap is unenforceable across multi-session runs.

**`data_integrity_round`** (this run has `--ext empirical`)**:** Counts data-integrity-auditor / data-selection-auditor REVISE rounds on the current cache build (Stage 3a step 7.5, fired in parallel after empirics-auditor PASS). Increments on each cycle where either auditor returns REVISE and the empiricist patches the data-construction code; resets to 0 on (a) both data auditors PASS, (b) any data auditor FAIL routed to data-layer redesign and re-execution, (c) entry to a new Stage 3a pass on a revised theory. **Hard cap: 3.** If `data_integrity_round >= 3` on entry to a fresh REVISE cycle (i.e., a 4th REVISE would be required from either data auditor), the orchestrator treats the round as FAIL per the FAIL branch of step 7.5. Without this counter the cap is unenforceable across multi-session runs. Note: `method-checker` REVISE rounds are tracked separately in `method_check_round` below — the two audits have different fix loops (data REVISE requires re-running the cache; method REVISE requires editing imports or adding justification).

**`method_check_round`** (this run has `--ext empirical`)**:** Counts method-checker REVISE rounds on the current empirical code (Stage 3a step 7.5, fired in parallel with the data auditors after empirics-auditor PASS). Increments on each cycle where method-checker returns REVISE and the empiricist either switches a flagged custom implementation to the canonical package OR adds the (a)–(d) justification to the script docstring and the relevant `output/stage3a/*.json`; resets to 0 on (a) method-checker PASS, (b) method-checker FAIL routed to section-restart with canonical packages, (c) entry to a new Stage 3a pass on a revised theory. **Hard cap: 3.** If `method_check_round >= 3` and method-checker still returns REVISE, the orchestrator treats the round as FAIL per the method-checker FAIL branch of step 7.5. The method-checker REVISE branch re-fires only `empirics-auditor` and `method-checker` (not the data auditors), because the fix touches code and not cached data; if the fix changes anything in the data layer, the orchestrator must instead route through the data-revision branch (re-fire all three auditors). Without this counter the method-check cap is unenforceable across multi-session runs.

**`claim_grounding_round`** (this run has `--ext empirical`)**:** Counts `claim-grounder` REVISE rounds at Stage 5 step 5a (the three-agent claim-grounding pipeline: enumerator → grounder → verifier). Increments only on `claim-verifier` REVISE whose failures are classified GROUNDER-ERROR (coverage shortfall, typo'd field path resolvable in the cited file, cited-vs-source mismatch, invalid-derivation-tag); resets to 0 on (a) `claim-verifier` PASS, (b) any re-fire of `paper-writer` per the PAPER-SIDE-ERROR routing (which restarts step 5a from the enumerator on a changed claim set), (c) any re-fire of `claim-enumerator` per the ENUMERATOR-DRIFT routing (also a changed claim set), (d) entry to a fresh Stage 5 pass after a Gate 5 major-revision routing. **Hard cap: 3.** If `claim_grounding_round >= 3` and `claim-verifier` still returns REVISE with GROUNDER-ERROR failures **on the same claim set**, halt the GROUNDER path for operator routing — three rounds of grounder revision on the same claim set without convergence indicates either a systematically broken enumerator pattern or a structural mismatch between paper claims and empiricist output naming that an operator must adjudicate. The halt is GROUNDER-ERROR-specific: PAPER-SIDE-ERROR failures in the same report still route to paper-writer per Stage 5 step 5a. PAPER-SIDE-ERROR re-fires of `paper-writer` reset `claim_grounding_round` each cycle (changed claim set) but are tracked separately by `paper_writer_pse_round` and `paper_writer_pse_claim_ids` (see below).

**`paper_writer_pse_round`** (this run has `--ext empirical`)**:** Counter for consecutive PAPER-SIDE-ERROR re-fires of `paper-writer` at Stage 5 step 5a. On each verifier REVISE whose PAPER-SIDE-ERROR claim_id set overlaps the prior cycle's set by >=50% (Jaccard: |A ∩ B| / |A ∪ B|, where the current PSE set is read from `output/stage5/claim_verification_summary.json:pse_claim_ids`), the orchestrator increments this counter. On verifier PASS, or on a PSE cycle whose overlap with the prior set is <50% (substantively new failures — paper-writer is making progress), the counter resets to 0. The `>=` boundary at exactly 50% is deliberate: exactly half the claims persisting (e.g., 2 of 4 across cycles) is not meaningful progress; without the `>=` boundary, paper-writer could evade the cap indefinitely by rotating one new failure into the set each cycle while keeping a fixed core. **First-cycle convention:** when `paper_writer_pse_claim_ids` is `[]` (no prior PSE cycle), Jaccard = 0, so the counter resets to 0 — the first PSE cycle never increments the cap. **Hard cap: 3.** On the 4th consecutive PSE cycle with >=50% overlap, halt for operator routing — persistent non-convergence on substantially the same claims indicates an empiricist gap the loop is not closing or paper-writer authoring numbers it cannot source.

**`paper_writer_pse_claim_ids`** (this run has `--ext empirical`)**:** The claim_id set from the most recent PAPER-SIDE-ERROR verifier report, used to compute the >=50% overlap above. Updated on each PSE cycle to the current cycle's failure-claim-id set. Reset to `[]` on verifier PASS **and on entry to a fresh Stage 5 pass after a Gate 5 major-revision routing** — a new Stage 5 pass starts the PSE-cycle accounting from scratch, so a stale prior-cycle set must not carry over and produce a false-positive Jaccard overlap on the new pass's first PSE cycle. Without this list the orchestrator would have to re-read prior `claim_verification.md` files (which may not exist after Gate 5 major-revision re-entries); persisting it in `pipeline_state.json` makes the cap enforceable across sessions and across paper-revision cycles.

**`claim_format_reexport_round`** (this run has `--ext empirical`)**:** Counter for consecutive VERIFIER-LIMITATION (`format-unsupported`) re-fires at Stage 5 step 5a. The claim-grounding pipeline resolves field paths only in JSON and LaTeX tables; when a claim's value exists but only in a non-parseable file (CSV/parquet/pickle/etc. — either the grounder tagged it `NEEDS_REEXPORT` or the verifier's Gate-3 format pre-check caught a `GROUNDED` entry citing a non-parseable file), the verifier emits `VERIFIER-LIMITATION / format-unsupported` (counted in `verifier_limitation_claim_ids`, **never** in `pse_claim_ids` or `paper_side_error_count`). The orchestrator re-fires `empiricist` to re-export the value(s) as JSON, then re-fires `claim-grounder` and re-runs the verifier; this counter increments each cycle the same claim set is still `format-unsupported`. Like `claim_grounding_round`, it is scoped to a fixed claim set and resets to 0 on (a) `claim-verifier` PASS, (b) any re-fire of `paper-writer` per PAPER-SIDE-ERROR routing (changed claim set), (c) any re-fire of `claim-enumerator` per ENUMERATOR-DRIFT (changed claim set), and (d) entry to a fresh Stage 5 pass after a Gate 5 major-revision routing. Without resets (b)–(d) the counter could halt a brand-new claim set's first or second re-export attempt against a budget consumed by a prior, now-superseded claim set. **Hard cap: 2.** If `claim_format_reexport_round >= 2` and `format-unsupported` persists on the same claim set, halt for operator routing — two rounds without the empiricist emitting a parseable JSON for a value it has already computed indicates a deeper output-pipeline problem (a value that cannot be re-derived, or an empiricist re-emitting the wrong format) that an operator must adjudicate. Independent of `claim_grounding_round` and the PSE counters: format re-export routes to the empiricist, not the grounder or paper-writer, so it consumes none of their cap budgets. This separation is the fix for the field-report failure where format-blind verifier failures were miscounted as fabrications and routed to drop real numbers.
