# Stage 3a: Empirical Analysis

This file covers two sub-stages: **Gate 3a-feasibility** (empirical feasibility, runs *before* Stage 3 implications) and **Stage 3a** (full empirical analysis, runs *after* Stage 3 implications). In `pipeline_state.json`, use `"stage_3a_feasibility"` during feasibility and `"stage_3a"` during full analysis.

## Preflight: data-source liveness (before any `empiricist` launch in this stage)

`start_services.sh` ran once at session start and produced `output/data_inventory.md`, but a long Stage 2 iteration may have outlived the WRDS session. Before each `empiricist` launch in this stage (Gate 3a-feasibility, Stage 3a plan, Stage 3a execute, and any re-fire), the orchestrator must verify the WRDS server is still reachable:

```bash
PYTHONPATH=code python3 -c "from utils.wrds_client import wrds_ping; exit(0 if wrds_ping() else 1)"
```

If the ping returns False, attempt one restart with `bash code/utils/start_services.sh`. If that also fails, halt the stage by setting `pipeline_state.json:status = "halted_wrds_unreachable"` rather than launching the empiricist into a stack of failed queries — re-run when access is restored. This preflight is cheap (sub-second when healthy) and prevents the most common silent stall in empirical runs. The same rule applies to the FIX-EMPIRICS empiricist re-launch in `docs/stage_puzzle_triage.md`, the Stage 6 Reject re-fire in `docs/stage_6.md` (which routes through this stage's "Re-fire on theory revision" section), and any future empiricist launch site.

## Gate 3a-feasibility: Empirical Feasibility (falsify-first)

Quick falsification check: can this theory be calibrated at all? Do the key empirical moments exist? A theory that predicts the wrong sign on a well-measured moment is dead regardless of how elegant the implications are. Check this BEFORE investing in implications.

**Empirical-first caution.** A wrong-sign feasibility result only kills the idea when the moment is well measured by a proxy/design that actually matches the Stage 1 empirical question. If the mismatch is plausibly due to a proxy, sample, merge-key, aggregation-key, coding, or identification-design artifact, do **not** mark the theory FALSIFIED. Route it as a feasibility-fix: document the artifact in `output/stage3a/empirical_feasibility.md`, repair the proxy/design if possible, and rerun feasibility. If the corrected feasible design no longer identifies the selected idea, use the no-design escalation in `docs/stage_1.md` Step 4 rather than puzzle triage.

1. Launch `empiricist` with a focused instruction: "Quick feasibility check only — download the 2-3 key moments this theory needs to match. Report whether the theory's predictions are in the right ballpark. Do NOT run a full analysis."
2. Save to `output/stage3a/empirical_feasibility.md`
3. If the key moments contradict the theory (wrong sign, off by an order of magnitude) **and** the proxy/design passed the caution above: flag as **FALSIFIED** — increment `theory_attempt` and reset `theory_version` to 1, then return to Stage 1 for a new idea (the theory is dead; counter must advance so the "5 theories on same problem → Stage 0" escalation rule in core.md fires correctly). Don't waste time on implications for a theory the data already rejects.

{{SEED_OVERRIDE_STAGE_3A_FALSIFIED}}
4. If moments are roughly consistent: proceed to Stage 3. If the empiricist declares any moment **unavailable**, require a negative-search log at `output/stage3a/data_search_log.md` documenting the query attempts (`list_tables`/`describe_table` for WRDS, provider catalog search for FRED/PWT/OECD/World Bank, canonical alternates tried, WebSearch for renames). If the log is missing or the search is shallow (no alternates tried, no description grep, no WebSearch), the "unavailable" verdict is not substantiated — return to the empiricist for a real search. Only proceed to Stage 3 once the log exists or the moment is confirmed truly absent.
5. Commit: `artifact: empirical feasibility — {OK/FALSIFIED}`

## Stage 3a: Full Empirical Analysis

This is the full empirical analysis — deeper than the feasibility check at Gate 3a-feasibility. Now that implications are developed, the empiricist can design proper tests, calibrations, and portfolio sorts.

1. **Identification design.**
<!-- THEORY_FIRST_START -->
   Always launch `identification-designer` with the theory, implications, and data inventory — the orchestrator does not pre-judge whether the work will make a causal claim. The designer is the single authority on that question and records its decision as a formal artifact at `output/stage3a/identification_menu.md`, one of:
   - A ranked menu of candidate identification strategies (each with assumptions, diagnostics, estimand, theory-match analysis, anticipated auditor concerns, and software references) when the theory implies one or more causal claims that are testable from the data.
   - `N/A — no causal claim` with a one-paragraph explanation when the empirical work this theory needs is purely calibration, descriptive moment-matching, or model-fit comparison.
   - `OUT-OF-SCOPE` with a macro-variant recommendation when the question requires a macro identification toolkit (SVAR, sign restrictions, narrative shocks, calibrated DSGE-as-identification — currently unsupported, see `LIMITATIONS.md` and issue #18).

   On `N/A`: record the menu artifact and skip step 3 (the identification audit). The downstream empiricist still writes a plan in step 2; that plan must be consistent with the no-causal-claim record (calibration / descriptive / fit only). On `OUT-OF-SCOPE`: either reframe the empirical work as descriptive / model-fit (which would have produced `N/A` had the theory been written that way), or escalate.
<!-- THEORY_FIRST_END -->
<!-- EMPIRICAL_FIRST_START -->
   In empirical-first mode the design was produced at Stage 1 (see `docs/stage_1.md` Step 4) and lives at `output/stage1/identification_design.md`. On first pass through Stage 3a, **do not relaunch `identification-designer`** — copy the Stage 1 artifact to `output/stage3a/identification_menu.md` so downstream agents (`empiricist` step 2, `identification-auditor` step 3, `stage_puzzle_triage.md` references) keep their existing canonical-path expectations. Then proceed to step 2.

   Re-launch `identification-designer` only when the "Re-fire on theory revision" trigger conditions apply (the revised mechanism introduces a new causal claim or changes the theoretical object the empirics must identify). On a re-fire, the new menu may overwrite the Stage 1 artifact or be saved to `output/stage3a/identification_menu_vN.md` — at minimum the canonical `output/stage3a/identification_menu.md` must reflect the binding design.

   `N/A` and `OUT-OF-SCOPE` outcomes are not expected in empirical-first mode (the Stage 1 designer would have escalated rather than producing a non-causal artifact); if either appears at re-fire time, treat it as a no-design escalation, not as a puzzle. Launch `branch-manager` with context = `stage-1-empirical-first-no-design` using the revised designer verdict, the current selected idea, the current mechanism, and `data_inventory.md`. Apply the same REENTER-STAGE-1 / REENTER-STAGE-0 / OPERATOR-ESCALATE routing described in `docs/stage_1.md` Step 4. A revised design that becomes non-causal or infeasible is an identification failure, not an empirical contradiction.

2. **Analysis plan.** Launch `empiricist` with instruction: "Write an analysis plan only — do not execute yet." The empiricist reads the theory, implications, data inventory, feasibility results, and (if produced) `identification_menu.md`. If a menu exists, the plan must select a strategy from it or explicitly justify departing from the menu. The empiricist then writes `output/stage3a/empirical_plan.md` describing: what tests to run, what data sources to use — as a `## Source selection` table in `empirical_plan.md` with columns `variable | role | chosen source | alternatives considered | reason chosen dominates | sample cutoff | cutoff citation`. **Load-bearing variables only** (LHS of a headline regression, focal RHS, sort/portfolio-assignment variable, treatment-definition variable, calibration moment): controls and FE buckets get a one-line `source: X` and no further justification. For each load-bearing row, `alternatives considered` lists the finer/longer/more-direct sources from `data_inventory.md` and the wired skills that were checked and rejected; `none — canonical single source` is acceptable for variables with one obvious source (Ken French factors, FRED FEDFUNDS). The `cutoff citation` names the regulation, SEC release, dataset codebook, or prior paper that **defines** the threshold (not merely uses it); intuition-only cutoffs are a fail-loud bug. The `WHY` is the table — do not paraphrase it in prose, what the expected results look like, and what would constitute support vs. rejection of the theory. The plan MUST include a **proxy–theory mapping** section: for each empirical proxy, state (a) which theoretical object it is standing in for, (b) which sub-class / mechanism / scope condition it captures (if the theory has heterogeneous agent types, scope-conditional predictions, or multiple mechanisms), (c) whether the proxy construction is mechanically correlated with the theoretical object (e.g., HHI as proxy for concentration-driven noise variance is mechanical; tracking-error is not), and (d) a non-mechanical alternative proxy. If the theory has multiple sub-classes, the plan must include **at least one proxy per sub-class in the primary analysis** — not deferred to robustness. If the main proxy is mechanically correlated with its theoretical object, the non-mechanical alternative is mandatory in the primary analysis as well.
<!-- EMPIRICAL_FIRST_START -->
   When the design was set (or revised) by `identification-designer`, `identification_menu.md` already carries a per-strategy **Source selection (load-bearing design variables)** mini-table for the variables the identification hinges on (running/forcing variable, treatment indicator, instrument, focal LHS/RHS). For those variables, copy the designer's three pre-filled cells (`chosen source`, `sample cutoff`, `cutoff citation`) into the matching row of `empirical_plan.md`'s `## Source selection` table **verbatim** — they are already anchored at the design point and must not be re-derived. The designer's `role in design` column maps to the plan's `role` column; only the plan-specific `alternatives considered` and `reason chosen dominates` columns need filling in. (On a Stage 3a designer re-fire, re-copy from the updated menu the same way.) This anchors citations and cutoffs to the design and gives `data-selection-auditor` a cross-check (designer's table vs. plan's table must agree). Non-design variables (controls, FE buckets, auxiliary covariates) are not in the designer's table — source them as usual.

3. **Identification audit.** If step 1's designer artifact is a strategy menu (not `N/A` and not `OUT-OF-SCOPE`), launch `identification-auditor` on `empirical_plan.md`. The auditor returns PASS / REVISE / FAIL with severity-ranked named failure modes (e.g., `TWFE-staggered-no-robust-estimator`, `weak-iv-stockyogo-misuse`, `no-rd-manipulation-test`) and an estimand-vs-theory match analysis. Saves to `output/stage3a/identification_audit.md`. (The auditor also has a self-check that returns PASS-N/A if the empiricist's plan turns out to make no causal claim despite the designer producing a menu — this is a safety net for cases where the empiricist scoped down between step 1 and step 2; the designer remains the canonical decider.)
   - If **PASS**: proceed to step 4 (orchestrator plan review).
   - If **PASS-N/A** (auditor safety-net — empiricist scoped down to a non-causal plan despite the designer issuing a menu): proceed as if PASS for routing purposes; the designer's menu remains the canonical record of what the theory implied identification-wise, and the auditor's PASS-N/A flags that the executed plan ended up narrower. The orchestrator should re-read the plan in step 4 and verify it is genuinely non-causal (the empiricist's plan, not the auditor's read, is binding); if any causal claim sneaks back into the plan after this verdict, kick it back to the empiricist for a plan that is consistent with the auditor's read.
   - If **REVISE**: re-launch `empiricist` with the audit's failure-mode list and severity-7+ fixes. The empiricist revises the plan in place. Re-run the auditor. **Increment `pipeline_state.json:loops.identification_plan_revision.round`** on each REVISE → re-plan cycle. **Hard cap: 3 plan-revision rounds.** If `loops.identification_plan_revision.round >= loops.identification_plan_revision.cap` and the auditor still returns REVISE, treat as FAIL. Reset the counter to 0 on PASS, on FAIL routing to a different strategy from the menu, or on Stage 3a re-fire entry per "Re-fire on theory revision."
   - If **FAIL**: the chosen design class cannot identify the theoretical object from this data. Reset `loops.identification_plan_revision.round` to 0 **AND reset `loops.method_check.round` AND `loops.data_integrity.round` to 0** — a strategy switch produces fresh code under different estimators (DiD → RDD changes the canonical-package universe entirely) and typically a fresh data slice; the prior counters from the abandoned strategy must not bleed across or they will premature-cap-FAIL legitimate first-pass REVISEs on the new strategy's code. Re-launch `empiricist` with the auditor's verdict and the designer's full menu, instructing the empiricist to select a different strategy. If all strategies in the menu have been exhausted or the designer returned `N/A — no design feasible`, treat the prediction as untestable from available data: either reframe the empirical work as descriptive / calibration / model-fit (re-enter at step 1; the next pass returns `N/A` from the designer and skips step 3) OR route through puzzle-triager (`docs/stage_puzzle_triage.md`) — the triager decides between HONEST-NULL (acknowledge the limitation in the paper) and BACK-TO-IDEA (the prediction was load-bearing and a different theory is needed). **Empirical-first exception:** because empirical-first commits to a causal design at Stage 1, exhausted or infeasible strategies are a no-design escalation, not a puzzle; use the branch-manager routing in `docs/stage_1.md` Step 4 instead of puzzle-triage.
   - If **OUT-OF-SCOPE** (macro design): see step 1 handling.
   - Skip this step entirely if step 1 returned `N/A` (no causal claim).
4. **Review the plan.** Read the plan. Check: does it use the best available data? (If WRDS is available but the plan uses only CZ portfolios, reject the plan.) Does it test what the theory actually predicts? **Does every theoretical sub-class have at least one empirical proxy in the primary analysis?** Identification soundness is already gated by step 3 — focus this review on data-choice and proxy-theory mapping concerns the auditor doesn't cover. If the plan is wrong on these dimensions, re-launch the empiricist with specific feedback.
5. **Execute.** Launch `empiricist` with the approved plan. The agent executes the plan, fetches data via skills (FRED, Ken French, Chen-Zimmerman, WRDS, EDGAR), and runs the analysis. Saves to `output/stage3a/empirical_analysis.md` and `code/empirical.py`. The analysis report MUST include a `## Headline claims` section with 1-5 numerical claims tagged `[HEADLINE]` and assigned snake_case `[claim_id: …]` — these are the load-bearing numbers the next step replicates.
6. All code must be written to files (`code/` for final, `code/tmp/` for scratch). Never run inline `python3 -c`.
6.5. **Headline replication (independent path).** Launch `headline-replicator` on `output/stage3a/empirical_analysis.md` + `code/empirical.py` + the raw data sources. For each `[HEADLINE]`-tagged claim the agent recomputes the value via a DIFFERENT aggregation path (alternative merge key, different aggregation order, raw source not cache, or alternative canonical estimator package) and emits `code/tmp/empirics_verify.py` + `output/stage3a/empirics_verify_result.json` with per-claim `{reported, replicated, relative_delta, agree, path_class}`. The agent self-FAILs on absent script, trivially-equivalent path, missing `[HEADLINE]` tags, or any claim disagreeing beyond tolerance.

   **Pre-routing file check.** Before evaluating the routing, verify `output/stage3a/empirics_verify_result.json` exists on disk and parses as JSON. If absent or malformed (typically because the replicator crashed, hit a token limit, or timed out before writing), treat this as a replicator self-failure on the same loop as `trivially_equivalent_path`: **increment `loops.replicator_self_refire.round`; if `loops.replicator_self_refire.round >= loops.replicator_self_refire.cap`, halt** with `pipeline_state.json:status = "halted_replicator_self_failure"`; otherwise re-launch `headline-replicator` with an instruction to investigate why the prior run failed to emit a valid result file. With the default cap 3 this tolerates three failed firings before halting. (This is now a real capped loop with backing state — it survives a session restart, unlike the former in-session firing count. Its reset scope is the current replicator attempt on the current headline: a valid replicator verdict or a new empiricist headline zeroes it per the generic Audit-loop scoping rule.) Do not infer a default verdict from an empty or missing file — the routing below assumes the file exists and parses.

   **Routing.** Evaluate the conditions below in order; the first match wins. (The conditions are mutually exclusive by construction — a `verdict: PASS` cannot co-occur with substantive failures, and the warning-driven cases are dispatched before the substantive ones so an over-tagged-but-still-disagreeing run is correctly routed as substantive.)
   - If **`verdict: PASS`**: proceed to step 7. The `over_tagging` and `untagged_headline_*` warnings (if present) are informational only at this step — they get forwarded to empirics-auditor for inclusion in its report, and the empiricist may revise tagging on the next iteration if the auditor flags it.
   - If **`verdict: FAIL` AND `"source_unreachable" ∈ untagged_warnings`** (replicator could not pull from the raw data source; `claims` is empty): retry the data-source preflight at the top of this file once. If the source comes back, re-fire `headline-replicator`. If still unreachable, set `pipeline_state.json:status = "halted_data_audit_unreachable"` and stop. Do not increment any counter.
   - If **`verdict: FAIL` AND `"no_headline_tags" ∈ untagged_warnings`** (empiricist forgot to tag; `claims` is empty): re-launch `empiricist` with the instruction to add `[HEADLINE]` tags to `empirical_analysis.md`. Tagging fix only — do **not** increment the step 7 audit-fix counter or `loops.headline_replication.round`. Re-fire `headline-replicator` after the empiricist returns.
   - If **`verdict: FAIL` AND `"trivially_equivalent_path" ∈ untagged_warnings`** (replicator emitted a banned trivial path): replicator-self-failure, not an empiricist bug; do **not** increment the step 7 audit-fix counter or `loops.headline_replication.round`. Increment `loops.replicator_self_refire.round` (the same self-refire loop as the crash case in the pre-routing file check above); **if `loops.replicator_self_refire.round >= loops.replicator_self_refire.cap`, halt** with `pipeline_state.json:status = "halted_replicator_self_failure"` for operator review; otherwise re-launch `headline-replicator` with the prior bad output as feedback (cap 3 → three failed firings tolerated before halting).
   - If **`verdict: FAIL` AND any claim row has `agree: false`** (substantive disagreement on a headline number; over-tagging warning may co-occur and is forwarded as informational): re-launch `empiricist` with the `empirics_verify_result.json` payload and an instruction: "Either correct the headline value(s) in `empirical_analysis.md` / `code/empirical.py` to match the replicated value, or attach a rebuttal note to the disputed `[HEADLINE]` line in `empirical_analysis.md` formatted as `[REBUTTAL claim_id: <id>] <why the prior verification path was incorrect> [verification-redesign suggestion: <proposed alternative path>]`. A rebuttal must cite the specific lines in `empirics_verify.py` it disputes." Increment `pipeline_state.json:loops.headline_replication.round`. Re-fire `headline-replicator` on the revised analysis. **Hard cap: 3 headline-replication rounds.** If `loops.headline_replication.round >= loops.headline_replication.cap` and the verdict is still FAIL with `agree: false` claims, treat as FAIL → return to Stage 2 with the disagreement as input to theory-generator (the headline result is unverifiable as written and the theory cannot rest on it). **Counter resets for `loops.headline_replication.round`** (all set to 0): on PASS at this step, on the `no_headline_tags` / `source_unreachable` / `trivially_equivalent_path` routings above (those are not substantive disagreement rounds), on re-execution from a substantive data FAIL at step 7.5, on any empirics-auditor re-fire at step 7 that materially changes `code/empirical.py` or headline content, and on Stage 3a re-fire entry per "Re-fire on theory revision."
   - If **`verdict: FAIL` AND none of the above match** (no warnings indicating a known failure mode; no `agree: false` claim row): treat as replicator-self-failure of an unrecognized class. Re-launch `headline-replicator` once with an instruction to investigate and either emit a recognized failure mode or PASS. Do **not** increment any counter. If the next firing also lands in this branch, halt with `pipeline_state.json:status = "halted_replicator_unrecognized_failure"` for operator review — this signals a contract gap between the agent body and the routing.
7. **Empirics audit.** Launch `empirics-auditor` on the empirical analysis + code + theory draft + `output/stage3a/empirics_verify_result.json`. Saves to `output/stage3a/empirics_audit.md`. The auditor reads the replicator's per-claim results as confirmed/disputed signals (the replicator owns headline recomputation; the auditor does NOT re-derive headline numbers), then runs the code, checks methodology mechanics (clustering, robust SEs, sample construction), and reviews interpretation. Identification-design soundness is already gated at step 3; the empirics-auditor focuses on whether the code actually implements the audited plan.
   - If **PASS**: proceed to step 7.5 (data-integrity audit).
   - If **FAIL**: re-launch `empiricist` with the audit feedback. Keep iterating as long as the number of issues is decreasing. **Hard cap: 5 audit-fix attempts total.** Escalate if the issue count plateaus or increases across two consecutive attempts, OR if 5 attempts have been made. Escalation treats the empirical analysis as failed for this theory version → return to Stage 2 with the audit notes as input to theory-generator (the theory may be untestable as written). On any empiricist re-fire from this step that materially changes `code/empirical.py` or `empirical_analysis.md` headline content, **reset `pipeline_state.json:loops.headline_replication.round` to 0** and **re-fire `headline-replicator` (step 6.5) on the revised analysis before re-firing empirics-auditor** — the auditor-driven re-fire is a fresh substantive change to the headline; the prior replicator counter must not bleed across, and a stale verify result on changed code is exactly the bug class the replicator exists to prevent.
7.5. **Post-empirics audit triad (data integrity + data selection + method canonical-availability).** `empirics-auditor` PASS verifies (a) the code runs and its with-cache output matches the report, AND (b) every stochastic LOAD-BEARING spec reproduces bit-for-bit when the derived cache is moved aside and the spec is re-run from scratch (issue #56 — same-path determinism, distinct from the headline-replicator's different-path tolerance check) — it does NOT verify the cache *content* is correct against the raw source (that is the data-integrity auditor's job below), nor whether the methods used are textbook-canonical or hand-rolled. Launch THREE auditors **in parallel** (single message, three Agent calls): `data-integrity-auditor`, `data-selection-auditor`, and `method-checker`. The integrity auditor re-queries the source database and verifies cached field values against source (Class 1 — content); the selection auditor enumerates candidate identifiers under the documented inclusion rule with relaxed filters and diffs them against the cached universe (Class 2 — sample); the method-checker reads `.claude/skills/canonical-packages/SKILL.md` and flags every place the empiricist wrote custom code for an econometric method that has a canonical author-maintained package (Class 3 — method canonical-availability; see [issue #36](https://github.com/alejandroll10/zeropaper/issues/36)). Each returns PASS / REVISE / FAIL with severity-ranked named failure modes; outputs go to `output/stage3a/data_integrity_audit.md`, `output/stage3a/data_selection_audit.md`, and `output/stage3a/method_check.md` (+ summary JSON for method-checker). **Before aggregating, verify all three output files exist on disk** — `output/stage3a/data_integrity_audit.md`, `output/stage3a/data_selection_audit.md`, `output/stage3a/method_check.md`. If any is absent (typically because the corresponding agent crashed, hit a token limit, or timed out), re-launch only that absent agent and wait for its output before aggregating; do not infer a default verdict from an empty file. A silently-missing method_check.md treated as PASS-by-omission is exactly the issue-36 failure mode this triad exists to prevent. Then aggregate the three verdicts:
   - **All three PASS**: proceed to **puzzle-triage entry check** (next section). Reset `pipeline_state.json:loops.data_integrity.round` AND `loops.method_check.round` to 0 (both counters tracked the triad's REVISE loops and are stale once the triad clears).
   - **Any data auditor REVISE (and no FAIL)**: re-launch `empiricist` with the data-audit reports and the named failure modes the empiricist must fix. The empiricist patches the data-construction code (not the identification design — if a finding straddles identification, route to step 3 instead). **Increment `pipeline_state.json:loops.data_integrity.round`.** Re-run step 7 (empirics-auditor) and then step 7.5 on the rebuilt cache. **The empirics-auditor re-fire here is a reproduction check on the rebuilt cache, not a substantive audit-fix iteration — it does NOT count against step 7's 5-attempt cap.** This re-fire still includes the cache-bypassed determinism rerun (issue #56) on stochastic LOAD-BEARING specs — patched data-construction code can introduce a fresh unseeded call, so the rerun check must re-run, not be skipped as "already passed." **Hard cap: 3 data-revision rounds.** If `loops.data_integrity.round >= loops.data_integrity.cap` and either data auditor still returns REVISE, treat as FAIL.
   - **method-checker REVISE only (data audits both PASS)**: re-launch `empiricist` with `output/stage3a/method_check.md` and an instruction to either (i) replace the flagged custom implementations with the canonical packages named in the report, or (ii) add the (a)–(d) justification to the script docstring AND the corresponding `output/stage3a/*.json`. **Increment `pipeline_state.json:loops.method_check.round`.** Re-run step 7 (empirics-auditor — to verify the canonical-package swap reproduces) and then re-fire `method-checker` only (the data audits already passed; no cache change). **The empirics-auditor re-fire here is a reproduction check on a canonical-package swap or a docstring/JSON addition, not a substantive audit-fix iteration — it does NOT count against step 7's 5-attempt cap.** This re-fire still includes the cache-bypassed determinism rerun (issue #56) on stochastic LOAD-BEARING specs — a canonical-package swap can change a method's seeding behavior, so the rerun check must re-run. **Hard cap: 3 method-check rounds.** If `loops.method_check.round >= loops.method_check.cap` and method-checker still returns REVISE, treat as FAIL.
   - **Both data REVISE and method-checker REVISE**: handle the data REVISE first (the empiricist patches data construction; re-run empirics-auditor and all three step-7.5 auditors). **Increment `loops.data_integrity.round`** per the data-REVISE branch on this firing; do NOT increment `loops.method_check.round` yet — the method fix has not been attempted. On the next step 7.5 firing, if method-checker still REVISEs (likely, because data fixes do not address method choices), follow the method-checker-only branch and increment `loops.method_check.round` at that point.
   - **Any FAIL**: hard escalation. Three sub-cases. These two data/method sub-cases are **exception 1 (escalation non-reset)** to the generic Audit-loop scoping rule: the FAILing loop is escalating (not being retried on a fresh artifact), so it is left as-is even though the sibling loop's artifact is regenerated and that sibling therefore zeroes. (a) **source-unreachable FAIL** (data auditors could not re-query because WRDS/FRED/etc. is down): retry the preflight at the top of this file once, then if still unreachable set `pipeline_state.json:status = "halted_data_audit_unreachable"` and stop. (b) **substantive data FAIL** (data auditor re-queried and found a load-bearing data problem): re-launch `empiricist` with the FAIL report and an explicit instruction to redesign the data layer (re-source, re-filter, re-construct the universe), then re-enter step 5 (execute). A substantive data FAIL counts as a re-execution, not a revision round; **do not reset `loops.data_integrity.round`** (it is escalating — leave it) **but reset `loops.method_check.round` to 0** — the data-layer redesign is a fresh execution pass and the method-checker counter from the prior data layer must not bleed across (otherwise the first method-checker REVISE in the new execution could trigger a premature cap-FAIL). (c) **method-checker FAIL** (multiple custom implementations of canonical methods, suggesting systematic disregard): re-launch `empiricist` with `output/stage3a/method_check.md` and an explicit instruction to restart the flagged sections using the canonical packages. A method-checker FAIL counts as a re-execution; **do not reset `loops.method_check.round`** (it is escalating — leave it) **but reset `loops.data_integrity.round` to 0** — the section-restart is a fresh execution pass and the data-revision counter from the prior code structure must not bleed across.
   - The triad re-fires on Stage 3a re-entry (see "Re-fire on theory revision" below) and on any cache regeneration (`mtime` advance on any cached file referenced by the analysis). On a re-fire that does not change `code/empirical.py` (e.g., cache-only regeneration), if the most recent `output/stage3a/method_check.md` records a **PASS** verdict, you MAY replay that verdict rather than re-launching — method choices are code-level and a cache-only change cannot invalidate a PASS. If the most recent verdict is REVISE or FAIL, **re-launch method-checker** (the pending fix cycle must complete before the monotone shortcut applies); a stale REVISE/FAIL must not be replayed because the empiricist may have fixed it in the interim and a fresh PASS is the only signal that confirms the fix.
   - **Conditions for applying the PASS-replay shortcut.** The shortcut is an optimization; the conservative default is to always re-launch. Apply it only when ALL of the following hold; if any condition is uncertain, re-launch. (1) The mtimes of `code/empirical.py`, any existing `code/empirical_post_v*.py` files (post-pipeline-edit additions per `core.md`'s post-pipeline rule), every file under `code/empirical/`, AND every file under `code/utils/` that `code/empirical.py` (or any `empirical_post_v*.py`) imports (resolve by inspecting the `from utils.X import ...` / `import utils.X` lines) are all strictly older than the mtime of `output/stage3a/method_check.md`. (2) No mtime reset signature is present: a fresh `git clone` resets every file's mtime to the clone time, so if `method_check.md`'s mtime is the same as or older than every watched code file's mtime (i.e., the prior verdict appears to predate even the code it covers), the mtime signal is unreliable and the shortcut MUST NOT be applied. (3) The triager / orchestrator has not flagged a pending code revision in `pipeline_state.json` (e.g., `loops.method_check.round > 0` with no intervening PASS recorded). When in doubt, **re-launch** — a redundant method-checker run costs one sonnet call; a wrongly-replayed PASS lets a regression through. **Known limitation:** the shortcut relies on local filesystem mtime, which is not robust to (a) `git clone`, `tar -xz`, or `cp -r` operations that reset mtimes, nor to (b) **transitive imports** — condition (1) resolves only the direct `from utils.X import …` / `import utils.X` lines in `code/empirical.py`, so a change to a helper that `code/utils/X.py` itself imports (e.g., `utils/wrds_client.py` importing `utils/auth.py`) is invisible to the shortcut's mtime walk. The failure mode in (a) is wrongly-blocked-shortcut (harmless, just redundant work); the failure mode in (b) is wrongly-applied-shortcut (a stale PASS replays when the transitive helper has been modified in a way that could affect method choices). There is no content-hash fallback in v1; if either failure mode becomes a deployment pain point, the agent's verdict file should record a SHA-256 hash of `code/empirical.py` plus a recursive closure of its import graph at PASS time, so the orchestrator can compare hashes when mtime is ambiguous. Tracked under `LIMITATIONS.md` if the issue surfaces in practice.
8. Commit: `artifact: headline replication — {PASS/FAIL}; empirics audit — {PASS/FAIL}; data audits — {PASS/REVISE/FAIL × 2}; method check — {PASS/REVISE/FAIL}`

## Puzzle-triage entry check (mandatory after empirics-auditor PASS and both data audits PASS)

Before proceeding to Stage 4, you must check whether the empirical results contradict any prediction in `output/stage3/implications.md`.

1. Read `output/stage3/implications.md` and identify which implications were tested.
2. Read `output/stage3a/empirical_analysis.md` and the auditor's verification.
3. For each tested implication: did the data contradict it (sign reversal, magnitude outside the predicted range, condition that should hold but failed)?
4. Write `output/stage3a/contradiction_check.md` with one of:
   - **NONE** — empirics confirm or are silent on every tested implication. Proceed to Stage 4.
   - **CONTRADICTIONS FOUND** — list the contradicted implications and what the data shows. **Proceed to puzzle triage** (`docs/stage_puzzle_triage.md`), not Stage 4.
5. Commit: `artifact: contradiction check — {NONE/CONTRADICTIONS FOUND}`

This step is mandatory and may not be skipped — silently jumping to Stage 4 after empirics PASS bypasses the puzzle-pivot mechanism that exists to extract value from theory-empirics disagreements.

## Re-fire on theory revision

Stage 3a is not one-shot. When the theory revises after the first 3a pass — Gate 3 INCREMENTAL rework, Gate 4 REVISE→Stage 2, Stage 6 Major Revision triggering theory-generator work, or any substantive content change — the original `empirical_analysis.md` becomes stale relative to the current theory. The empiricist must re-run on the revised content before Gate 4 can advance again.

**Trigger.** Any of:
- `theory_version` advances and `stage3a_theory_version < theory_version`.
- `implications.md` is overwritten (Gate 3 INCREMENTAL rework, PIVOT, or any path that re-runs Stage 3) and the new file contains NOVEL or PUZZLE-CANDIDATE implications not present in the prior version.
- A referee identifies an empirical gap that wasn't addressed in the first 3a pass (e.g., "this prediction was deferred" or "the identification doesn't address X").
- Stage 6 Reject verdict triggers a deepen directive (see `docs/stage_6.md` Reject row): the deepen directive's empirics requirements become the focus of the re-fire.

**Procedure.**
