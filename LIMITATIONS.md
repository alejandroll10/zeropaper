# LIMITATIONS

Known architectural limits in the pipeline. Each entry: failure mode, what would close it, tracking issue.

Per `CLAUDE.md` ("no unsolved, undocumented, or untracked architectural limits"), additions go here when a limit is identified during a pipeline edit but not closed in the same pass, and every addition must link its corresponding GitHub issue.

## Update quiescence is cooperative for processes outside supported launchers

**Scope:** applying `update.sh` replacements to an existing deployment while another same-UID process can mutate that project.

**Failure mode:** path validation alone cannot bind a later pathname mutation. A concurrent writer can rename a validated managed parent and replace it with a symlink before replacement; a Round-11 reproduction swapped `.claude` after validation and redirected the old updater's `rm`/`cp` operations into an external directory. v2.24.0 closes this for every supported runtime: `launch.sh` keeps a shared `fcntl` lock on a parent-Bash-owned project-directory descriptor for its full process lifetime, `update.sh` acquires the exclusive side before creating any target path, and each parent runs the complete runtime/update body in a child subshell with that descriptor closed so descendants cannot unlock or leak it. A live legacy OpenCode server (which predates the lock) is refused. No pathname lock, separate holder, or reusable readiness file exists. Thus normal Claude/Codex/Gemini/Grok/OpenCode launch-vs-update concurrency fails before target mutation.

**Operational boundary:** stop any process that accesses the project without going through the deployed `launch.sh` before updating. The lock is cooperative; an arbitrary same-UID script can ignore it, and the updater cannot infer every process with a file descriptor or future pathname into the project.

**What would close it:** make every target mutation descriptor-relative, no-follow, and race-bound—including directory replacement, stale sweep, `.env` merge, venv bootstrap/guard refresh, and manifest replacement—or add a cross-platform OS confinement mechanism proven safe even when an allowed project inode is concurrently renamed outside its original path. Regress with a non-cooperating rename/symlink attacker that proves both external paths and project-owned user content remain unchanged.

**Tracking:** [#259](https://github.com/alejandroll10/zeropaper/issues/259).

## Codex subagent dispatch depends on a CLI wrapper, not the native spawn tool

**Scope:** the codex runtime's agent dispatch — `code/utils/agent_launcher/launch_agent.sh`, the launch rules in `deploy_assets/templates/runtime/codex/session.md` and `session_manual.md`, and the per-agent `model` / `model_reasoning_effort` in `.codex/agents/*.toml`.

**Why.** codex's built-in `spawn_agent` tool (verified against codex-cli 0.144.1 by capturing the on-wire tool schema) exposes only `{fork_turns, message, task_name}`. It has **no** `agent_type`, `model`, or `reasoning_effort` parameter, so it cannot select a role from `.codex/agents/` and cannot honor the per-agent model/effort we pin there — and it defaults `fork_turns="all"`, handing a subagent the orchestrator's entire conversation, which silently defeats evaluator independence. Codex *does* discover and parse the role TOMLs (a malformed one warns at startup, and `<project>/.codex/config.toml` is confirmed a live config layer) — the format is simply unreachable from the shipped spawn tool. This looks like a codex regression, not an intentional removal: the `unknown agent_type '…'` error and the whole `agent_roles.rs` loader are still compiled into the binary.

**Mitigation (in place).** The codex orchestrator launches agents via `launch_agent.sh`, which reads the agent's `.toml` and runs a fresh `codex exec` worker with the pinned model + effort, `project_doc_max_bytes=0` (suppresses the orchestrator AGENTS.md so the worker runs on its own instructions), and its own `-s` sandbox. A `codex exec` process starts a clean session by construction, so evaluator independence is restored. Verified end-to-end: a launched `bib-verifier` ran on `gpt-5.6-luna` at `effort=low` (session default was `gpt-5.6-terra`) per the codex threads DB.

**Residuals (three open gaps plus one accepted design trade-off):**

1. **CLI-version fragility.** The launcher depends on `codex exec` flags (`-m`, `--sandbox`, `--ignore-user-config`, `-c model_reasoning_effort`, `--add-dir`, `-o`, `project_doc_max_bytes`) and permission-profile config keys. Launch rejects codex-cli <0.147.0, but a future release could rename or drop one of these surfaces and — unlike the Claude subagent models, which `setup.sh` probes and remaps — nothing checks the complete interface at setup time. It fails loud (strict config/nonzero exit) rather than silently, but the future-version edge is unguarded. **What would close it:** a setup-time probe that runs `codex exec --help` and validates a permission-profile canary, plus a re-check if `spawn_agent` ever gains an `agent_type`/`model` parameter (at which point the native tool could replace the wrapper).

2. **codex sandbox granularity is coarser than the Claude `tools` list (by design, permissive).** The launcher defaults every worker to `workspace-write` so agents can write and run as their definitions intend (their Claude `tools` include Write, and most include Bash — verdict files, drafts, sympy/latex/python). codex's sandbox is *filesystem-scoped* (`read-only` / `workspace-write` / `danger-full-access`), not *per-tool* like Claude's `tools` list, so a worker may have shell access even when its Claude def omits Bash. This is a deliberate choice, not an open gap: we do **not** lock evaluators to `read-only` — the intent is that agents write and run. (A caller can still pass `--sandbox read-only` for a one-off pure-read task, or an agent can pin `sandbox_mode` in its TOML.) The only thing intentionally denied to every worker is launching *other* agents — enforced by the no-spawn catalog patch plus the leaf-worker directive (see the launcher), independent of the write/run sandbox.

3. **Gemini remains unconfined (#187).** Claude, Codex, Grok, and OpenCode now all enforce filesystem write boundaries; Codex's permission profile also closes the former #254 read-confinement gap for `~/.ssh`, `~/.aws`, and `~/.claude`. Gemini still launches with `--yolo`, so it can mutate host state outside the project. This is also a WRDS lockout-safety boundary: an unconfined Gemini process could mutate the host-owned socket/singleton/latch or bypass the persistent client, so `launch.sh` does not auto-start WRDS for Gemini and the v2.24.8 state-protection guarantee excludes that runtime. **Failure mode:** a Gemini empirical run may lack WRDS, or—if another runtime already started it—can undermine the one-login/operator-latch contract. **What would close it:** the write confinement already required by #187, with `~/.local/state/zeropaper/wrds` outside Gemini's writable roots and a regression proving it cannot create, replace, unlink, or lock those entries.

4. **Nested sandboxes don't stack — workers run under the orchestrator's sandbox, not their own (guarded, version-dependent).** The launcher is normally invoked *from inside* the orchestrator's Seatbelt sandbox, and macOS refuses a second `sandbox_apply` under codex's deny-by-default profile: a nested worker's `apply_patch` (native tool and shell helper alike) fails with `sandbox_apply: Operation not permitted` while its plain exec commands silently run under the **outer** sandbox only (codex skips re-sandboxing exec when `CODEX_SANDBOX` is already set — so the inner sandbox tier was never enforced for nested workers in the first place). Observed in production (Stage 0, 2026-07-12) and reproduced on codex-cli 0.144.1. **Guard (in place):** `launch_agent.sh` and `codex_common.sh` detect nesting via `$CODEX_SANDBOX` and run the worker `danger-full-access`; the orchestrator's outer sandbox still confines the whole worker tree (verified — a `$HOME` write from such a worker is denied), so the boundary is unchanged and apply_patch works. **Consequences:** per-worker tiering (`--sandbox read-only`, TOML `sandbox_mode`, codex-math's `network=false`) is only enforced when the scripts run un-nested; nested, the outer sandbox is the only one in force. Relatedly, the orchestrator's own `git commit` requires the permission profile to add `$(pwd)/.git` as its own workspace root (Codex hard-codes each root's top-level `.git` read-only; a root of `.git` itself has no carve-out). Launch now fails below codex-cli 0.147.0, but these behaviors remain version-dependent — if a future Codex fixes nested sandboxing or changes the `.git` carve-out, revisit the guard and profile. **What would close it:** upstream support for nested sandboxing (or an explicit `allow_git_writes`), or a setup-time probe that detects the behaviors and adjusts.

**Tracking:** [#240](https://github.com/alejandroll10/zeropaper/issues/240) covers the unreachable `.codex/agents` role format, setup-time CLI compatibility probing, nested `sandbox_apply` behavior, and the hard-coded `.git` carve-out. Codex read-confinement #254 is closed by the v2.24.10 permission profile; the closed write-confinement pass is #186. Gemini's remaining confinement gap is [#187](https://github.com/alejandroll10/zeropaper/issues/187).

## Codex behind authenticated proxies: ≤0.144.x is a silent total outage (upstream, mitigated by a warn-only preflight)

**Scope:** every codex invocation — the codex-runtime orchestrator (`launch.sh codex`), dispatched workers (`launch_agent.sh`), and the Claude runtime's codex-math co-processor — in any environment whose only network path is an authenticated HTTP proxy (`HTTPS_PROXY` with embedded credentials; typical for hardened sandboxes).

**Failure mode.** codex-cli ≤0.144.x sends no `Proxy-Authorization` header on its HTTPS CONNECT tunnels, even when credentials are embedded in the proxy URL (verified 2026-07-31 with an instrumented relay: every codex CONNECT arrived without the header while curl in the same env sent it). The proxy 407s the bare CONNECT; reqwest surfaces the failed tunnel as `error sending request for url (...)` with **no HTTP status** — so nothing points at the proxy. The OAuth token refresh against `auth.openai.com` fails the same way, so once the access token expires the outage additionally masquerades as an auth/login problem. Fixed upstream in codex 0.146.0.

**Mitigation (in place).** `code/utils/codex_preflight.sh` (`codex_proxy_auth_preflight`, issue #213): at `launch.sh codex` startup, at every `launch_agent.sh` worker dispatch (per-dispatch on purpose — codex can auto-update or roll back mid-run, staling the startup verdict), and at every codex-math `codex_leaf_setup`, if the codex version is < 0.146.0 **and** a proxy env var carries embedded credentials, print a warning naming the defect and the remedies. Warn-only by design — without an authenticated proxy old versions work fine, and a parse failure must never block a launch; the version lookup runs under a 10s watchdog so a hung binary can't block either.

**Standby remedy (when upgrading codex is not possible).** Run a local forward proxy that accepts CONNECT, injects `Proxy-Authorization: Basic base64(user:pass)` (credentials parsed from the real proxy URL), and tunnels to the real proxy; point `HTTPS_PROXY`/`HTTP_PROXY` at it, leaving the credentials out of the codex-facing URL. This restored codex end-to-end in the 2026-07-31 incident (and, having regained network, codex auto-updated itself past the defect — which is also the caveat: an auto-update is not a durable fix if a rollback or pin lands ≤0.144.x again).

**What would close it:** nothing on our side — it is fixed upstream; the preflight exists because a pinned/rolled-back CLI can silently reintroduce it. Related: #146 (codex hard-stop audit — this is exactly such a hard stop), and the CLI-version-fragility entry above (same "no setup-time probe of the codex CLI" root).

## Headless workers can crash Matplotlib on macOS when the GUI backend is inherited

**Scope:** detached Codex workers on macOS, and any other headless runtime launch path that inherits Matplotlib's `macosx` backend instead of explicitly selecting a non-GUI backend.

**Failure mode:** an agent-written Python script imports `matplotlib.pyplot` and creates a figure for `savefig()`. AppKit initialization in the detached process aborts Python with `SIGABRT`; calculations/figures fail and macOS displays repeated “Python quit unexpectedly” dialogs. Individual helpers such as `ssj_solve.py` select `Agg`, but the general launcher environment does not.

**What would close it:** establish and test a non-interactive backend (normally `MPLBACKEND=Agg`) across every headless orchestrator/worker launch path, define explicit script/user override precedence, and give concurrent workers a writable cache-safe `MPLCONFIGDIR` where needed. The regression test must create and save a figure in a genuinely detached process without initializing AppKit.

**Tracking:** [#250](https://github.com/alejandroll10/zeropaper/issues/250).

## OpenCode runtime: external OS sandbox, one model tier, and experimental background durability

**Scope:** the OpenCode runtime assembled under `.opencode/agents/`, configured by `opencode.json`, and launched through `./launch.sh opencode`.

1. **Launcher confinement is external to OpenCode (closed for supported launch paths in v2.22.0).** OpenCode has no native kernel sandbox, so `./launch.sh opencode` wraps the persistent authenticated server and every attached client, while `--once` wraps the whole TUI, in Anthropic Sandbox Runtime. The resulting Seatbelt/bubblewrap policy covers their descendant trees, permits project/project-scoped OpenCode-state/cache writes and arbitrary network access, and denies reads/writes under `~/.ssh` and `~/.aws`; real canaries verify project and cache writes, external write/delete denial, protected-state immutability, credential denial, network access, and a nested child. The unsandboxed driver is a narrow control plane: its Python runs isolated, its PATH excludes every sandbox-writable root, and its helper/log/identity/credential files live under sandbox-immutable directories. Pre-v2.22 state is migrated; if its old unconfined server/group is still alive, the new launcher fails closed and requires it to be stopped before starting a confined replacement. The adapter deliberately uses SRT's library API because its CLI schema requires a finite domain allowlist, which is incompatible with an open-ended research pipeline. **Residuals:** bare `opencode` bypasses the wrapper; SRT is a beta dependency whose API may change; root execution is unsupported; Ubuntu 24.04+ needs an AppArmor user-namespace profile (or Anthropic's broader sysctl workaround). OpenCode can also write shared caches and the non-control portions of `~/.codex` required by codex-math, so it can delete Codex session/log state, although auth, config, plugins, skills, rules, and packages are write-denied. Use the launcher and rerun `deploy_assets/scripts/test_opencode_sandbox.sh` after SRT upgrades.

2. **All capability tiers collapse to one model.** Every generated subagent and the orchestrator use `opencode/deepseek-v4-flash`; `--light` is a no-op. Generator/judge model decorrelation and automatic model fallback are unavailable. **What would close it:** multiple suitable OpenCode Zen tiers plus an availability probe/remap.

3. **Background subagents depend on an experimental, process-local upstream registry.** `./launch.sh opencode` enables OpenCode's native `task(background=true)` and keeps one authenticated localhost `opencode serve` alive across attached CLI turns. Verified on OpenCode 1.18.11: a child survives attached-client exit, completion is durably injected into the parent as a synthetic message, and that message autowakes the parent without another client. The project-exclusive driver tracks launch generations (a resumed `task_id` can reuse its child session ID), causally pairs each with its persisted synthetic completion/error user notification and a later completed/error parent response, discovers generations spawned by that response, and then waits for the parent plus its child sessions to become stably idle before sending an external continuation; a reused parent is quiesced even when its generation ledger is empty. Cancellation aborts the tree, confirms status-only quiescence, and replaces the server instance before advancing its history baseline, preventing a delayed notification/autowake from crossing that boundary. However, OpenCode's background-job registry is instance-scoped memory: a **server-process** crash interrupts active children even though their session transcripts and artifact checkpoints persist. The driver restarts the server, uses an always-present parent/server epoch and a server-instance-bound history baseline to detect and retire lost generations, and persists uniquely tokenized recovery intent until its native user prompt is observable; it then explicitly orders the parent to reconcile/resume unfinished child IDs. It cannot make an uncheckpointed upstream model/tool call atomic across a server crash. **Mitigation:** every task prompt names an artifact path, gates verify that artifact rather than trusting notification alone, authenticated server/client and parent-bound pending-generation state are cached for driver restart, and older OpenCode versions whose task schema lacks `background` fall back naturally to foreground calls. **What would close it:** upstream persistence and restart recovery for the background-job registry, followed by removing the experimental flag and recovery caveat.

4. **Skill-source selection depends on the launcher.** Deployments contain `.claude/skills` and `.agents/skills`. `./launch.sh opencode` disables automatic external scans while `opencode.json` explicitly registers `.claude/skills`, avoiding duplicate IDs. Starting bare `opencode` bypasses that selection; use `./launch.sh opencode --once` for the TUI.

5. **An OpenCode-only empirical host cannot auto-start the shared WRDS daemon.** The v2.24.8 WRDS transport is reachable from every runtime sandbox through a private Unix socket once the host-wide daemon exists, and Claude/Codex/Grok launchers establish it before sandbox entry. OpenCode is deliberately excluded from that host hook: its unsandboxed control plane must never source the project venv or execute project-writable service code. Starting the daemon from a short SRT command is not an equivalent fix—the wrapper may tear down its descendants, and a PID written from an isolated namespace may make the durable login-attempt owner check look dead to peers. **Failure mode:** if OpenCode is the first/only empirical runtime on a host, WRDS remains unavailable until an operator starts the v5 daemon from an empirical deployment (or another supported launcher establishes it); once present, OpenCode reuses it normally over `~/.local/state/zeropaper/wrds/wrds_server_23847.sock`. **What would close it:** a launcher-owned, long-lived SRT-confined WRDS service whose identity/lifecycle are validated by the trusted control plane, whose project code and venv never execute unsandboxed, and whose write-ahead auth-latch ownership remains meaningful across PID namespaces. Per-process database connections are not acceptable because they discard the one-login/account-lockout safety contract.

**Tracking:** [#220](https://github.com/alejandroll10/zeropaper/issues/220) (initial OS confinement — closed), [#251](https://github.com/alejandroll10/zeropaper/issues/251) (bare-launch confinement bypass, SRT compatibility, and shared Codex-state writes), [#221](https://github.com/alejandroll10/zeropaper/issues/221) (model tiers + fallback), [#222](https://github.com/alejandroll10/zeropaper/issues/222) (background lifecycle and process-local registry crash recovery — reopened), [#244](https://github.com/alejandroll10/zeropaper/issues/244) (deterministic skill-source selection under bare launches), [#261](https://github.com/alejandroll10/zeropaper/issues/261) (sandbox-confined WRDS service lifecycle).

## Grok runtime: single model tier, no model probe, and partial mode/extension coverage

**Scope:** the Grok Build runtime — `deploy_assets/scripts/assemble_grok_agents.py`, the `.grok/agents/*.md` it emits, the labeled-dispatch fork in `deploy_assets/templates/runtime/codex/session.md`, and the grok wiring in `setup.sh`.

**Design note (not a limitation).** Grok reads project instructions from the root `AGENTS.md` — the *same* file codex reads, and its filename cannot be changed or redirected (verified: grok ignores `GROK.md`/`.grok/AGENTS.md` when a root `AGENTS.md` is present). So codex and grok deliberately **share** one `AGENTS.md`, whose dispatch section is runtime-labeled ("If you are Codex … / If you are Grok …"); each CLI follows its own branch. Verified end-to-end: grok reads the shared doc, self-selects the grok branch (native `task` tool + `subagent_type`, agents in `.grok/agents/`), and spawns an assembled pipeline agent successfully.

**Fixed footgun — shared leader socket cancels concurrent grok projects (closed by per-project `--leader-socket`).** Every grok client connects to one host-global leader process at `~/.grok/leader.sock` by default. A second client connecting to that socket **tears down the first session's in-flight turn** (reproduced on grok 0.2.93: a `grok -p` probe, and a same-socket interactive client, each wiped a running session's turn mid-execution; cross-cwd — so two *different* projects collide, not just two windows on one project). This directly breaks the pipeline's recommended "one interactive tmux window per project" layout for long unattended runs, which is safe for Claude/gemini (independent processes) and codex (isolated `codex exec` workers) but not for grok's single-leader model. Note this is *not* triggered by the pipeline's own subagents — grok spawns those via the in-process native `task` tool, not new `grok` CLI processes — only by a second top-level `grok` invocation on the host. **Fix (in place):** the documented launch line pins a per-project socket, `grok --sandbox pipeline --always-approve --leader-socket "$(pwd)/.grok/leader.sock"`, and `./launch.sh grok` passes it automatically (a launch.sh regression that dropped the flag was caught and fixed in #190); distinct sockets give each project an independent leader (verified: with distinct sockets a second session left the first's turn running untouched; `.grok/leader.sock` is gitignored, created lazily by the leader, and orthogonal to session persistence, which is keyed by cwd so `--continue`/resume are unaffected). **Known edge (accepted):** a unix socket path is capped at ~104 bytes (`sun_path`), so a very deeply-nested project directory could overflow `"$(pwd)/.grok/leader.sock"`; deploy paths are user-chosen and normally short. **What would fully close the edge:** a shorter, collision-free socket path (e.g. a hash of the project root under a short runtime dir) if long paths ever appear in practice.

**Fixed footgun — grok's bash tool demotes the activated venv below `/usr/bin` (closed by `~/.local/bin` shims, #190).** grok rebuilds its bash tool's PATH prepending its own dirs (`~/.grok/bin`, `~/.local/bin`) plus the macOS default PATH ahead of every inherited entry, so the venv activated by `launch.sh` lands below `/usr/bin` and bare `python3` resolves to the system interpreter — no `sympy`/`matplotlib`/`wrds`, so python steps fail (captured on grok 0.2.93; the demotion mechanism independently reproduced via a login-shell `path_helper` rebuild). grok has no config knob to reorder its bash PATH (checked the full user guide). **Fix (in place):** `install_grok_venv_shims` in `launch.sh` writes `VIRTUAL_ENV`-keyed shims (`python3`/`python`/`pip3`/`pip`) into `~/.local/bin`, which grok's rebuild keeps ahead of `/usr/bin`. Shims are transparent outside grok (no active venv → exec the next real binary on PATH, skipping their own dir), marker-tagged, idempotently rewritten each launch, and never installed over a pre-existing non-shim file (warn-and-skip). **Trade-offs (accepted):** the shim is host-global — every shell on the host that resolves `~/.local/bin` early now routes bare `python3` through it (behaviorally identical by construction, but a new moving part); and the fix only auto-installs via `./launch.sh grok`, so a manual `grok --sandbox pipeline ...` launch on a host where the launcher never ran still hits the demotion. **Residual unknown:** grok's exact PATH-head ordering (`~/.local/bin` at position 2) comes from one captured session; re-verify with a live `echo $PATH` through grok's bash tool if a grok update changes shell setup.

**Fixed footgun — `git push` fails under grok's sandbox: macOS keychain unreachable (mitigated by an opt-in repo-scoped token store, #190).** The `osxkeychain` credential helper needs `mach-lookup com.apple.SecurityServer` (the legacy securityd endpoint of the classic `SecKeychain*` APIs); grok's Seatbelt profile denies it, and grok's `sandbox.toml` schema is filesystem+network only (`extends`/`restrict_network`/`read_only`/`read_write`/`deny` — no mach-service field), so the grant cannot be expressed. Discriminator verified with `sandbox-exec`: denying *only* `com.apple.SecurityServer` reproduces the failure (`errSecParam -50`); denying only `com.apple.securityd` leaves the keychain working. Consequence: with an HTTPS remote, every pipeline push (`core.md` commit discipline) fails on auth; commits stay local, runs are not blocked. **Mitigation (in place, opt-in):** `code/utils/setup_push_token.sh` writes a fine-grained PAT scoped to the project's backup repo into `.git/push-credentials` (0600, untracked) and switches the repo to a local `credential.helper store` (leading empty helper clears the inherited osxkeychain). `launch.sh grok` warns at launch when an HTTPS remote lacks the store. Chosen over a hand-maintained `sandbox-exec` keychain wrapper (re-exposes the whole keychain, macOS-only, duplicates grok's sandbox upkeep) and over external pushes (doesn't fit autonomous scale). **Trade-offs (accepted):** a token lives on disk (scoped to one repo — narrowest blast radius); the store path is absolute, so a moved project needs the script re-run; without opting in, grok runs are local-only.

**Limitations (four open, plus one closed record):**

1. **Single model tier collapses generator↔judge decorrelation.** xAI exposes one general-purpose model in v1 (`grok-4.5`), so every Claude tier maps to it. Claude, Codex, and Gemini use different generator/evaluator tiers where available; Grok and OpenCode cannot. Per-agent reasoning effort still varies on Grok, but that is weaker than a tier split. **What would close it:** an xAI capability-tier lineup.

2. **Grok subagent models are not probed/remapped.** Like the codex/gemini runtimes (see the model-availability section in `CLAUDE.md`), only *Claude* models are probed at setup and remapped on unavailability. If `grok-4.5` is withdrawn or the account loses access, grok agents hard-fail at launch with no fallback. The `model_fallbacks.json` schema and resolver/apply split are provider-agnostic; what's missing is a `grok models`-based probe and applying the remap over `.grok/agents/*.md`.

3. **Manual/report dispatch guidance — closed in v2.20.0.** The shared manual and report sessions now distinguish Codex's detached launcher from Grok/OpenCode native tasks.

4. **Skills and extension agents are not wired for grok.** `assemble_grok_agents.py` does not emit a `skills:` frontmatter list, and grok project-skill discovery is unverified (grok reads Claude-format skills at the user level; project-level discovery of `.claude/skills`/`.agents/skills` was not confirmed). The extension appliers (`apply_extension_empirical.sh`, `apply_extension_theory_llm.sh`) take the claude/codex/gemini agent dirs as positionals but not `.grok/agents`, so `--ext empirical` / `--ext theory_llm` deploy no grok extension agents while the extension's stage instructions are still baked into the shared `AGENTS.md` (a Grok orchestrator would be told to launch agents absent from `.grok/agents/`). Base theory-only agents are unaffected. **What would close it:** thread `$GROK_AGENTS_OUT` through both extension appliers (agents), and add a `skills:` emitter + confirm grok's project-skill path (skills).

5. **Grok cross-turn autonomy is unverified — `./launch.sh grok` may be only pseudo-autonomous.** codex verifiably has no autowake (a parent whose turn ended is never woken by a completing child), which is why its launch path is a headless driver loop; grok gets a plain interactive `exec grok` on the *assumption* it behaves like Claude (autowake-native). Whether a grok orchestrator turn-end between stages stalls until a human types has not been tested (the attempt during #190 verification hit an exhausted Grok usage balance — `402 Payment Required`). **Failure mode if the assumption is wrong:** unattended `./launch.sh grok --tmux` fleet runs silently park at the first inter-stage turn-end. **What would close it:** with balance restored, run a two-stage toy task through `./launch.sh grok` and observe whether the session self-continues past a turn-end; if it stalls, grok needs a driver loop analogous to codex's (`grok -p` single-turn + session resume exists, so the same driver shape fits).

**Tracking:** [#182](https://github.com/alejandroll10/zeropaper/issues/182) (extension agents), [#183](https://github.com/alejandroll10/zeropaper/issues/183) (manual/report dispatch fork — item 3, closed), [#184](https://github.com/alejandroll10/zeropaper/issues/184) (skills — item 4), [#185](https://github.com/alejandroll10/zeropaper/issues/185) (model probe + single-tier — items 1 & 2), [#190](https://github.com/alejandroll10/zeropaper/issues/190) (leader-socket regression, venv PATH shims, keychain push, autonomy verification — item 5).

## Macro empirical work has no identification gate

**Scope:** the `macro` variant, and any future `macro_empirical` variant or macro `--ext empirical` flow.

**Failure mode:** when the empirical extension is enabled for macro work, `empiricist` and `empirics-auditor` audit data, code, and methodology, but no agent gates **identification design**. A macro empirical paper can therefore reach Stage 6 with an under-specified SVAR identification scheme, an HFI surprise series that ignores the information effect / Bauer-Swanson predictability critique, narrative shocks without an exclusion argument, or a calibrated DSGE whose parameters are not actually identified by the chosen targets — and the pipeline will not catch this until referee-mechanism. Identification mistakes caught at the referee are expensive (a Major-Revision cycle minimum) compared to catching them at the plan stage.

**Asymmetry with finance:** the finance variant has `identification-designer` + `identification-auditor` (see `deploy_assets/extensions/empirical/agent_bodies/finance/`) wired into Stage 3a step 3, which gates the empirical plan on identification before execution. ## Closed: table-legibility source escapes now have a rendered semantic backstop

**Scope:** the Stage-5 and final-post-polish table-legibility gates — `arpipeline.sty` Layer 5, `table-auditor`, Stage-5 build/audit routing, and the paper-writer wide-table contract ([#85](https://github.com/alejandroll10/zeropaper/issues/85), [#253](https://github.com/alejandroll10/zeropaper/issues/253)).

The original Layer 5 measured only unstarred `\resizebox{...}{...}{<tabular>}` width against a fixed 0.6 ratio. Direct `\tiny`, `\resizebox*`, `\scalebox`, `adjustbox`, bare `array`/custom alignments, and image tables could therefore compile inside the margins with unreadable text. The old marker was also not literally a build failure: it was a `\typeout` that depended on the orchestrator running a later grep.

**Closed behavior:** Layer 5 now captures the document class's actual `\scriptsize` boundary and rejects a native `tabular`/`tabular*`/`longtable` below it. For `\resizebox` (plain and starred) and `\scalebox`, it typesets the natural content once, records the smallest source font observed, measures both realized dimensions, and rejects when the effective rendered size falls below that boundary. Command-form `adjustbox` gets the same source check for an unambiguous two-axis reduction, while allowing axis-exchanging transforms such as pure rotation; its one-axis and compound cases are decided by the rendered auditor because an axis-aligned before/after box cannot identify their glyph scale without false positives. This retains scale measurement — font-at-table-entry alone cannot see a transform applied afterward — and correctly permits a small source table scaled up to a readable result. Because the `adjustbox` environment hides its collected body from a compatible one-pass wrapper, any native table inside that environment fails closed; use native reflow/landscape or the measurable command form instead. `array` participates only inside a semantic table float, so resized equation arrays are not hard-classified as tables; rendered inspection remains the semantic backstop for table-like custom alignments elsewhere. A semantic table float whose only exhibit is `\includegraphics` fails as an inaccessible pre-rendered table; a native table may still contain images such as icons or sparklines. Every source violation includes `ARPIPELINE-TABLE-LEGIBILITY-FAIL` in both the diagnostic and the raised `\PackageError`, so trial typesetting that suppresses `\typeout` (for example `tabularx`) cannot hide the marker and `latexmk` exits nonzero rather than relying only on prompt compliance.

Source tokens cannot reliably decide that a graphic placed in a `figure` is semantically a table, recognize every custom alignment macro, or judge clipping/overprinting. The independent `table-auditor` therefore rasterizes and inspects every page of the main PDF and populated Internet Appendix after Stage 5 and again after final polish. It reads source for navigation but treats rendered pages as authoritative, so vector and raster image tables are both in scope; it explicitly excludes the invisible tiny provenance fingerprint. PASS is a completion precondition, REVISE routes through a capped paper-writer repair/rebuild/re-audit loop, and missing render tooling is GATE-BROKEN rather than a false PASS.

Nested box-scaling around table content also fails closed, even when its individual factors might compose above the floor: re-entrant transform measurement shares TeX scratch-box state, so accepting arbitrary nesting would reopen state-clobber bypasses. Nested transforms containing only figures remain legal. CI-enforced LaTeX regressions use the deployed skeleton's package order and cover the allowed `\scriptsize` boundary, normal/upscaled native tables, non-scaling and pure-rotation command `adjustbox`, scaled/nested non-table figures (including an `adjustbox` environment), direct and resized equation arrays, and native tables containing an image; and reject direct `\tiny`, plain/starred `\resizebox`, horizontal/vertical/nested `\scalebox`, a table followed by a nested figure transform, shrinking command `adjustbox`, table-bearing `adjustbox` environments, transformed `array` inside a semantic table float, undersized `longtable`/`tabularx`, and image-only semantic table floats. Assembly tests verify `table-auditor` across autonomous runtimes and its report-mode pruning.

## Core-bypass guard: early gate-time detection and orchestrator-only bypass recording remain optimizations

**Scope:** the core-bypass degradation guard (issue #51) — `docs/core_bypass.md`, `inject_core_bypass_into_agents` (setup.sh), the `{{CORE_BYPASS_GUARD}}` placeholder, `process_log/degradation_ledger.md`.

**Closed (terminal backstop, default mode).** A non-binding verification can no longer pass as a clean run. The session entry point (`deploy_assets/templates/runtime/claude/session.md`, shared by all three autonomous runtimes) refuses to set `status = "complete"` while `degradation_ledger.md` has an unresolved binding row (`binding? = yes`, `action` not `resolved`). Because every bypass — wherever it occurs in the run — leaves a durable ledger row, this terminal check makes "ran to success while a core was silently downgraded" impossible regardless of stage, *without* any `core.md` edit (re #27). This was the irreducible #51 complaint ("the run reports success while a core invariant was silently relaxed"); the backstop closes it mechanically in the default deploy, not just visibly.

**Amended in v2.12.0 (issue #179): the block is no longer always a halt.** An unresolved binding row from a **deferrable** outage — one whose source is down for a stated bounded horizon (a rate limit or credit budget with a reset time) *and* whose re-check is a cheap lookup — now completes as `status = "complete_pending_verification"` with the owed check recorded in `pipeline_state.json`'s `pending_verification`, and a later session re-runs it and self-completes. Everything else, plus any ambiguous classification, plus every case under `--halt-on-core-bypass`, still takes the `halted_core_bypass` path. Resolution is likewise no longer operator-only: a session may mark a row `resolved` for a binding verification **it re-ran itself and that came back clean** (evidence, not faith); all other resolution stays operator-driven. The invariant is unchanged — `complete_pending_verification` is not clean success — but a transient budget outage no longer parks a finished paper pending a human signature. See `docs/core_bypass.md`.

**Failure mode (two residual gaps — both latency/coverage optimizations, not soundness holes):**

1. **No gate blocks *earlier* than completion.** The gates themselves — `scorer`, `editor`, `referee`, the polish auditors — still do not read `degradation_ledger.md`. A degradation that occurs before a gate (e.g. a `codex-math` outage misclassified at Gate 2) is caught at completion, not at the gate, so the run can burn the intervening stages before halting. This is a wasted-work cost, not a correctness gap: the terminal backstop still prevents a degraded run from reporting success. (The surfacing example — a Stage 8 bib-verify downgrade — occurs *after* every gate, so for it the terminal check is the only possible mechanical block anyway.)

2. **Default mode does not record orchestrator-only bypasses (conditions 2-3).** Gate-skipped and designated-agent-substituted are events only the orchestrator can detect (an agent can't see that it was skipped). The default (no-flag) deploy intentionally leaves the orchestrator doc (`core.md`) untouched to avoid runtime-doc growth (issue #27), so in default mode only agent-detectable bypasses (conditions 1 and 4 — source-fallback, tool-misclassification) are recorded; conditions 2-3 are recorded/halted only under `--halt-on-core-bypass`. Note that *if* a 2-3 event is recorded (under the flag, or by a future default-mode recording step), the terminal backstop blocks completion on it for free — the recording is the only missing half.

**What would close them:** (1) add a hard-requirement check to `scorer` (and the Stage 6 `editor`) that reads `degradation_ledger.md` and treats any unresolved `binding? = yes` row whose core is a gate the paper relies on as a blocking condition (REVISE/hold) — moving detection earlier than completion. (2) Inject a minimal orchestrator-side recording instruction even in default mode — a recording step in the relevant pointed-to stage docs (`docs/stage_*.md`, off the runtime-doc budget) at each gate's skip/substitution decision point. Agent-substitution (condition 3) has no cheap mechanical detector beyond orchestrator self-report and remains the irreducible flag-only residual.

**Tracking:** [#51](https://github.com/alejandroll10/zeropaper/issues/51) is the closed originating issue; [#61](https://github.com/alejandroll10/zeropaper/issues/61) tracks the two remaining optimizations (reopened because this entry still describes unresolved work).

**Interim behavior:** the terminal completion-block in `deploy_assets/templates/runtime/claude/session.md` guarantees no degraded run reports clean success in any autonomous pipeline mode (i.e. not `--mode report` or `--manual`, which have no `status` machine and so get the record-and-surface half only); earlier gate-time detection (gap 1) and default-mode recording of conditions 2-3 (gap 2) are deferred as latency/coverage improvements, and conditions 2-3 are fully halted under `--halt-on-core-bypass`.

## Codex fire-and-forget: `--once` interactive mode has no result-collection driver

**Scope:** the codex launch protocol — `code/utils/agent_launcher/launch_agent.sh` (fire-and-forget), `launch.sh`'s `--once` branch, and `deploy_assets/templates/runtime/codex/{session,session_manual,session_report}.md`.

**Why.** `launch_agent.sh` returns as soon as the worker is detached (it must — a blocking launcher trips codex's ~10s silent-exec cap and is reaped as `UnknownProcessId`). In the headless driver (`./launch.sh codex`) this is invisible: `wait_for_workers` blocks between turns until every sentinel clears, and the driver re-prompts the orchestrator to collect. But `./launch.sh codex --once` (plain interactive TUI) has **no driver and no autowake** — after a launch returns immediately, the human must manually type "continue" (or poll) to get the orchestrator to collect the detached worker's result. Under the old blocking launcher the `--once` user got collection for free (the call just blocked).

**Failure mode:** a `--once` operator launches an agent, sees the launcher return instantly, and either (a) waits at a stalled prompt expecting inline output that never comes, or (b) writes a `sleep`-loop poll in one command and reproduces the `UnknownProcessId` cap. Neither corrupts state (the worker still finishes and writes `$OUTPUT`), but it is an operator-experience regression.

**What would close it:** a lightweight `--once` collect helper (or a TUI hint after each launch: "worker detached — type 'continue' when you want to collect"). Low priority: `--once` is a debug path; production is the headless driver, which handles collection automatically.

**Tracking:** [#242](https://github.com/alejandroll10/zeropaper/issues/242).

## Codex fire-and-forget: worker success/failure is a text banner in `$OUTPUT`, not an exit code

**Scope:** `code/utils/agent_launcher/launch_agent.sh` and any future programmatic reader of `process_log/agent_runs/*.md`.

**Why.** The old blocking launcher conveyed worker success/failure via its own synchronous exit code. Fire-and-forget returns 0 on successful *detach*, before the worker's outcome is known; the worker's actual rc is surfaced only as a `WORKER FAILED (rc=N)` text banner written into `$OUTPUT` on failure (plus a `tail -40` of the worker log). This is fine for the LLM orchestrator, which reads the file and is told (in `session.md`) to treat the banner as failure. But it means a **failed** agent produces a *non-empty* output file whose first line is the banner.

**Failure mode:** no current script parses `agent_runs/*.md` programmatically (verified repo-wide), so today's blast radius is nil. But a *future* programmatic consumer (a hypothetical claim-verifier, scribe, or synthesis step that reads another agent's raw `agent_runs` output directly rather than a committed stage deliverable) that treats file-non-empty as success would ingest a failure banner as if it were a real result.

**What would close it:** any such future consumer must check for the `WORKER FAILED (rc=` prefix before trusting the content; alternatively, add a machine-readable rc sidecar (e.g. `$OUTPUT.rc`) if a programmatic consumer is ever introduced. Documented here so the constraint is explicit rather than a surprise.

**Tracking:** [#243](https://github.com/alejandroll10/zeropaper/issues/243).

## Codex driver: worker liveness is inferred from the wrapper pid alone, so a pid-targeted kill can orphan a live worker

**Scope:** `wait_for_workers()` in `launch.sh` (codex driver only — the opencode driver tracks background work through server-side quiescence and does not use sentinels).

**Why.** Since v2.21.2 the wait decides whether a detached worker is still running by probing the `wrapper_pid` recorded in `process_log/agent_runs/.<agent>.running` with `kill -0` (plus `wrapper_lstart` as a pid-reuse guard where both sides captured it). That is the strongest signal available: `ps`/`pgrep` return nothing inside a codex sandbox without sysmond, which is also why `wrapper_lstart` is frequently empty. But `launch_agent.sh` runs the actual `codex exec` worker as an ordinary foreground child of the wrapper script rather than `exec`ing it in place, so wrapper and worker are two processes with one recorded pid between them.

**Failure mode:** a kill that targets the wrapper's pid alone — not its process group — leaves the worker running and unparented. The driver then reads the wrapper as dead, clears the sentinel, and the orchestrator (seeing no sentinel and a possibly-partial output file) may relaunch the same agent while the orphan is still writing the *same* `$OUTPUT` path, which the pipeline deliberately reuses across attempts. Two writers on one file can interleave a partial report with a fresh one and produce a plausible-looking hybrid that no gate would flag. Ordinary shutdown paths do not do this: a driver exit, a `TERM` to the process group, or a machine reboot takes wrapper and worker together, and the pre-v2.21.2 code made the same wrapper-pid-is-the-worker assumption, so this is a long-standing property rather than a new regression.

**What would close it:** have `launch_agent.sh` record the worker pid alongside the wrapper pid (or `exec` the worker so a single pid covers both), and treat *either* being alive as pending. A cheaper partial mitigation is to make the worker write to a unique per-attempt path and have the wrapper promote it to `$OUTPUT` on completion, so two live writers can never share a file. Neither is implemented; the driver currently trusts that nothing kills a bare wrapper pid.

**Tracking:** [#245](https://github.com/alejandroll10/zeropaper/issues/245). This is distinct from #223, which fixed incremental-output precedence while the wrapper remains alive.

## llm_cognition variant: shipped preprint is venue-neutral — the official venue style file is not bundled

**Scope:** every llm_cognition deployment. Closed in v2.14.0 (issue #200): llm_cognition ships its own skeleton (`deploy_assets/templates/paper_skeleton/llm_cognition/{main,internet_appendix}.tex.template` — single-column, 10pt, numeric citations, ML section order, a post-references checklist slot; the IA matches the main paper's format), `docs/stage_5.md` and `paper-writer` carry variant-conditional `related_work.tex` / `experiments.tex` / `checklist.tex` sections (via `VARIANT_LLM_COGNITION` markers resolved in `setup.sh`), and the page budget is vocab-keyed (`PW_LENGTH_RULE`).

**What remains:** the pipeline deliberately does not fetch or emulate a specific venue's class file (`neurips_20XX.sty`, `icml20XX.sty`, `iclr20XX.sty`, `tmlr.sty` — year-versioned, license-bound, and submission-cycle-specific). The shipped PDF is a venue-neutral ML preprint: content and section structure conform, but camera-ready submission still requires swapping in the venue's official style file at the `\documentclass`/`\usepackage` layer. **Failure mode it can produce:** an operator submits the shipped PDF directly and gets flagged for a missing official style/checklist form. Treat the style-file swap as the one manual step between the shipped preprint and a venue submission; the arXiv-first norm in ML makes the preprint itself the artifact most readers see.

## llm_cognition variant: economics-only skills still installed — CLOSED in v2.15.0

**Closed (issue #205):** `setup.sh` gates `ssj` and `nber-agenda` out of llm_cognition deployments (`variant_wants_skill` — assembly, utils copy, deps install, and the manual-mode catalogs all consult it), and `update.sh` gained a generic stale-infrastructure sweep: any path recorded as infrastructure in the target's old manifest but absent from the fresh manifest is removed on refresh, so pre-gating llm_cognition deployments converge to the gated state on their next `update.sh` run. ## Stage 0 discovery-exhausted: the re-scan branch terminates on judgment, not on an enumeration — CLOSED in v2.24.4

**Scope:** every variant. Introduced in v2.18.0 with the `stage-0-discovery-exhausted` branch-manager context (issue #156); substantially narrowed in v2.18.1 (issue #218).

Before v2.24.4, when problem discovery exhausted every gap without ever scoring a question (`gate0_best_question_score == -1`), `docs/stage_0.md` Step 0b launched `branch-manager`, which recommended RESCAN-NEW-DOMAIN, RESCAN-CORRECTED, or OPERATOR-ESCALATE. The intended per-domain budget was one fresh scan plus at most one corrected re-scan; if the domain space were finite, that would imply a bound of twice its size. The domain space was deliberately open, however, so actual termination rested on branch-manager judgment. **As shipped in v2.18.0**, spent domains were recorded only in the reports themselves (`output/stage0/branch_manager_discovery_p*.md`) — see the fix below.

**Fixed in v2.18.1 (#218):** the two concrete defects are gone. Step 0a now appends every domain it scans to `output/stage0/domain_log.md` (`{domain} — fresh scan` / `{domain} — corrected re-scan: {correction}`), a run-scoped log that — unlike `gap_log.md` — the Stage 0 entry hook never clears. Dedup is now an exact read of one log written by the agent that chose the domain, rather than a fresh `branch-manager` re-deriving the spent set from N prior reports' free text; branch-manager reads the log instead of every `branch_manager_discovery_p*.md`, and the report's "Domains already spent" section and the "your report is the durable record" rule are both deleted, since the log is the record. `--variant macro` gained a real sub-domain decomposition (monetary, fiscal, growth, labor search, international, heterogeneous-agent, expectations, macro-finance, business-cycle measurement), so RESCAN-NEW-DOMAIN has something to name there.

**What remains, by design:** `DOMAIN_AREAS` was deliberately **not** converted into a closed enumerated list (`DOMAIN_LIST`), which is what #218 originally proposed. A closed taxonomy would let the pipeline mistake "covered the enumeration" for "covered the field" and would freeze each variant's domain space at whatever `setup.sh` happened to name — the failure mode the repo's "prefer no structured classes" principle exists to prevent. The scope is therefore documented as naming starting points, and `branch-manager` may name an in-scope domain the scope does not list.

**Former failure mode:** an open domain space has no finite enumeration, so the nominal 2 × |domains| bound was not a numeric guarantee. Termination rested on branch-manager judging that no materially different in-scope domain remained. A pathological run could keep renaming or subdividing thin domains; `problem_attempt` and the visible log made that behavior observable but did not cap it.

**Closed in v2.24.4 (#252):** `loops.stage0_discovery` grants at most 100 physical broad-scout launch permits across the entire unseeded pipeline run; seeded and faithful runs bypass discovery. Stage 0 re-entry, successful handoff to Stage 1, and Regeneration Rounds all preserve this run-global budget. Every initial launch and crash retry commits a distinct permit first; a broad map counts only after atomic publication from its permit-specific staging path, and an incomplete launch at the cap routes to autonomous salvage instead of re-launching, so physical launch 101 is impossible even across repeated crash windows. Durable phase/substep state and stable gap IDs resume and reconcile selection, characterization, posing, review, logs, or routing without inferring progress from stale/partial canonical artifacts or duplicating near misses. `stage0_discovery_episode_start_attempt` separately scopes the compact near-miss portfolio and versioned source-map snapshots to the current search for a scored question; every downstream return increments `problem_attempt`, so a later Stage 0 episode cannot reuse stale candidates or archive names. Before the cap, branch-manager may still use substantive judgment to choose a new domain, one corrected scan, or early promotion; at the cap both re-scan verdicts are forbidden. `PROMOTE-NEAR-MISS` uses a durable three-way cap context: downstream returns reframe the failed question, incomplete permit-100 scans retain their instruction and current-episode evidence, and active legacy updates salvage whatever partial artifacts survived. Each route runs one final targeted gap characterization and sends the result through the ordinary independent question-poser/question-referee gate without another broad scan. This makes the numeric ceiling a runaway guard rather than a closed taxonomy: the pipeline neither claims the field has no questions nor halts for ordinary research judgment. Because no pre-#252 state can prove its lifetime physical-launch count, updating a non-pristine legacy deployment fails closed by consuming the full budget and continuing through autonomous salvage; only a pristine never-started deployment is initialized at zero. Legacy artifact inspection uses no-follow deployment-directory descriptors; the updater resumes the exact retired `halted_no_viable_question` status at Stage 0, while other safety halts remain untouched.

**Tracking:** [#156](https://github.com/alejandroll10/zeropaper/issues/156) (original undefined terminus — closed), [#218](https://github.com/alejandroll10/zeropaper/issues/218) (domain-log/open-domain redesign — closed), [#252](https://github.com/alejandroll10/zeropaper/issues/252) (global termination gap — closed in v2.24.4).

## Stage 0 domain history can be incomplete after a legacy mid-run update

**Scope:** deployments created before v2.18.1 and updated while already inside Stage 0. New deployments are unaffected.

`domain_log.md` starts at the first Step 0a that runs under v2.18.1+. A deployment created on v2.18.0 (or earlier), already inside a Stage 0 that exhausted discovery, and then refreshed by `update.sh`, reaches the `stage-0-discovery-exhausted` branch with no log — or with a log holding only the domains scanned after the refresh. Domains scanned before it are recorded only in the free text of that run's `branch_manager_discovery_p*.md`, so branch-manager can re-recommend one as untried or repeat corrected-scan budget already spent before the refresh. The redundancy is confined to deployments refreshed before v2.24.4. From v2.24.4 onward, a non-pristine legacy run whose lifetime launch history is unknowable fails closed at the 100-permit ceiling and proceeds through autonomous salvage rather than granting more broad scans. A Step 0b history backfill from the old reports was implemented and removed — the old reports recorded a correction only `used`/`available`, never its wording, and no placement of the trigger closed every ordering, so the guard kept failing in ways the unguarded gap does not. `branch-manager.md` instead tells the agent to report a missing log rather than read it as "nothing tried."

**Tracking:** [#241](https://github.com/alejandroll10/zeropaper/issues/241).
