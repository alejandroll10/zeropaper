# LIMITATIONS

Known architectural limits in the pipeline. Each entry: failure mode, what would close it, tracking issue.

Per `CLAUDE.md` ("no unsolved, undocumented, or untracked architectural limits"), additions go here when a limit is identified during a pipeline edit but not closed in the same pass, and every addition must link its corresponding GitHub issue.

---

## `--mode data-first`: coverage completeness has no ground truth

**Scope:** the data-first Stage 3a validation chain (`data-integrity-auditor`, `data-selection-auditor`, `coverage-auditor`) on the built dataset.

**Failure mode:** the audits verify what is *in* the dataset and that the triangulation protocol was actually executed, but nothing can verify the *absence* of missed events — an unscheduled event all consulted sources omit survives every audit. Mitigation: the mandatory coverage-triangulation protocol (≥2 genuinely independent sources per event class, written per-discrepancy reconciliation, spec-stated waivers for single-sourced classes) plus the required irreducible-residual disclosure in the paper's validation section. The residual — all sources sharing a blind spot — is irreducible in principle.

**Tracking:** [#281](https://github.com/alejandroll10/zeropaper/issues/281).

## `--mode data-first`: source-license interpretation and provenance semantics remain judgments

**Scope:** the Gate 2 spec audit's machine-readable rights inventory and the offline data-release producer's input-provenance declarations.

**Closed mechanical gap:** the trusted results runner now prevents an ordinary networked analysis from publishing beneath `output/dataset/`. A dataset release is a separate offline, credential-free run whose plan must match Gate 2's accepted inventory path, SHA-256, and current theory version in an autonomous deployment. A manual data-first deployment instead declares explicit caller authority over the exact path, digest, and positive dataset version; the runner checks that authority against `.deploy_manifest.json` and rejects an invented manual `pipeline_state.json`. It classifies every non-manifest producer input as data or the single paired-analysis control. Before publishing any byte, the runner requires every data input and every released data file to map only to source IDs classified `open`, rejects restricted IDs, and verifies a complete role-labelled checksum manifest. Analysis and release receipts activate or retire atomically as a pair, and replacement halves must carry matching supersession lineage.

**Residual failure mode:** no generic runner can determine whether the accepted license interpretation is legally correct, whether build code has embedded data constants, or whether a producer has hidden a runtime code dependency in a data-bearing input. The runner permits only the paired analysis receipt as a `control` input, rejects ordinary source-code suffixes in data inputs, and packages every declared code dependency byte-for-byte at its original path, but arbitrary dynamic loading is not decidable from declarations alone. The independent spec and empirics audits check those semantics, but they remain judgments. Closing that residual would require authoritative machine-verifiable license attestations at each source plus whole-program information-flow and runtime dependency tracing through the release program; a per-column manifest alone would merely move the same trust assertion downstream.

**Mechanical enforcement shipped:** [#282](https://github.com/alejandroll10/zeropaper/issues/282).

**Residual tracking (low priority):** [#292](https://github.com/alejandroll10/zeropaper/issues/292).

## `--mode data-first`: release is a static snapshot — no maintenance automation

**Scope:** the data-first release artifact (`output/dataset/`).

**Failure mode:** part of the value of the exemplar datasets comes from periodic updates; a one-shot run promises only a versioned snapshot plus the mechanically verified declared build-code closure, and the paper templates scope the release claim accordingly. What would close it: a post-release update automation mode (re-execute build + triangulation on the existing spec, publish a new dataset version).

**Tracking:** [#283](https://github.com/alejandroll10/zeropaper/issues/283).

## `--mode data-first`: descriptive-facts boundary is prompt-and-polish, not a hard gate

**Scope:** causal-overreach control in data-first papers, with the identification agents pruned by design.

**Failure mode:** the guards are the scorer's contribution-class fidelity block (a causal headline is an H1/H5 FAIL), self-attacker/referee vocab, referee-mechanism's descriptive-discipline dimension, and the re-targeted `polish-identification` Stage 9 pass — a mechanical backstop, but a late one. A fact stated causally could still ship if every guard misses it. What would close it: a mechanical causal-verb lint over facts-section prose at the Stage 5 build gate, or re-admitting the identification agents behind a per-fact causal flag (parallel to the deferred [#26](https://github.com/alejandroll10/zeropaper/issues/26)).

**Tracking:** [#284](https://github.com/alejandroll10/zeropaper/issues/284).

## WRDS daemon: a deadline-less healthcheck can wedge the singleton permanently after an upstream flap — CLOSED in v2.30.6

**Scope:** `--ext empirical`'s shared WRDS daemon (`deploy_assets/extensions/empirical/utils/wrds_server.py`), specifically `healthcheck()` and the `_busy_health()` ping path.

**Failure mode:** `healthcheck()` holds the daemon's state lock while running `SELECT 1` via `_healthy(self.db)` with `deadline=None`, so a connection that went half-open during a transient upstream outage blocks the check indefinitely at the socket layer. Every later ping then fails fast with "prior WRDS healthcheck is still in progress" while `wrds_auth_error()` stays empty, which the Stage 3a preflight reads as WRDS-unreachable: a seconds-long network flap becomes a persistent `halted_wrds_unreachable` that survives upstream recovery. The runtime doc's recovery notes then point the operator at the wrong repair ("restore the WRDS service") — the service is up; the daemon is wedged. SIGTERM cannot clear it (graceful shutdown waits on the same lock) and `start_services.sh` correctly refuses to replace a live singleton, so recovery requires SIGKILL of the recorded PID plus a service restart. Observed twice in one day on a live run (eventcal, 2026-08-26, project commits `e762cde`/`5c8aedc`).

**Closed in v2.30.2:** the daemon installs libpq socket guards (TCP keepalives + `tcp_user_timeout=60s`) into `_connect_args` at first login, so a half-open socket surfaces a socket error within about a minute instead of blocking until the kernel gives up; `healthcheck()` bounds its probe with a real deadline recorded in the lock-owner metadata, and `_busy_health()`'s healthcheck branch distinguishes in-progress from past-deadline like the command branch. Closing the wedge exposed a latent false-latch hazard in tier-2 recovery (an exhausted caller deadline after a spent-and-successful login reached `_latch_login_failure` and branded a working credential as rejected — pre-existing on the command path too); fixed by computing the reconnect budget before the write-ahead marker (expiry aborts as a timeout with no marker and no login) and running post-login verification under a fresh grace budget that also extends the recorded owner deadline. `psycopg2-binary>=2.9` floor pinned (older libpq hard-rejects `tcp_user_timeout`). Regression scenarios [8a]/[8b]/[8c] in `test_wrds_auth_latch.sh` cover the slow-successful reconnect, the expired deadline, and the discriminating sub-second-deadline pre-marker abort. The one-login-attempt invariant is preserved on every path. What remains open by design: a ping during an active in-budget healthcheck still reports not-ready (a probe mid-recovery does not prove DB health), and the preflight halt text still names generic unreachability rather than a distinct wedged-daemon diagnostic — with the wedge now self-healing in ~2 minutes, that diagnostic no longer has a persistent state to name.

**Tracking:** [#291](https://github.com/alejandroll10/zeropaper/issues/291) (closed).

## `results_pipeline` runner inherits the caller's shell timeout — a short synchronous call silently destroys a long producer run

**Scope:** `--ext empirical`'s trusted results runner (`results_pipeline.py run`), on every producer whose runtime exceeds the invoking agent's synchronous tool timeout — in practice every data-first acquisition build.

**Failure mode:** `execute()` has no wall-clock allowance of its own, so the effective limit is whatever the invoking tool call happens to grant; an interruption discards the entire disposable isolated workspace by design (atomic publish, nothing resumable). A 30-second synchronous call therefore silently destroys a legitimate ~20-minute acquisition — observed on a live run (eventcal, Stage 3a v6/a14, 2026-08-27), costing a debug cycle plus a full rebuild for a launcher-pattern mistake. v2.30.7 closes the instruction gap: `results_evidence.md`'s `run` procedure now leads with the mandate to launch through a harness-tracked long-allowance job and poll it. The mechanism gap remains: an agent that ignores the mandate reproduces the total loss.

**What would close it:** a runner-owned wall-clock allowance declared in the plan rather than inherited ambiently (insufficient alone — the runner cannot survive an external SIGKILL), receipt-safe acquisition checkpointing (a content-addressed source-cache layer a fresh attempt may re-verify and reuse without weakening the atomic-publish contract), or at minimum a startup stderr banner stating the expected duration and tracked-job requirement. The banner shipped in v2.30.12 after the failure mode recurred in the field (tradingdays Stage 3a a4, 2026-08-28 — three 30-second kills despite the v2.30.8 doc mandate, confirming doc-only is insufficient). After a fourth occurrence (tradingdays v8/a30, 2026-08-31: a ~30-second child exec killed the runner during workspace setup even though the same project's a19 diagnostic had prescribed tracked-job launches), v2.32.0 shipped the declaration mechanism: `run` and `run-empirical` refuse to start unless `--caller-allowance-seconds` declares at least 1200 seconds of caller lifetime, with refusal before any lock or workspace work and refusal text carrying the tracked-job launch instructions. **What remains open:** the declaration is honor-system by construction (a caller can overstate it and still kill the run), and receipt-safe acquisition checkpointing has not been built — an interrupted long acquisition still loses all progress.

**Tracking:** [#293](https://github.com/alejandroll10/zeropaper/issues/293) (was closed 2026-08-27 before three of the four field failures were logged; reopened 2026-08-31 for the checkpointing/honor-system residual).

## `deepvest` skill: an LLM-mediated data source has no raw re-query path for the integrity audit

**Scope:** the `--ext empirical` `deepvest` skill (`code/utils/deepvest_utils.py`, MCP server `api.deepvest.ai/mcp`) and the Stage 3a step 7.5 `data-integrity-auditor`, which verifies cached field values by re-querying the source.

**Failure mode:** DeepVest answers its natural-language `query` tools through a vendor-side LLM over an undisclosed upstream feed, keyed on current tickers. A re-query through the same layer is not byte-reproducible and can return a *different plausible* answer instead of a contradiction, so a cached pull with the wrong price basis (a live `quick_analysis` close was dividend-adjusted without saying so), a survivorship-biased ticker list, or a silently dropped screener filter can pass the audit — or a string comparison can flag a false disagreement. The skill body mitigates (raw tables / `format="json"`, first-pull cache JSON as the binding record, numeric comparison with tolerance, a mandatory cross-source check logged in `data_search_log.md`, no provenance badge, DeepVest's own backtests/optimizations never reported as results), but nothing mechanical enforces the cross-source check.

**What would close it:** a vendor raw-data endpoint (the portal's "REST API" tab is a *Coming Soon* placeholder as of 2026-08-21) or a disclosed upstream feed the auditor can re-pull outside the LLM layer; an auditor rule for LLM-mediated sources (re-issue the identical cached `(tool, arguments)`, parse both with `tables_from_response`, compare within the `returns_spreads_coefficients` tolerance class, treat shape drift as REVISE); and a `[HEADLINE]` guard refusing a headline whose only source is an LLM-mediated pull without a logged cross-source check.

**Tracking:** [#272](https://github.com/alejandroll10/zeropaper/issues/272).

## Update quiescence is cooperative for processes outside supported launchers

**Scope:** applying `update.sh` replacements to an existing deployment while another same-UID process can mutate that project.

**Failure mode:** path validation alone cannot bind a later pathname mutation. A concurrent writer can rename a validated managed parent and replace it with a symlink before replacement; a Round-11 reproduction swapped `.claude` after validation and redirected the old updater's `rm`/`cp` operations into an external directory. v2.24.0 closes this for every supported runtime: `launch.sh` keeps a shared `fcntl` lock on a parent-Bash-owned project-directory descriptor for its full process lifetime, `update.sh` acquires the exclusive side before creating any target path, and each parent runs the complete runtime/update body in a child subshell with that descriptor closed so descendants cannot unlock or leak it. A stray detached OpenCode server is also refused as defense in depth. No pathname lock, separate holder, or reusable readiness file exists. Thus normal Claude/Codex/Gemini/Grok/OpenCode launch-vs-update concurrency fails before target mutation.

**Operational boundary:** stop any process that accesses the project without going through the deployed `launch.sh` before updating. The lock is cooperative; an arbitrary same-UID script can ignore it, and the updater cannot infer every process with a file descriptor or future pathname into the project.

**What would close it:** make every target mutation descriptor-relative, no-follow, and race-bound—including directory replacement, stale sweep, `.env` merge, venv bootstrap/guard refresh, and manifest replacement—or add a cross-platform OS confinement mechanism proven safe even when an allowed project inode is concurrently renamed outside its original path. Regress with a non-cooperating rename/symlink attacker that proves both external paths and project-owned user content remain unchanged.

**Tracking:** [#259](https://github.com/alejandroll10/zeropaper/issues/259).

## Codex native subagents are same-turn, process-resident work

**Scope:** the Codex runtime under headless `codex exec`, its native custom roles in `.codex/agents/`, and the parent-turn watchdog in `launch.sh`.

**Current behavior.** Codex 0.147.0 exposes native role selection through `agent_type` and applies each role file's `model`, `model_reasoning_effort`, and developer instructions. The launcher pins the parent to MultiAgent V2 in both headless and interactive `--once` sessions, so ordinary user config cannot remove the assembled role tool surface and `--light` Luna uses the same four-slot schema as the runtime instructions. Every generated role then sets `project_doc_max_bytes = 0` (so evaluators do not inherit the orchestrator AGENTS.md), `[features.multi_agent_v2] enabled = false`, and `[agents] enabled = false`. Both child switches are required because Codex 0.147 evaluates the V2 feature first; the role's session-flag layer keeps the child a leaf against parent CLI/session flags and ordinary user config. Legacy managed_config/MDM layers and enterprise feature requirements are the explicit residual below. The headless launcher restores trust for exactly the deployed physical project after `--ignore-user-config`; otherwise Codex omits project roles. The orchestrator must keep the spawning turn alive, wait until every requested child is terminal, and validate its artifact before returning. Because the four-slot session includes the parent, fan-outs run in bounded waves of at most three live children (or a smaller runtime-reported capacity), validating a terminal result before refilling its slot and preserving the stage-defined combined/no-commit boundary. Each headless turn runs in an anchor-backed process group. An independently grouped watcher reads a parent-liveness pipe; on ordinary completion, parent death, or timeout it stops the anchored root group, recursively discovers descendant-owned process groups (including Codex shell tools that call `setsid()`), stops them to a stable snapshot, binds every live member to a kernel identity (pidfd/procfd on Linux, kqueue on macOS), kills the bound groups, and retains its independent project shared lock until every bound identity has exited. A credential-free regression uses a TERM-ignoring setsid tool child and proves neither timeout recovery nor visible-supervisor SIGKILL releases the lock first. Timeout therefore fails closed through a complete bound-tree KILL rather than trusting Codex's Linux-only, ignorable parent-death TERM.

**Empirical boundary.** A production-shaped canary verified that `agent_type=scorer` ran the scorer instructions on `gpt-5.6-terra` at high effort with no parent conversation or AGENTS.md, wrote its requested artifact, reached terminal status, and woke the waiting parent, which verified the exact bytes before returning. The canary is repeatable through `ZEROPAPER_RUN_CODEX_NATIVE_CANARY=1 bash deploy_assets/scripts/test_codex_native_live.sh` (it is opt-in because it consumes live Codex credentials and model tokens). A second source-audit canary spawned a 20-second child and let the primary `codex exec` turn finish immediately: the top-level process exited and the child recorded `turn_aborted` / `interrupted` after 1.786 seconds. The source matches the observation: primary-turn completion requests shutdown of the in-process app server. Native completion wakes an active waiting parent; it does not resurrect a finalized headless turn.

**Failure mode:** if the parent violates the in-turn wait invariant, the `codex exec` process crashes, or the 59-minute watchdog terminates a hung parent/child cohort, unfinished children are interrupted. They do not survive as detached background jobs, and an interrupted writer may leave a syntactically plausible partial file. In a live turn, only terminal-status outputs validated by the parent are usable, and the canonical stage keeps its own combined or no-commit boundary. After interruption, autonomous recovery treats every task-owned uncommitted diff as incomplete regardless of apparent contents: its owning agent rewrites or repairs the exact output, the parent validates it, and then follows that stage's required commit/routing sequence. Committed stage boundaries are the durable recovery receipts. A healthy child that exceeds the watchdog is indistinguishable from a hang and is retried from the last such boundary. Manual `--once` work has no autonomous recovery loop, so its operator must apply the same terminal-status and artifact-validation rule after a client/process interruption.

**Lifecycle closure:** a persistent app-server driver with a verified durable cross-turn completion trigger and crash recovery for child state, or upstream persistence that lets a new process adopt live children. Until then, the same-turn invariant plus stage-defined durable boundaries is the fail-closed design.

**Other residuals under the same Codex boundary:**

1. **CLI/config compatibility is version-floored, not capability-probed.** Launch rejects Codex below 0.147.0, but native dispatch depends on `agent_type`, fresh-fork semantics, project role loading, `--ignore-user-config`, the exact-project trust override, permission-profile keys, `project_doc_max_bytes`, and `[agents].enabled`. A future version can rename or change one of those surfaces. Strict config and nonzero native errors should fail loudly, and the opt-in live canary detects behavioral drift when run, but setup does not execute that credentialed/token-consuming probe. **What would close it:** a credential-free upstream capability/introspection API broad enough to validate the complete role/permission contract at setup, or a maintained upper compatibility bound plus mandatory release canary.

2. **Codex model availability is not probed or remapped.** Setup probes Claude tiers only. If a pinned Codex role model is withdrawn or unavailable to the account, native spawn terminates as infrastructure failure and the pipeline cannot self-heal to a fallback. **What would close it:** a non-billing Codex model-availability probe wired through the existing provider-agnostic fallback resolver and applied to every generated role.

3. **Tool/sandbox authority is coarser than Claude role metadata (accepted design trade-off).** Native roles share the parent Codex permission profile and Codex's filesystem/network sandbox; the assembler does not translate each Claude agent's `tools` allowlist into a per-role command surface. A Codex evaluator can therefore invoke shell tools even when its Claude definition omits Bash. Roles remain project/credential confined and recursive agent dispatch is disabled, but evaluator tool minimality is advisory rather than kernel-enforced. We deliberately do not make evaluator roles read-only because they must write verdict artifacts and many legitimately execute validation code. **What would close the granularity difference:** upstream per-role tool allowlists that can retain required artifact writes/validation commands without granting unrelated tools.

4. **Managed configuration can override part or all of role isolation.** Codex 0.147 inserts the custom-role file as a `SessionFlags` layer. Ordinary cloud `EnterpriseManaged` config sorts below it, but legacy `managed_config.toml` and MDM layers sort above it and can supersede every role pin. Separately, enterprise/system feature requirements can force `features.multi_agent_v2=true`; because Codex checks V2 before `agents.enabled`, that alone restores recursive agent tools even though the role disables the legacy switch. `--ignore-user-config` removes neither mechanism. The live canary proves resistance to a hostile parent session override, not to either managed path. **What would close it:** setup/launch introspection of the effective child config and feature requirements with a fail-closed conflict check, or an upstream immutable role-isolation capability that managed policy cannot silently weaken.

5. **Post-hoc process-tree binding cannot capture every adversarial process escape.** The watcher closes the actual Codex 0.147 shell-tool shape—direct children call `setsid()` but retain ancestry until cleanup—and the regression proves that separate session is stopped, killed, and gone before the update lock is released. A deliberately daemonizing/double-forking command can leave the turn ancestry before the watcher freezes it; a process already reparented after otherwise normal Codex exit has the same problem. A still-descendant command can also deliberately join a pre-existing, non-descendant-owned process group in the same session: the watcher excludes that group so it cannot freeze or kill trusted outer-launcher processes, and therefore cannot safely signal the escaped member through the group identity. The runtime sandbox still confines these processes, and pipeline prompts never authorize daemonization or process-group escape, but the launcher cannot claim kernel-complete containment for arbitrary adversarial process behavior. **What would close it:** make the watcher an ancestor and proactive identity-bound fork tracker before Codex starts (Linux subreaper/cgroup or PID namespace), plus a portable macOS-equivalent containment mechanism; otherwise upstream Codex must expose a durable process tracker/cleanup contract that survives hard parent death.

**Tracking:** [#240](https://github.com/alejandroll10/zeropaper/issues/240) covers lifecycle, CLI/config compatibility, model probing, and the accepted tool-authority difference. Removing the detached protocol closed [#242](https://github.com/alejandroll10/zeropaper/issues/242), [#243](https://github.com/alejandroll10/zeropaper/issues/243), and [#245](https://github.com/alejandroll10/zeropaper/issues/245) in v2.25.1. Gemini's separate confinement gap remains [#187](https://github.com/alejandroll10/zeropaper/issues/187).

## Codex-math nested sandboxes do not stack

**Scope:** the Claude/OpenCode `codex-math` skill's standalone `codex exec` helper when invoked from inside an existing Codex sandbox. Native Codex pipeline roles no longer start a nested process and are unaffected.

**Failure mode:** macOS refuses a second `sandbox_apply` under Codex's deny-by-default profile. Without a guard, the nested codex-math worker's `apply_patch` fails while ordinary exec commands silently remain under the caller's outer sandbox. The helper detects `$CODEX_SANDBOX`/`$SANDBOX_RUNTIME` and selects `danger-full-access` for the inner process, leaving the outer sandbox as the actual security boundary. Consequently, codex-math's narrower `network=false` command policy is enforceable only when the helper is launched un-nested; nested, egress follows the outer sandbox.

**What would close it:** upstream nested-sandbox support or a setup-time behavior probe that can safely select a working inner policy. Until then the guard is fail-visible and the parent permission profile remains binding.

**Tracking:** [#240](https://github.com/alejandroll10/zeropaper/issues/240).

## Gemini remains unconfined

**Scope:** the Gemini runtime, which still launches with `--yolo` rather than a filesystem boundary comparable to Claude, Codex, Grok, or OpenCode.

**Failure mode:** Gemini can mutate host state outside the project. In empirical deployments it could also modify the host-owned WRDS socket/singleton/latch or bypass the persistent client, so `launch.sh` does not auto-start WRDS for Gemini and the WRDS state-protection guarantee excludes that runtime. A Gemini empirical run may therefore lack WRDS or, when another runtime already started it, undermine the one-login/operator-latch contract.

**What would close it:** enforce Gemini write confinement with `~/.local/state/zeropaper/wrds` outside its writable roots and regress that it cannot create, replace, unlink, or lock those entries.

**Tracking:** [#187](https://github.com/alejandroll10/zeropaper/issues/187).

## Codex behind authenticated proxies: ≤0.144.x is a silent total outage (upstream, mitigated by a warn-only preflight)

**Scope:** every codex invocation — the codex-runtime orchestrator and its native subagents plus the Claude runtime's codex-math co-processor — in any environment whose only network path is an authenticated HTTP proxy (`HTTPS_PROXY` with embedded credentials; typical for hardened sandboxes).

**Failure mode.** codex-cli ≤0.144.x sends no `Proxy-Authorization` header on its HTTPS CONNECT tunnels, even when credentials are embedded in the proxy URL (verified 2026-07-31 with an instrumented relay: every codex CONNECT arrived without the header while curl in the same env sent it). The proxy 407s the bare CONNECT; reqwest surfaces the failed tunnel as `error sending request for url (...)` with **no HTTP status** — so nothing points at the proxy. The OAuth token refresh against `auth.openai.com` fails the same way, so once the access token expires the outage additionally masquerades as an auth/login problem. Fixed upstream in codex 0.146.0.

**Mitigation (in place).** `code/utils/codex_preflight.sh` (`codex_proxy_auth_preflight`, issue #213): at `launch.sh codex` startup and every codex-math `codex_leaf_setup`, if the codex version is < 0.146.0 **and** a proxy env var carries embedded credentials, print a warning naming the defect and the remedies. Native children share the already-started Codex process, so there is no separate per-dispatch binary to probe. Warn-only by design — without an authenticated proxy old versions work fine, and a parse failure must never block a launch; the version lookup runs under a 10s watchdog so a hung binary can't block either.

**Standby remedy (when upgrading codex is not possible).** Run a local forward proxy that accepts CONNECT, injects `Proxy-Authorization: Basic base64(user:pass)` (credentials parsed from the real proxy URL), and tunnels to the real proxy; point `HTTPS_PROXY`/`HTTP_PROXY` at it, leaving the credentials out of the codex-facing URL. This restored codex end-to-end in the 2026-07-31 incident (and, having regained network, codex auto-updated itself past the defect — which is also the caveat: an auto-update is not a durable fix if a rollback or pin lands ≤0.144.x again).

**What would close it:** nothing on our side — it is fixed upstream; the preflight exists because a pinned/rolled-back CLI can silently reintroduce it. Related: #146 (codex hard-stop audit — this is exactly such a hard stop) and #240 (Codex dispatch/CLI compatibility).

## Headless workers can crash Matplotlib on macOS when the GUI backend is inherited

**Scope:** native Codex subagents and any other headless runtime path on macOS that inherits Matplotlib's `macosx` backend instead of explicitly selecting a non-GUI backend.

**Failure mode:** an agent-written Python script imports `matplotlib.pyplot` and creates a figure for `savefig()`. AppKit initialization in the headless process aborts Python with `SIGABRT`; calculations/figures fail and macOS displays repeated “Python quit unexpectedly” dialogs. Individual helpers such as `ssj_solve.py` select `Agg`, but the general runtime environment does not.

**What would close it:** establish and test a non-interactive backend (normally `MPLBACKEND=Agg`) across every headless orchestrator/subagent path, define explicit script/user override precedence, and give concurrent children a writable cache-safe `MPLCONFIGDIR` where needed. The regression test must create and save a figure in a genuinely headless process without initializing AppKit.

**Tracking:** [#250](https://github.com/alejandroll10/zeropaper/issues/250).

## Requested paper edits are not uniformly application-verified

**Closed in v2.26.0 (#264):** every paper-producing mode now separates analysis from presentation through schema-v1 result bundles and presentation-only renderers, verifies their byte provenance with receipts, mechanically derives the paper's transitive LaTeX dependency/exhibit/citation-occurrence inventories, audits every included result-bearing exhibit and its prose/caption interpretation, and separately verifies every citation characterization against an exact source pointer. Both complete independent PASS inventories, result receipts, and exact paper bytes are bound in one durable receipt after every paper mutation. Formal theory notation is deliberately outside result bundles.

**Remaining scope:** source grounding does not establish that every requested edit was actually applied. A writer can omit or incompletely apply a referee/polish instruction while leaving all surviving claims well grounded.

**What would close it:** a separate application-only delta verifier that checks requested edits against the resulting paper without re-adjudicating their scientific or provenance merits.

**Tracking:** [#77](https://github.com/alejandroll10/zeropaper/issues/77).

## Results and paper-evidence boundaries that remain open

**Scope:** the v2.26.0 computed-results producer/renderer runner introduced for #264. Its receipt establishes the declared filesystem chain from code/input bytes to JSON bundle, artifact, rendered exhibit, and paper; it is not a proof that an adversarial program used no other operating-system capability.

1. **Provider/network authority.** Producers receive EOF on stdin and a sanitized allowlist instead of the ambient environment. Raw WRDS credentials remain absent and WRDS access stays behind its query-only bridge. A run plan explicitly selects zero or more provider-key variables; no other provider key reaches that producer. LLM-backed producers may still receive those selected credentials and outbound network because those computations cannot run without them. The runner rejects literal selected-provider credentials and percent-decoded authenticated-proxy passwords of at least eight bytes from staged files. Renderers receive neither provider credentials nor network environment and run without network capability on Linux and macOS. A networked producer can still encode or transmit a selected credential or consume an undeclared response, so a receipt proves captured declared bytes, not absence of producer network exfiltration or recomputation. **What would close it:** an ephemeral trusted inference/network broker that owns credentials, scopes destinations and methods, records request/response bytes and model parameters as declared artifacts, and revokes the capability on attempt exit. **Tracking:** [#267](https://github.com/alejandroll10/zeropaper/issues/267).

2. **macOS containment edges.** The lock-free supervisor kills and waits for the launched process group when its parent dies; Linux additionally uses bubblewrap parent-death and PID-namespace containment. A hostile macOS child can call `setsid`, double-fork, and escape that process group. It remains under the default-deny filesystem sandbox but may outlive the attempt long enough to use network/provider authority or race isolated-workspace writes. The profile grants no blanket Mach-service lookup, so it cannot contact `com.apple.SecurityServer` or read the user's Keychain. Seatbelt also cannot carve an arbitrary project back out of a broadly allowed system-runtime subtree, so a macOS project nested under `/System`, `/Library`, `/usr`, `/bin`, `/sbin`, `/dev`, `/etc`, `/private/etc`, or `/opt` fails closed; normal user-home deployments are unaffected. Supported producers do not daemonize. **What would close it:** a macOS job/coalition primitive covering every descendant regardless of session changes plus a mount-namespace/container view for unusual system-root deployments, with a double-forked regression and broker-capability revocation. **Tracking:** [#268](https://github.com/alejandroll10/zeropaper/issues/268).

3. **Large declared directories and macOS inputs without copy-on-write cloning.** Linux producer/renderer workspaces descriptor-pin and read-only bind each declared regular file through Bubblewrap, so even a cross-filesystem multi-gigabyte file consumes no per-attempt copy. Declared directories still copy as one immutable membership snapshot, and macOS has no equivalent mount namespace in the supported Seatbelt runner. Only current-attempt declared sources are copied, never receipt history, and the copier requests cloning before a physical fallback. A large directory on any platform, or a non-cloneable/cross-filesystem macOS file, can therefore still consume equivalent temporary disk and I/O. **What would close it:** native same-volume `clonefile` support on macOS plus a scalable immutable directory snapshot representation; retaining physical copy only when neither can preserve the exact declared-source view. **Tracking:** [#269](https://github.com/alejandroll10/zeropaper/issues/269).

4. **Arbitrary TeX expansion and file readers.** The paper dependency inventory recursively follows supported static `input`/package/class, bibliography, graphic, listing, CSV, pgfplots, PDF, and conditional-input syntax, and rejects known dynamic readers, custom graphics-extension ordering, and common user-defined citation aliases. TeX is programmable, however: a local package/class can define or invoke another macro or primitive that reads a project file or expands into a citation without matching the static inventory. That byte or citation can affect the rendered paper without entering the paper-evidence receipt. Paper authors must therefore use the supported citation commands directly rather than hide them behind macros. **What would close it:** run the canonical TeX build before every evidence checkpoint inside a restricted build sandbox, parse its recorder `.fls` plus citation side effects, reject inputs outside the allowed runtime/project roots, fingerprint every project-relative `INPUT`, and bind the exact build command/configuration and recorder output to the audit input. Static discovery can then remain an early diagnostic rather than the completeness boundary. **Tracking:** [#270](https://github.com/alejandroll10/zeropaper/issues/270).

5. **Exact execution-environment closure beyond the historical capture.** Ordinary result-receipt v2 and empirical result-receipt v3 automatically bind what the trusted runner can capture without executing environment-controlled inspection code: the resolved launcher file and bytes, platform/kernel/machine/libc and OS-release identity, relevant locale/numerical flags, recognized dependency manifests, and the project venv's `pyvenv.cfg`, installed distribution name/version metadata, wheel `RECORD`, direct-source, installer, entry-point, and path-configuration metadata. Producers and renderers receive that environment read-only, and publication fails if the same capture differs after execution. Agents may still install packages normally before a run; later installations intentionally do not invalidate the historical receipt. The capture does not hash every installed package source byte, observe the exact imported-module/native-library set, inventory non-Python package stores without a project manifest, or trace external executables launched by R/Julia/shell code. A package file changed without corresponding metadata, or a mutable native/system tool outside the resolved launcher, can therefore differ while the historical `captured` manifest remains the same. Producers default to `reproducibility: captured`; `exact` and `bounded` remain audited assertions requiring a separately declared content-addressed closure or nondeterminism bound. **What would close it:** loaded-file/exec tracing or an immutable content-addressed runtime that covers imported package bytes, native libraries, and subprocess toolchains across every supported launcher. That stronger replay guarantee is deliberately distinct from the low-overhead historical capture. **Tracking:** [#271](https://github.com/alejandroll10/zeropaper/issues/271).

6. **Empirical execution summaries are semantically audited, not mechanically derived traces (accepted boundary).** Receipt v3 fingerprints the exact producer code, entrypoint, inputs, environment, command, artifacts, bundle, and execution summary. The runner checks that the summary completely and consistently realizes the contract's samples, count flows, settings, decisions, tuning, seeds, and ownership. The empirics auditor reads the code and reconciles those records, and the independent replicator checks headline results. The trusted runner still cannot interpret arbitrary programs to prove that a reported intermediate count or setting equals the producer's transient in-memory state; a semantic audit can miss a mismatch, while exact reproduction faithfully repeats it. **What would close it:** constrain empirical work to trusted instrumented operations or require an independently derived operation trace. That would limit generality and is not planned; code provenance plus semantic audit is the intended assurance level. **Tracking:** [#296](https://github.com/alejandroll10/zeropaper/issues/296) (closed as accepted).

7. **Exhibit element maps are declarations, not a mechanical census of arbitrary rendered content (accepted boundary).** Receipt v3 proves that every declared exhibit result belongs to one analysis, is assigned once to a stable element ID, and appears in the element/result union. The isolated renderer sees only its declared presentation-safe inputs. The runner does not parse arbitrary TeX, plot state, or image pixels to prove that every visible cell, series, annotation, and note came from that map; a renderer could hard-code an additional value that only the evidence auditor's visual reconciliation catches. **What would close it:** constrain rendering to a trusted machine-readable exhibit specification whose complete cell/series inventory can consume only validated result objects. That would put arbitrary custom renderers outside the supported interface and is out of scope; visual reconciliation is the intended backstop. **Tracking:** [#297](https://github.com/alejandroll10/zeropaper/issues/297) (closed as accepted/out of scope).

8. **Agent-selected computation classification remains semantic in manual mode (accepted boundary).** Manual mode removes the autonomous stage machine; it does not mean the human performs the analysis. Agents still write and execute the empirical code, and their empirical procedures require `run-empirical`. Any plan with an `analyses` map is mechanically forced onto receipt v3. An agent could nevertheless omit that map, choose an unrelated output path, and misclassify empirical work as ordinary receipt v2. Paper audit exposes the receipt as unclassified and directs the evidence auditor to reject hidden empirical reports, but recognizing scientific content remains judgment. A mandatory `computation_kind` field selected by the same agent would restate that judgment without making it more trustworthy; a genuinely mechanical guarantee would require an external trusted classifier for arbitrary code and outputs. That is not planned, so semantic audit is the intended boundary. **Tracking:** [#298](https://github.com/alejandroll10/zeropaper/issues/298) (closed as accepted).

## OpenCode runtime: external OS sandbox, one model tier, and experimental background durability

**Scope:** the OpenCode runtime assembled under `.opencode/agents/`, configured by `opencode.json`, and launched through `./launch.sh opencode`.

1. **Launcher confinement is external to OpenCode (closed for supported launch paths in v2.22.0).** OpenCode has no native kernel sandbox, so `./launch.sh opencode` wraps the persistent authenticated server and every attached client, while `--once` wraps the whole TUI, in Anthropic Sandbox Runtime. The resulting Seatbelt/bubblewrap policy covers their descendant trees, permits project/project-scoped OpenCode-state/cache writes and arbitrary network access, and denies reads/writes under `~/.ssh` and `~/.aws`; real canaries verify project and cache writes, external write/delete denial, protected-state immutability, credential denial, network access, and a nested child. The unsandboxed driver is a narrow control plane: its Python runs isolated, its PATH excludes every sandbox-writable root, and its helper/log/identity/credential files live under sandbox-immutable directories. Pre-v2.22 state is migrated; if its old unconfined server/group is still alive, the new launcher fails closed and requires it to be stopped before starting a confined replacement. The adapter deliberately uses SRT's library API because its CLI schema requires a finite domain allowlist, which is incompatible with an open-ended research pipeline. **Residuals:** bare `opencode` bypasses the wrapper; SRT is a beta dependency whose API may change; root execution is unsupported; Ubuntu 24.04+ needs an AppArmor user-namespace profile (or Anthropic's broader sysctl workaround). OpenCode can also write shared caches and the non-control portions of `~/.codex` required by codex-math, so it can delete Codex session/log state, although auth, config, plugins, skills, rules, and packages are write-denied. Use the launcher and rerun `deploy_assets/scripts/test_opencode_sandbox.sh` after SRT upgrades.

2. **All capability tiers collapse to one model.** Every generated subagent and the orchestrator use `opencode/deepseek-v4-flash`; `--light` is a no-op. Generator/judge model decorrelation and automatic model fallback are unavailable. **What would close it:** multiple suitable OpenCode Zen tiers plus an availability probe/remap.

3. **Background subagents depend on an experimental, process-local upstream registry.** `./launch.sh opencode` enables OpenCode's native `task(background=true)` and keeps one authenticated localhost `opencode serve` alive across attached CLI turns. Verified on OpenCode 1.18.11: a child survives attached-client exit, completion is durably injected into the parent as a synthetic message, and that message autowakes the parent without another client. The project-exclusive driver tracks launch generations (a resumed `task_id` can reuse its child session ID), causally pairs each with its persisted synthetic completion/error user notification and a later completed/error parent response, discovers generations spawned by that response, and then waits for the parent plus its child sessions to become stably idle before sending an external continuation; a reused parent is quiesced even when its generation ledger is empty. Cancellation aborts the tree, confirms status-only quiescence, and replaces the server instance before advancing its history baseline, preventing a delayed notification/autowake from crossing that boundary. However, OpenCode's background-job registry is instance-scoped memory: a **server-process** crash interrupts active children even though their session transcripts and artifact checkpoints persist. The driver restarts the server, uses an always-present parent/server epoch and a server-instance-bound history baseline to detect and retire lost generations, and persists uniquely tokenized recovery intent until its native user prompt is observable; it then explicitly orders the parent to reconcile/resume unfinished child IDs. It cannot make an uncheckpointed upstream model/tool call atomic across a server crash. **Mitigation:** every task prompt names an artifact path, gates verify that artifact rather than trusting notification alone, authenticated server/client and parent-bound pending-generation state are cached for driver restart, and older OpenCode versions whose task schema lacks `background` fall back naturally to foreground calls. **What would close it:** upstream persistence and restart recovery for the background-job registry, followed by removing the experimental flag and recovery caveat.

4. **Skill-source selection depends on the launcher.** Deployments contain `.claude/skills` and `.agents/skills`. `./launch.sh opencode` disables automatic external scans while `opencode.json` explicitly registers `.claude/skills`, avoiding duplicate IDs. Starting bare `opencode` bypasses that selection; use `./launch.sh opencode --once` for the TUI.

**Tracking:** [#220](https://github.com/alejandroll10/zeropaper/issues/220) (initial OS confinement — closed), [#251](https://github.com/alejandroll10/zeropaper/issues/251) (bare-launch confinement bypass, SRT compatibility, and shared Codex-state writes), [#221](https://github.com/alejandroll10/zeropaper/issues/221) (model tiers + fallback), [#222](https://github.com/alejandroll10/zeropaper/issues/222) (background lifecycle and process-local registry crash recovery — reopened), [#244](https://github.com/alejandroll10/zeropaper/issues/244) (deterministic skill-source selection under bare launches).

## Grok runtime: single model tier, no model probe, and partial mode/extension coverage

**Scope:** the Grok Build runtime — `deploy_assets/scripts/assemble_grok_agents.py`, the `.grok/agents/*.md` it emits, the labeled-dispatch fork in `deploy_assets/templates/runtime/codex/session.md`, and the grok wiring in `setup.sh`.

**Design note (not a limitation).** Grok reads project instructions from the root `AGENTS.md` — the *same* file codex reads, and its filename cannot be changed or redirected (verified: grok ignores `GROK.md`/`.grok/AGENTS.md` when a root `AGENTS.md` is present). So codex and grok deliberately **share** one `AGENTS.md`, whose dispatch section is runtime-labeled ("If you are Codex … / If you are Grok …"); each CLI follows its own branch. Verified end-to-end: grok reads the shared doc, self-selects the grok branch (native `task` tool + `subagent_type`, agents in `.grok/agents/`), and spawns an assembled pipeline agent successfully.

**Fixed footgun — shared leader socket cancels concurrent grok projects (closed by per-project `--leader-socket`).** Every grok client connects to one host-global leader process at `~/.grok/leader.sock` by default. A second client connecting to that socket **tears down the first session's in-flight turn** (reproduced on grok 0.2.93: a `grok -p` probe, and a same-socket interactive client, each wiped a running session's turn mid-execution; cross-cwd — so two *different* projects collide, not just two windows on one project). This directly breaks the pipeline's recommended "one interactive tmux window per project" layout for long unattended runs, which is safe for Claude/gemini (independent top-level processes) and codex (one isolated top-level `codex exec` session per project; native children share it) but not for grok's single-leader model. Note this is *not* triggered by the pipeline's own subagents — grok spawns those via the in-process native `task` tool, not new `grok` CLI processes — only by a second top-level `grok` invocation on the host. **Fix (in place):** the documented launch line pins a per-project socket, `grok --sandbox pipeline --always-approve --leader-socket "$(pwd)/.grok/leader.sock"`, and `./launch.sh grok` passes it automatically (a launch.sh regression that dropped the flag was caught and fixed in #190); distinct sockets give each project an independent leader (verified: with distinct sockets a second session left the first's turn running untouched; `.grok/leader.sock` is gitignored, created lazily by the leader, and orthogonal to session persistence, which is keyed by cwd so `--continue`/resume are unaffected). **Known edge (accepted):** a unix socket path is capped at ~104 bytes (`sun_path`), so a very deeply-nested project directory could overflow `"$(pwd)/.grok/leader.sock"`; deploy paths are user-chosen and normally short. **What would fully close the edge:** a shorter, collision-free socket path (e.g. a hash of the project root under a short runtime dir) if long paths ever appear in practice.

**Fixed footgun — grok's bash tool demotes the activated venv below `/usr/bin` (closed by `~/.local/bin` shims, #190).** grok rebuilds its bash tool's PATH prepending its own dirs (`~/.grok/bin`, `~/.local/bin`) plus the macOS default PATH ahead of every inherited entry, so the venv activated by `launch.sh` lands below `/usr/bin` and bare `python3` resolves to the system interpreter — no `sympy`/`matplotlib`/`wrds`, so python steps fail (captured on grok 0.2.93; the demotion mechanism independently reproduced via a login-shell `path_helper` rebuild). grok has no config knob to reorder its bash PATH (checked the full user guide). **Fix (in place):** `install_grok_venv_shims` in `launch.sh` writes `VIRTUAL_ENV`-keyed shims (`python3`/`python`/`pip3`/`pip`) into `~/.local/bin`, which grok's rebuild keeps ahead of `/usr/bin`. Shims are transparent outside grok (no active venv → exec the next real binary on PATH, skipping their own dir), marker-tagged, idempotently rewritten each launch, and never installed over a pre-existing non-shim file (warn-and-skip). **Trade-offs (accepted):** the shim is host-global — every shell on the host that resolves `~/.local/bin` early now routes bare `python3` through it (behaviorally identical by construction, but a new moving part); and the fix only auto-installs via `./launch.sh grok`, so a manual `grok --sandbox pipeline ...` launch on a host where the launcher never ran still hits the demotion. **Residual unknown:** grok's exact PATH-head ordering (`~/.local/bin` at position 2) comes from one captured session; re-verify with a live `echo $PATH` through grok's bash tool if a grok update changes shell setup.

**Fixed footgun — `git push` fails under grok's sandbox: macOS keychain unreachable (mitigated by an opt-in repo-scoped token store, #190).** The `osxkeychain` credential helper needs `mach-lookup com.apple.SecurityServer` (the legacy securityd endpoint of the classic `SecKeychain*` APIs); grok's Seatbelt profile denies it, and grok's `sandbox.toml` schema is filesystem+network only (`extends`/`restrict_network`/`read_only`/`read_write`/`deny` — no mach-service field), so the grant cannot be expressed. Discriminator verified with `sandbox-exec`: denying *only* `com.apple.SecurityServer` reproduces the failure (`errSecParam -50`); denying only `com.apple.securityd` leaves the keychain working. Consequence: with an HTTPS remote, every pipeline push (`core.md` commit discipline) fails on auth; commits stay local, runs are not blocked. **Mitigation (in place, opt-in):** `code/utils/setup_push_token.sh` writes a fine-grained PAT scoped to the project's backup repo into `.git/push-credentials` (0600, untracked) and switches the repo to a local `credential.helper store` (leading empty helper clears the inherited osxkeychain). `launch.sh grok` warns at launch when an HTTPS remote lacks the store. Chosen over a hand-maintained `sandbox-exec` keychain wrapper (re-exposes the whole keychain, macOS-only, duplicates grok's sandbox upkeep) and over external pushes (doesn't fit autonomous scale). **Trade-offs (accepted):** a token lives on disk (scoped to one repo — narrowest blast radius); the store path is absolute, so a moved project needs the script re-run; without opting in, grok runs are local-only.

**Limitations (four open, plus one closed record):**

1. **Single model tier collapses generator↔judge decorrelation.** xAI exposes one general-purpose model in v1 (`grok-4.5`), so every Claude tier maps to it. Claude, Codex, and Gemini use different generator/evaluator tiers where available; Grok and OpenCode cannot. Per-agent reasoning effort still varies on Grok, but that is weaker than a tier split. **What would close it:** an xAI capability-tier lineup.

2. **Grok subagent models are not probed/remapped.** Like the codex/gemini runtimes (see the model-availability section in `CLAUDE.md`), only *Claude* models are probed at setup and remapped on unavailability. If `grok-4.5` is withdrawn or the account loses access, grok agents hard-fail at launch with no fallback. The `model_fallbacks.json` schema and resolver/apply split are provider-agnostic; what's missing is a `grok models`-based probe and applying the remap over `.grok/agents/*.md`.

3. **Manual/report dispatch guidance — closed in v2.25.1.** The shared manual and report sessions distinguish Codex native custom roles (same-turn bounded waves) from Grok/OpenCode native tasks.

4. **Skills and extension agents are not wired for grok.** `assemble_grok_agents.py` does not emit a `skills:` frontmatter list, and grok project-skill discovery is unverified (grok reads Claude-format skills at the user level; project-level discovery of `.claude/skills`/`.agents/skills` was not confirmed). The extension appliers (`apply_extension_empirical.sh`, `apply_extension_theory_llm.sh`) take the claude/codex/gemini agent dirs as positionals but not `.grok/agents`, so `--ext empirical` / `--ext theory_llm` deploy no grok extension agents while the extension's stage instructions are still baked into the shared `AGENTS.md` (a Grok orchestrator would be told to launch agents absent from `.grok/agents/`). Base theory-only agents are unaffected. **What would close it:** thread `$GROK_AGENTS_OUT` through both extension appliers (agents), and add a `skills:` emitter + confirm grok's project-skill path (skills).

5. **Grok cross-turn autonomy is unverified — `./launch.sh grok` may be only pseudo-autonomous.** A completed top-level Codex turn is inert until another prompt, which is why its launch path has a headless re-prompt driver (native Codex children instead complete and wake the active parent inside their spawning turn); grok gets a plain interactive `exec grok` on the *assumption* it behaves like Claude between stages. Whether a grok orchestrator turn-end between stages stalls until a human types has not been tested (the attempt during #190 verification hit an exhausted Grok usage balance — `402 Payment Required`). **Failure mode if the assumption is wrong:** unattended `./launch.sh grok --tmux` fleet runs silently park at the first inter-stage turn-end. **What would close it:** with balance restored, run a two-stage toy task through `./launch.sh grok` and observe whether the session self-continues past a turn-end; if it stalls, grok needs a driver loop analogous to codex's (`grok -p` single-turn + session resume exists, so the same driver shape fits).

**Tracking:** [#182](https://github.com/alejandroll10/zeropaper/issues/182) (extension agents), [#183](https://github.com/alejandroll10/zeropaper/issues/183) (manual/report dispatch fork — item 3, closed), [#184](https://github.com/alejandroll10/zeropaper/issues/184) (skills — item 4), [#185](https://github.com/alejandroll10/zeropaper/issues/185) (model probe + single-tier — items 1 & 2), [#190](https://github.com/alejandroll10/zeropaper/issues/190) (leader-socket regression, venv PATH shims, keychain push, autonomy verification — item 5).

## Closed: table-legibility source escapes now have a rendered semantic backstop

**Scope:** the Stage-5 and final-post-polish table-legibility gates — `arpipeline.sty` Layer 5, `table-auditor`, Stage-5 build/audit routing, and the paper-writer wide-table contract ([#85](https://github.com/alejandroll10/zeropaper/issues/85), [#253](https://github.com/alejandroll10/zeropaper/issues/253)).

The original Layer 5 measured only unstarred `\resizebox{...}{...}{<tabular>}` width against a fixed 0.6 ratio. Direct `\tiny`, `\resizebox*`, `\scalebox`, `adjustbox`, bare `array`/custom alignments, and image tables could therefore compile inside the margins with unreadable text. The old marker was also not literally a build failure: it was a `\typeout` that depended on the orchestrator running a later grep.

**Closed behavior:** Layer 5 now captures the document class's actual `\scriptsize` boundary and rejects a native `tabular`/`tabular*`/`longtable` below it. For `\resizebox` (plain and starred) and `\scalebox`, it typesets the natural content once, records the smallest source font observed, measures both realized dimensions, and rejects when the effective rendered size falls below that boundary. Command-form `adjustbox` gets the same source check for an unambiguous two-axis reduction, while allowing axis-exchanging transforms such as pure rotation; its one-axis and compound cases are decided by the rendered auditor because an axis-aligned before/after box cannot identify their glyph scale without false positives. This retains scale measurement — font-at-table-entry alone cannot see a transform applied afterward — and correctly permits a small source table scaled up to a readable result. Because the `adjustbox` environment hides its collected body from a compatible one-pass wrapper, any native table inside that environment fails closed; use native reflow/landscape or the measurable command form instead. `array` participates only inside a semantic table float, so resized equation arrays are not hard-classified as tables; rendered inspection remains the semantic backstop for table-like custom alignments elsewhere. A semantic table float whose only exhibit is `\includegraphics` fails as an inaccessible pre-rendered table; a native table may still contain images such as icons or sparklines. Every source violation includes `ARPIPELINE-TABLE-LEGIBILITY-FAIL` in both the diagnostic and the raised `\PackageError`, so trial typesetting that suppresses `\typeout` (for example `tabularx`) cannot hide the marker and `latexmk` exits nonzero rather than relying only on prompt compliance.

Source tokens cannot reliably decide that a graphic placed in a `figure` is semantically a table, recognize every custom alignment macro, or judge clipping/overprinting. The independent `table-auditor` therefore rasterizes and inspects every page of the main PDF and populated Internet Appendix after Stage 5 and again after final polish. It reads source for navigation but treats rendered pages as authoritative, so vector and raster image tables are both in scope; it explicitly excludes the invisible tiny provenance fingerprint. PASS is a completion precondition, REVISE routes through a capped paper-writer repair/rebuild/re-audit loop, and missing render tooling is GATE-BROKEN rather than a false PASS.

Nested box-scaling around table content also fails closed, even when its individual factors might compose above the floor: re-entrant transform measurement shares TeX scratch-box state, so accepting arbitrary nesting would reopen state-clobber bypasses. Nested transforms containing only figures remain legal. CI-enforced LaTeX regressions use the deployed skeleton's package order and cover the allowed `\scriptsize` boundary, normal/upscaled native tables, non-scaling and pure-rotation command `adjustbox`, scaled/nested non-table figures (including an `adjustbox` environment), direct and resized equation arrays, and native tables containing an image; and reject direct `\tiny`, plain/starred `\resizebox`, horizontal/vertical/nested `\scalebox`, a table followed by a nested figure transform, shrinking command `adjustbox`, table-bearing `adjustbox` environments, transformed `array` inside a semantic table float, undersized `longtable`/`tabularx`, and image-only semantic table floats. Assembly tests verify `table-auditor` across autonomous runtimes and its report-mode pruning.

## Core-bypass guard: early gate-time detection and orchestrator-only bypass recording remain optimizations

**Scope:** the core-bypass degradation guard (issue #51) — `docs/core_bypass.md`, `inject_core_bypass_into_agents` (setup.sh), the `{{CORE_BYPASS_GUARD}}` placeholder, `process_log/degradation_ledger.md`.

**Closed (terminal backstop, default mode).** A non-binding verification can no longer pass as a clean run. The session entry point (`deploy_assets/templates/runtime/claude/session.md`, shared by all three autonomous runtimes) refuses to set `status = "complete"` while `degradation_ledger.md` has an unresolved binding row (`binding? = yes`, `action` not `resolved`). Because every bypass — wherever it occurs in the run — leaves a durable ledger row, this terminal check makes "ran to success while a core was silently downgraded" impossible regardless of stage, *without* any `core.md` edit (re #27). This was the irreducible #51 complaint ("the run reports success while a core invariant was silently relaxed"); the backstop closes it mechanically in the default deploy, not just visibly.

**Amended in v2.12.0 (issue #179): the block is no longer always a halt.** An unresolved binding row from a **deferrable** outage — one whose source is down for a stated bounded horizon (a rate limit or credit budget with a reset time) *and* whose re-check is a cheap lookup — now completes as `status = "complete_pending_verification"` with the owed check recorded in `pipeline_state.json`'s `pending_verification`, and a later session re-runs it and self-completes. Everything else, plus any ambiguous classification, plus every case under `--halt-on-core-bypass`, still takes the `halted_core_bypass` path. Resolution is likewise no longer operator-only: a session may mark a row `resolved` for a binding verification **it re-ran itself and that came back clean** (evidence, not faith); all other resolution stays operator-driven. The invariant is unchanged — `complete_pending_verification` is not clean success — but a transient budget outage no longer parks a finished paper pending a human signature. See `docs/core_bypass.md`.

**Failure mode (two residual gaps — both latency/coverage optimizations, not soundness holes):**

1. **No gate blocks *earlier* than completion.** The gates themselves — `scorer`, `editor`, `referee`, the polish auditors — still do not read `degradation_ledger.md`. A degradation that occurs before a gate (e.g. a `codex-math` outage misclassified at Gate 2) is caught at completion, not at the gate, so the run can burn the intervening stages before halting. This is a wasted-work cost, not a correctness gap: the terminal backstop still prevents a degraded run from reporting success. (The surfacing example — a Stage 8 bib-verify downgrade — occurs *after* every gate, so for it the terminal check is the only possible mechanical block anyway.)

2. **Default mode does not record orchestrator-only bypasses (conditions 2-3).** Gate-skipped and designated-agent-substituted are events only the orchestrator can detect (an agent can't see that it was skipped). The default (no-flag) deploy intentionally leaves the orchestrator doc (`core.md`) untouched to avoid runtime-doc growth (issue #27), so in default mode only agent-detectable bypasses (conditions 1 and 4 — source-fallback, tool-misclassification) are recorded; conditions 2-3 are recorded/halted only under `--halt-on-core-bypass`. Note that *if* a 2-3 event is recorded (under the flag, or by a future default-mode recording step), the terminal backstop blocks completion on it for free — the recording is the only missing half.

**What would close them:** (1) add a hard-requirement check to `scorer` (and the Stage 6 `editor`) that reads `degradation_ledger.md` and treats any unresolved `binding? = yes` row whose core is a gate the paper relies on as a blocking condition (REVISE/hold) — moving detection earlier than completion. (2) Inject a minimal orchestrator-side recording instruction even in default mode — a recording step in the relevant pointed-to stage docs (`docs/stage_*.md`, off the runtime-doc budget) at each gate's skip/substitution decision point. Agent-substitution (condition 3) has no cheap mechanical detector beyond orchestrator self-report and remains the irreducible flag-only residual.

**Tracking:** [#51](https://github.com/alejandroll10/zeropaper/issues/51) is the closed originating issue; [#61](https://github.com/alejandroll10/zeropaper/issues/61) tracks the two remaining optimizations (reopened because this entry still describes unresolved work).

**Interim behavior:** the terminal completion-block in `deploy_assets/templates/runtime/claude/session.md` guarantees no degraded run reports clean success in any autonomous pipeline mode (i.e. not `--mode report` or `--manual`, which have no `status` machine and so get the record-and-surface half only); earlier gate-time detection (gap 1) and default-mode recording of conditions 2-3 (gap 2) are deferred as latency/coverage improvements, and conditions 2-3 are fully halted under `--halt-on-core-bypass`.

## Stage 0 discovery-exhausted: the re-scan branch terminates on judgment, not on an enumeration — CLOSED in v2.24.4

**Scope:** every variant. Introduced in v2.18.0 with the `stage-0-discovery-exhausted` branch-manager context (issue #156); substantially narrowed in v2.18.1 (issue #218).

Before v2.24.4, when problem discovery exhausted every gap without ever scoring a question (`gate0_best_question_score == -1`), `docs/stage_0.md` Step 0b launched `branch-manager`, which recommended RESCAN-NEW-DOMAIN, RESCAN-CORRECTED, or OPERATOR-ESCALATE. The intended per-domain budget was one fresh scan plus at most one corrected re-scan; if the domain space were finite, that would imply a bound of twice its size. The domain space was deliberately open, however, so actual termination rested on branch-manager judgment. **As shipped in v2.18.0**, spent domains were recorded only in the reports themselves (`output/stage0/branch_manager_discovery_p*.md`) — see the fix below.

**Fixed in v2.18.1 (#218):** the two concrete defects are gone. Step 0a now appends every domain it scans to `output/stage0/domain_log.md` (`{domain} — fresh scan` / `{domain} — corrected re-scan: {correction}`), a run-scoped log that — unlike `gap_log.md` — the Stage 0 entry hook never clears. Dedup is now an exact read of one log written by the agent that chose the domain, rather than a fresh `branch-manager` re-deriving the spent set from N prior reports' free text; branch-manager reads the log instead of every `branch_manager_discovery_p*.md`, and the report's "Domains already spent" section and the "your report is the durable record" rule are both deleted, since the log is the record. `--variant macro` gained a real sub-domain decomposition (monetary, fiscal, growth, labor search, international, heterogeneous-agent, expectations, macro-finance, business-cycle measurement), so RESCAN-NEW-DOMAIN has something to name there.

**What remains, by design:** `DOMAIN_AREAS` was deliberately **not** converted into a closed enumerated list (`DOMAIN_LIST`), which is what #218 originally proposed. A closed taxonomy would let the pipeline mistake "covered the enumeration" for "covered the field" and would freeze each variant's domain space at whatever `setup.sh` happened to name — the failure mode the repo's "prefer no structured classes" principle exists to prevent. The scope is therefore documented as naming starting points, and `branch-manager` may name an in-scope domain the scope does not list.

**Former failure mode:** an open domain space has no finite enumeration, so the nominal 2 × |domains| bound was not a numeric guarantee. Termination rested on branch-manager judging that no materially different in-scope domain remained. A pathological run could keep renaming or subdividing thin domains; `problem_attempt` and the visible log made that behavior observable but did not cap it.

**Closed in v2.24.4 (#252):** `loops.stage0_discovery` grants at most 100 physical broad-scout launch permits across the entire unseeded pipeline run; seeded and faithful runs bypass discovery. Stage 0 re-entry, successful handoff to Stage 1, and Regeneration Rounds all preserve this run-global budget. Every initial launch and crash retry commits a distinct permit first; a broad map counts only after atomic publication from its permit-specific staging path, and an incomplete launch at the cap routes to autonomous salvage instead of re-launching, so physical launch 101 is impossible even across repeated crash windows. Durable phase/substep state and stable gap IDs resume and reconcile selection, characterization, posing, review, logs, or routing without inferring progress from stale/partial canonical artifacts or duplicating near misses. `stage0_discovery_episode_start_attempt` separately scopes the compact near-miss portfolio and versioned source-map snapshots to the current search for a scored question; every downstream return increments `problem_attempt`, so a later Stage 0 episode cannot reuse stale candidates or archive names. Before the cap, branch-manager may still use substantive judgment to choose a new domain, one corrected scan, or early promotion; at the cap both re-scan verdicts are forbidden. `PROMOTE-NEAR-MISS` uses a durable three-way cap context: downstream returns reframe the failed question and incomplete permit-100 scans retain their instruction and current-episode evidence. Each route runs one final targeted gap characterization and sends the result through the ordinary independent question-poser/question-referee gate without another broad scan. This makes the numeric ceiling a runaway guard rather than a closed taxonomy: the pipeline neither claims the field has no questions nor halts for ordinary research judgment. v2.28.1 removed the former legacy-state salvage path together with general backward update compatibility; current updates require the complete v2.28 state contract.

**Tracking:** [#156](https://github.com/alejandroll10/zeropaper/issues/156) (original undefined terminus — closed), [#218](https://github.com/alejandroll10/zeropaper/issues/218) (domain-log/open-domain redesign — closed), [#252](https://github.com/alejandroll10/zeropaper/issues/252) (global termination gap — closed in v2.24.4).

## data-first: exact coverage predicates are negotiated one full pipeline cycle per unsatisfiable event

**Scope:** `--mode data-first` (both field runs observed, 2026-08-29).

A dataset spec may commit to an exact coverage predicate over an enumerable event set ("an explicit direct receipt for every non-waivable event"). Whether a specific event can satisfy the predicate is only discoverable by exhaustive Stage 3a acquisition, so each newly-discovered unprovable event triggers an honest scope repair that costs a full Stage 2 → Gate 2 spec audit → Gate 3 novelty re-check → Stage 3 portfolio re-derivation → fresh Stage 3a attempt cycle — O(k) full cycles for k gap events. Observed: four coverage-driven spec returns on one Nasdaq receipt scope in the tradingdays run (residue shrinking 15 → 4 → 2 events across rounds); the eventcal run's spec v6→v9 march after its a29 coverage-audit FAIL has the same shape.

**Failure mode it produces:** not incorrect output — the honesty machinery works — but a convergence cost that multiplies wall-clock and re-runs gates invariant to the scope tweak (novelty re-checks returning the same INCREMENTAL verdict, portfolio re-derivations for an untouched portfolio). On archives with a long tail of unprovable events, the loop count is bounded only by the tail.

**What would close it:** an acquisition census before predicate freeze (Gate 2 acceptance requires per-event acquirability evidence for enumerable committed sets); or ledger-form coverage commitments (measured coverage + versioned exception ledger the coverage-auditor audits for honesty, instead of exact-count predicates); or a machine-checkable portfolio-invariant amendment lane that re-enters at the spec audit without re-running novelty/portfolio stages. See the issue for trade-offs.

**Tracking:** [#295](https://github.com/alejandroll10/zeropaper/issues/295).
