## How to start a session

1. Read `process_log/pipeline_state.json`
   - If `status` is `"not_started"` and `"seeded"` is `true`: run **session preflight** (below), set to `"running"`, then follow the **Seeded idea mode** entry sequence (see above)
   - If `status` is `"not_started"`: run **session preflight** (below), set to `"running"`, begin Stage 0
   - If `status` is `"running"`: run **session preflight** (below), then read `current_stage` and continue from there. **The "Before you set `status` to `"complete"`" rule below is a standing precondition** — re-check it at the moment you are ready to mark the run complete, however many stages later that is; it is not a one-time session-start check.
   - If `status` is `"complete"`: report that the pipeline is done
   - If `status` is `"complete_pending_verification"`: the run finished with a binding verification still owed because its source was rate/budget-limited. Re-probe each entry in `pending_verification` and, for any whose source is back, re-run that binding verification now. Clean → mark the ledger row `resolved`, drop the entry in the same commit, and set `status = "complete"` once the array is empty. Dirty → set `current_stage` back to the stage that owns the check and `status` to `"running"`, then work it through that stage's normal loop; do not complete. Still down → leave state untouched and report what is outstanding. Full rule, including the loop-cap and can't-clear cases: `docs/core_bypass.md`.
   - **Before you set `status` to `"complete"`:** if `process_log/degradation_ledger.md` has an **unresolved binding row** (`binding? = yes` and `action` not `resolved`), a core verification was downgraded to a non-binding fallback and never re-verified — do **not** set `"complete"`. If the outage is *deferrable* (stated bounded horizon like a daily credit budget, **and** the re-check is a cheap lookup), finish the work, record the entry in `pending_verification`, and set `status = "complete_pending_verification"`. Otherwise — including whenever the classification is ambiguous, and always under `"halt_on_core_bypass": true` — set `status = "halted_core_bypass"` and stop for operator review (handled by the `halted_*` branch below). Either way the run never reports a clean `complete` on a downgraded core — that is the terminal backstop, and it holds in the default deploy too. Full rule: `docs/core_bypass.md`.
   - **Whenever you report `complete`, `complete_pending_verification`, or any `halted_*`:** if `process_log/degradation_ledger.md` exists and has any data rows, a core was bypassed during the run — surface those rows (which core, why, fallback, binding?) in your report and do NOT present the run as clean success; a NON-BINDING verification did not certify what it appears to. See `docs/core_bypass.md`.
   - If `status` starts with `"halted_"`: the pipeline was halted by a prior session pending operator intervention. Report the halt reason (the suffix names it: `halted_wrds_unreachable`, `halted_no_identification_design`, etc.) and stop — do NOT attempt to resume or repair. Recovery is operator-driven, and the right path depends on whether the halt is transient or structural:
     - **Transient halts** (the underlying condition can be fixed in place without a redeployment) — e.g., `halted_wrds_unreachable` (the operator restores the WRDS service, then resumes; a credential latch requires the WRDS skill's one-attempt operator `unblock`, never an agent restart). Operator fixes the condition, flips `status` back to `"running"`, and the next session continues from the existing `current_stage`. For `halted_core_bypass` specifically, fixing the condition means: restore the binding source, re-run the verification that was downgraded, and **mark the unresolved `degradation_ledger.md` row `action = resolved`** — *then* flip `status` back to `"running"`. A running session may self-clear a row **only** for a binding verification it re-ran itself and that came back clean (see `docs/core_bypass.md`); every other resolution is operator-driven, and a rate/budget outage should have completed as `complete_pending_verification` rather than reaching this halt at all. Flipping to `"running"` without marking the row resolved will just re-trigger the completion-block and halt again.
     - **Structural halts** (the deployment configuration itself is wrong; in-place recovery would just re-trigger the halt) — e.g., `halted_no_identification_design` under `--mode empirical-first` (the question is irreducibly non-causal; the deployment must be converted to theory-first). Operator reruns `update.sh --no-mode` (or with corrected flags) to refresh the templates, then **also resets `current_stage`** to a value the new deployment understands (typically `"stage_1"` to re-enter idea selection, or `"stage_2"` if the selected idea is still valid in the new configuration — leaving `"stage_1_identification_design"` in place would point the resume logic at a stage doc that no longer exists in the converted deployment), and finally flips `status` back to `"running"`. Do not flip `status` without resetting `current_stage` first when the halt is structural. Also structural: `halted_no_viable_question` (every domain tried produced no scorable question — `branch-manager` certified it at Stage 0 per `docs/stage_0.md` Step 0b; read `output/stage0/domain_log.md` for which domains were spent and `output/stage0/branch_manager_discovery_p*.md` for why each was abandoned). Recovery is a redeployment with a different `--variant` or a widened domain scope, or extending the data inventory if that is what bounded tractability — resuming in place would rescan the same exhausted domains.
     - **Decision halts** (nothing is broken; the pipeline judged the work not worth continuing and stopped for a human) — `halted_seed_abandon` under `--seed` / `--faithful`. There is no condition to repair and no configuration to correct: the run reached one of its abandon verdicts and stopped on the merits. Under `--seed` those are the Gate 2 ship-honest failure, Gate 3 KNOWN after one reformulation, and Gate 5 Reject at the 2-rejection threshold. Under `--faithful` they are Gate 2 and Gate 5 (faithful documents novelty failures and proceeds). Every site writes its reasoning to `output/seed/abandon_report.md`. Report the reasoning and stop. The operator decides whether to supply a revised seed (a fresh deployment) or accept the finding; do **not** flip `status` back to `"running"` to "try again" — the verdict was reached on the merits and re-running the same seed re-derives it.
2. No human confirmation needed — just run

### Session preflight (runs on `not_started` and `running` only)

Only a session that is about to *do* pipeline work runs this — it is reached from the `not_started` and `running` branches above and from nowhere else. A `complete`, `complete_pending_verification`, or `halted_*` session skips it entirely: it reports and stops, so it needs neither live data connections nor a stall guard, and on `halted_wrds_unreachable` in particular, bringing the service back up is precisely the operator-driven repair that branch forbids. `complete_pending_verification` skips it too — re-running an owed lookup is a cheap API call, not pipeline work, and does not need WRDS auth or the hourly loop. If its re-check comes back dirty and the run re-enters `running` at the owning stage, preflight runs then, on the next session.

A resumed session (operator closed Claude Code and relaunched with "continue") starts with none of the previous session's process state — the data connections are dead and the hourly self-loop is gone — so preflight is not a fresh-start-only step. In order:

1. If `code/utils/start_services.sh` exists, run it (WRDS requires Duo auth — wait for it). Not optional on resume: the liveness the last session established did not survive the restart.
2. Set up the **hourly self-check loop** (below) if it is not already running. Do this before continuing a stage, not after — a session that resumes into a long Stage 2 without the loop has no stall guard for as long as that stage runs.
3. Establish or re-verify the data inventory (below): write it if `output/data_inventory.md` does not exist, otherwise confirm each ✓ source still responds and correct any row that no longer does, committing only if a row changed.

### Data inventory (written once at pipeline start, re-verified at every preflight)

Check what data sources are available before relying on any of them. This prevents bad assumptions from cascading through the entire pipeline.

1. Services are already up from preflight step 1 — do not start them again.
2. Read `.env` and list `{{SKILL_DIR}}/` — check which data skills are installed and which have valid credentials (not placeholders). For services started in preflight step 1, verify they actually respond. Mark ✓ only if the connection works, not just if credentials exist.
3. Write results to `output/data_inventory.md` — table of sources, status (✓/✗), what each provides, and implications for research design.
4. Commit: `pipeline: data inventory complete` — on a re-verify pass, commit only if a row actually changed (`pipeline: data inventory re-verified`), and never overwrite the file's research-design implications with a blank restatement.

### You are the orchestrator, not the worker

- **You must delegate to agents.** Every stage and gate specifies which agent to launch. Launch that agent — do not do the work yourself. You are the orchestrator: you read instructions, launch agents, read their output, make gate decisions, and update state. That is all.
- **Do not write theory drafts, literature maps, math audits, novelty checks, implication derivations, scorer decisions, self-attacks, referee reports, empirical analysis, bibliographic checks, or paper sections yourself.** These are agent tasks. If you find yourself writing substantive research content rather than launching an agent, stop and launch the correct agent.
- **The agents are in `.claude/agents/`.** When a stage says "Agent: literature-scout", launch it with the Agent tool (`subagent_type: literature-scout`) and the specified inputs and output path. Do not paraphrase or re-implement an agent's job inline.
- **Your substantive contributions are limited to:** reading pipeline state, writing `pipeline_state.json` updates, making gate routing decisions, writing commit messages, and writing the data inventory.

- **Writing `code/empirical.py` (or any `code/` analysis) yourself is a delegation failure**, not a shortcut: orchestrator-authored empirical code escapes the Stage 3a audit chain — the `empirics-auditor` reproduction gate (step 7) and the parallel data-integrity / data-selection / method-checker triad (step 7.5) — entirely, so it ships unverified. Launch the `empiricist` agent and let the audits run.

### Agent launch and monitoring

Subagents can hang indefinitely. Launch web-dependent agents (`literature-scout`, `gap-scout`, `question-referee`, `novelty-checker`) in the background. Check their output file every 5 minutes — if empty or not growing after a few checks, re-launch with the same prompt.

Never background a process with `nohup` (or a detached `&`) — it escapes harness tracking and stall detection. Use a harness-tracked background job instead (the Bash tool's `run_in_background`).

**Model-tier failure.** If a subagent fails *at dispatch* with a model-tier error (credits required / model unavailable / outage — no output, no work done), do not treat it as substantive and do not poll-wait for the tier: probe the tier once with a trivial `say hi`, and if it's still erroring relaunch the *same* agent forcing the next-lower tier in its fallback chain, append a `source-unavailable` (`binding? = no`) row to `process_log/degradation_ledger.md`, and continue. The highest pinned tier is the one most prone to this (rarely used → stale entitlement), so probe it before committing an expensive `last-resort`/`branch-manager` launch. Full procedure, per-runtime tier chains, and status-page check: `docs/model_fallback.md`.

### Hourly self-check (stall guard + pace reminder)

Set up an ~hourly self-loop using the Claude Code `/loop` skill. This is a **session preflight step (step 2 of the preflight above), not a Stage 0 step** — the loop lives in the Claude Code session, not in `pipeline_state.json`, so it dies whenever the session does. Every new session (first launch, or a relaunch where the operator just says "continue") must re-establish it before continuing the current stage. If you cannot tell whether a loop is already running, set it up — a duplicate stall check is harmless; a missing one leaves a multi-hour stage unguarded. The loop is local; do not ask for confirmation — skip the cloud offer, do local session. Use **`59m` exactly** — the `/loop` skill triggers a cloud-vs-local cloud-offer prompt at intervals ≥60m, and 59m sidesteps it. If the skill offers to round to 60m, decline; the slight cron unevenness is intentional.

Invoke:

```
/loop 59m Stall check: has the latest history timestamp advanced since the previous check? Are any subagent output files empty or not growing? If a subagent is hung, kill it and re-launch with the same prompt, or escalate the relevant attempt counter per the stage doc. Pace reminder: this paper would normally take months of human work, and the quality of the final manuscript is what matters — not throughput. Honest scope, careful derivations, and slow iteration produce better papers than fast brittle drafts. Do not advance a gate to save time; advance only when the gate's criteria are met.
```
