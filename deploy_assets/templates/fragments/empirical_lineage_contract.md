### Empirical specification lineage

Every quick-feasibility or full empirical computation uses `results_pipeline.py run-empirical`. Offline dataset-release packaging remains a separate ordinary `run`; do not attach analysis contracts to that release receipt.

Keep immutable, versioned scientific records under `output/analysis_specs/`. Start with one small project baseline containing only definitions genuinely intended to be reused; do not put estimator choices, robustness grids, or table order there merely to make it comprehensive. Each evidence module gets one analysis contract with a stable `analysis_id`, a purpose, the baseline path and semantic digest, and six open, non-empty ID-keyed sections: inputs, samples, variables, procedures, inference, and outputs. An analysis may own several procedure nodes and results. A robustness or comparison analysis names a `reference_analysis_id` from the same receipt. A composite comparison output identifies its receipt-qualified operands and states the unit/alignment assumptions that make them comparable. For every historical operand, bind both its receipt and bundle to that analysis input; if its result is artifact-only, bind that artifact too. An operand must be active or retained through an accepted replacement handoff. The runner recursively verifies its complete operand closure and blocks withdrawal of evidence that remains load-bearing for any active comparison.

Stable IDs are immutable across analyses and active receipts. Reusing one means byte-for-byte semantic equality after canonical JSON parsing. A changed baseline definition gets a new ID, `variant_of`, and `variant_reason`; any genuinely new definition gets `purpose`. The contract's grouped `deviations` must give a substantive reason for exactly every removed baseline ID and every variant ID—no unexplained change and no reason attached to an unchanged path. Validate before running:

```bash
python3 -I -S code/utils/results_pipeline/analysis_contract.py \
  --baseline "$ANALYSIS_BASELINE" --scaffold "$ANALYSIS_CONTRACT" \
  --analysis-id <stable_id> --purpose "<scientific purpose>"
python3 -I -S code/utils/results_pipeline/analysis_contract.py \
  "$ANALYSIS_CONTRACT" --baseline "$ANALYSIS_BASELINE"
```

The scaffold is only an authoring shortcut: it copies reusable definitions into one complete contract and never creates runtime inheritance. Fill its missing scientific definitions and validate the resolved file; do not maintain a second hand-expanded copy.

The run plan declares an `analyses` object keyed by `analysis_id`. Each entry contains `contract`, the fresh audit-only `execution_summary` artifact, and `input_bindings` mapping every contract input ID to its actual declared producer-input path(s). Contract and baseline files are producer inputs. Their paths plus all bound paths must exactly cover `producer_inputs`, so no scientific input is ownerless. All analyses in one run use the same baseline digest. Also declare `renderer_inputs`, the exact subset of individual regular-file artifacts safe and necessary for presentation; do not select directories or files containing execution summaries, row manifests, raw inputs, or privacy-sensitive counts.

The producer writes each execution summary using `analysis-execution-v1.schema.json`. It records realizations only: each sample's observed period and key-uniqueness diagnostic; a unit-bearing count map, declared-input/output count flow, and fingerprint for every ordered sample step; unit-bearing counts for every procedure; the exact fixed settings used by every procedure; and one realization for every predeclared decision rule. Any seed or tuning choice appears in the contract and is repeated exactly in the realization. A data-dependent choice is allowed only when the contract states its rule and allowed domain before execution; `allowed` may be a finite value array or a bounded numeric/integer domain. An undeclared choice, out-of-domain realization, or change to a fixed setting invalidates the run. Counts may refer to observations, entities, periods, clusters, imputations, windows, or replications as appropriate; never collapse incompatible units into one global N.

Every bundle result has exactly one `analysis_id`, and each contract's output IDs exactly equal the results it owns. Every exhibit retains `result_ids` for compatibility and adds an `elements` object mapping stable displayed element IDs (panel, row, series, coefficient block, note statistic) to nonempty result-ID arrays. The duplicate-free union of `elements` must exactly equal `result_ids`. A renderer formats these declared results; it does not calculate cross-specification differences. Put any comparison in a dedicated producer-computed result owned by its comparison analysis.

An empirical receipt is v3 and preserves, per analysis, the baseline, contract, and execution-summary paths and semantic digests plus result IDs. This makes whitespace/key-order changes irrelevant while retaining the exact file fingerprints already recorded by the receipt, and keeps baseline/contract path identity enforceable across replacements and retirement. The runner recomputes that projection on verification. The JSON schemas are authoring aids; `analysis_contract.py` and `results_pipeline.py run-empirical` are authoritative.
