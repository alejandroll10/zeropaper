# Stage 3a: Empirical Analysis

This file covers two sub-stages: **Gate 3a-feasibility** (empirical feasibility, runs *before* Stage 3 implications) and **Stage 3a** (full empirical analysis, runs *after* Stage 3 implications). In `pipeline_state.json`, use `"stage_3a_feasibility"` during feasibility and `"stage_3a"` during full analysis.

## Preflight: data-source liveness (before any `empiricist` launch in this stage)

`start_services.sh` ran once at session start and produced `output/data_inventory.md`, but a long Stage 2 iteration may have outlived the WRDS session. Before each `empiricist` launch in this stage (Gate 3a-feasibility, Stage 3a plan, Stage 3a execute, and any re-fire), the orchestrator must verify the WRDS server is still reachable:

```bash
PYTHONPATH=code .venv/bin/python3 -c "from utils.wrds_client import wrds_ping; exit(0 if wrds_ping() else 1)"
```

If the first ping returns False, call `wrds_auth_error()` once for the operator-facing diagnosis, then immediately run the exact `wrds_ping()` command above one final time. Honor that final authoritative service result: if it succeeds, continue normally—the first failure or diagnostic result was transient and must not produce a halt. Only if the final ping also returns False may you halt the stage by setting `pipeline_state.json:status = "halted_wrds_unreachable"` and escalate. A non-empty diagnosis means authentication was rejected and the server has latched; an empty diagnosis means the host daemon is absent/unhealthy. In either case **do not restart, call unblock, or run `start_services.sh` from the sandbox**: protected singleton/latch state is deliberately read-only there. The operator restores the service on the host and resumes the run. This preflight is cheap (sub-second when healthy) and prevents the most common silent stall in empirical runs. The same rule applies to the FIX-EMPIRICS empiricist re-launch in `docs/stage_puzzle_triage.md`, the Stage 6 Reject re-fire in `docs/stage_6.md` (which routes through this stage's "Re-fire on theory revision" section), and any future empiricist launch site.

## Gate 3a-feasibility: Empirical Feasibility (falsify-first)

Quick falsification check: can this theory be calibrated at all? Do the key empirical moments exist? A theory that predicts the wrong sign on a well-measured moment is dead regardless of how elegant the implications are. Check this BEFORE investing in implications.

**Empirical-first caution.** A wrong-sign feasibility result only kills the idea when the moment is well measured by a proxy/design that actually matches the Stage 1 empirical question. If the mismatch is plausibly due to a proxy, sample, merge-key, aggregation-key, coding, or identification-design artifact, do **not** mark the theory FALSIFIED. Route it as a feasibility-fix: document the artifact in `output/stage3a/empirical_feasibility.md`, repair the proxy/design if possible, and rerun feasibility. If the corrected feasible design no longer identifies the selected idea, use the no-design escalation in `docs/stage_1.md` Step 4 rather than puzzle triage.

1. Let T be the current `theory_attempt` and allocate K as the next unused feasibility serial across the entire run (it never resets on a new theory or Regeneration). Set `ANALYSIS_PATH = output/stage3a/empirical_feasibility_t{T}_a{K}.md`, `RESULT_PLAN = output/stage3a/empirical_feasibility_t{T}_a{K}_results.plan.json`, `RESULT_BUNDLE = output/stage3a/empirical_feasibility_t{T}_a{K}_results.json`, `RESULT_RECEIPT = output/stage3a/empirical_feasibility_t{T}_a{K}_results.receipt.json`, `ANALYSIS_ENTRYPOINT = code/empirical_feasibility_t{T}_a{K}.py`, `INPUT_SNAPSHOT_DIR = output/stage3a/feasibility_inputs_t{T}_a{K}`, and `SUPERSEDES_ARGS = ()`, substituting the numeric T and K rather than writing braces literally. Copy every mutable document input into that fresh directory before writing `RESULT_PLAN`. Launch `empiricist` with those exact values and a focused instruction: "Quick feasibility check only — download the 2-3 key moments this theory needs to match. Report whether the theory's predictions are in the right ballpark. Do NOT run a full analysis. Write the run plan before execution and the schema-v1 bundle via `RESULTS_BUNDLE_PATH`." If an already accepted feasibility decision for this same theory is intentionally being recomputed, keep it active, set `SUPERSEDES_ARGS` to its exact repeated `--supersedes` pair, and use a fresh K; a rejected pending retry never supersedes anything.
2. Require the report, plan, bundle, and receipt. The feasibility bundle may have no exhibits because it governs a pipeline decision rather than a reader-facing paper claim. Verify it with `python3 code/utils/results_pipeline/results_pipeline.py verify --receipt "$RESULT_RECEIPT" --rerender`; mechanical verification leaves the candidate **pending**. Do not activate until the proxy/design caution and negative-search quality checks below have substantively accepted its decision. Any proxy/design/search-quality repair, execution failure, or verification retry preserves the diagnostic, retires a pending receipt with a non-empty reason, increments K, and allocates a fresh complete `empirical_feasibility_tT_aK` namespace; never rerun prior paths. If a prior accepted feasibility decision is being replaced, it remains active through this routing.
3. Apply the empirical-first caution before treating the sign or magnitude as evidence about the theory. If proxy, sample, merge, aggregation, coding, or identification quality is not adequate, retire the pending candidate and return to step 1 with K+1 and the exact diagnostic. If the candidate declares a moment unavailable, require `output/stage3a/data_search_log.md` to document the query attempts (`list_tables`/`describe_table` for WRDS, provider catalog search for FRED/PWT/OECD/World Bank, canonical alternates tried, WebSearch for renames). A missing or shallow log is likewise a rejected pending candidate: retire it and retry in a fresh namespace. Only a confirmed absence or an adequately measured moment reaches decision routing.
4. Route the substantively accepted decision. If the key moments contradict the theory (wrong sign, off by an order of magnitude) on an adequate proxy/design, flag **FALSIFIED**; otherwise flag **OK** (including a genuinely unavailable moment whose negative search passed). Now activate `RESULT_RECEIPT`; if it replaced a prior accepted feasibility receipt, immediately retire that predecessor with `--superseded-by RESULT_RECEIPT` (this decision gate has no separate state pointer). For **OK**, proceed to Stage 3. For non-seeded **FALSIFIED**, record the accepted falsification, retire its now-active feasibility receipt with the reason that its theory identity is being abandoned, increment `theory_attempt`, reset `theory_version` to 1, and apply the fresh-theory identity reset in `core.md` before returning to Stage 1 (the theory is dead; the counter must advance so the "5 theories on same problem → Stage 0" escalation fires). Don't waste time on implications for a theory the data already rejects.

2. **Analysis plan.** Launch `empiricist` with instruction: "Write an analysis plan only — do not execute yet." The empiricist reads the theory, implications, data inventory, feasibility results, and (if produced) `identification_menu.md`. If a menu exists, the plan must select a strategy from it or explicitly justify departing from the menu. The empiricist then writes `output/stage3a/empirical_plan.md` describing: what tests to run, what data sources to use — as a `## Source selection` table in `empirical_plan.md` with columns `variable | role | chosen source | alternatives considered | reason chosen dominates | sample cutoff | cutoff citation`. **Load-bearing variables only** (LHS of a headline regression, focal RHS, sort/portfolio-assignment variable, treatment-definition variable, calibration moment): controls and FE buckets get a one-line `source: X` and no further justification. For each load-bearing row, `alternatives considered` lists the finer/longer/more-direct sources from `data_inventory.md` and the wired skills that were checked and rejected; `none — canonical single source` is acceptable for variables with one obvious source (Ken French factors, FRED FEDFUNDS). The `cutoff citation` names the regulation, SEC release, dataset codebook, or prior paper that **defines** the threshold (not merely uses it); intuition-only cutoffs are a fail-loud bug. The `WHY` is the table — do not paraphrase it in prose, what the expected results look like, and what would constitute support vs. rejection of the theory. The plan MUST include a **proxy–theory mapping** section: for each empirical proxy, state (a) which theoretical object it is standing in for, (b) which sub-class / mechanism / scope condition it captures (if the theory has heterogeneous agent types, scope-conditional predictions, or multiple mechanisms), (c) whether the proxy construction is mechanically correlated with the theoretical object (e.g., HHI as proxy for concentration-driven noise variance is mechanical; tracking-error is not), and (d) a non-mechanical alternative proxy. If the theory has multiple sub-classes, the plan must include **at least one proxy per sub-class in the primary analysis** — not deferred to robustness. If the main proxy is mechanically correlated with its theoretical object, the non-mechanical alternative is mandatory in the primary analysis as well.

If top-level `artifact_errors` is nonempty, do not enter the refresh batch or delete an ambiguous artifact: set `pipeline_state.json:status = "halted_replication_artifact_collision"`, record every exact path/error for operator recovery, and stop. This bounded safety halt prevents an orphan or invalid reserved-namespace object from causing an infinite re-fire loop. Otherwise, if any analysis entry is `CHANGED` or `ERROR`, sequentially re-fire `headline-replicator` for each named analysis with the `verify_script`/`verify_result`/`pass_candidate` paths in that entry (normal disagreement/self-failure routing applies). **Data/cache invalidation mode:** when the branch that entered step 6.5 rebuilt, re-fetched, re-filtered, or otherwise changed empirical data/cache bytes, set `FORCE_ALL_ANALYSES = true` and re-fire every enumerated analysis unconditionally even if `check-all` says its code/headline hashes are unchanged—the manifest deliberately excludes data. After either batch, run `check-all` again. Do not enter step 7 until its top-level status is `UNCHANGED` and every forced firing PASSes. During a batch, defer recursive all-analysis checks until every stale/forced entry has been refreshed; verifier scripts live outside `code/`, so successful sibling revalidations converge without invalidating one another.

   **Stored-input guard for code/headline-only downstream repairs.** Where a later branch explicitly invokes this guard, before reusing the current replicator PASS run `compare --result VERIFY_RESULT_PATH --analysis ANALYSIS_PATH` exactly once. Nonzero exit, `status: "CHANGED"`, or a manifest bound to a different analysis path means the PASS is stale: reset `loops.headline_replication.round` to 0 and re-fire step 6.5 on `ANALYSIS_PATH` before the next audit; step 6.5's all-analysis freshness gate then refreshes every sibling invalidated by the same code change. `status: "UNCHANGED"` permits direct audit re-fire. Never inspect a Git diff or decide whether a repair was "material." Any branch that can rebuild empirical data instead mandates step 6.5 unconditionally, because changed data bytes are outside this lightweight manifest.

7. **Empirics audit.** Set `ANALYSIS_ENTRYPOINTS` to every exact analysis entrypoint the empiricist ran to produce or update `ANALYSIS_PATH`, and set `RENDER_ENTRYPOINT` to the renderer bound by `RESULT_RECEIPT`. Launch `empirics-auditor` on `ANALYSIS_PATH` + `RESULT_BUNDLE` + `RESULT_RECEIPT` + `ANALYSIS_ENTRYPOINTS` + `RENDER_ENTRYPOINT` + the complete code surface + theory draft + its derived `VERIFY_RESULT_PATH`; set `AUDIT_OUTPUT_PATH = output/stage3a/empirics_audit.md` unless the caller supplied a versioned post-pipeline path. The auditor reads the replicator's per-claim results as confirmed/disputed signals (the replicator owns headline recomputation; the auditor does NOT re-derive headline numbers), runs the named entrypoints, verifies the receipt with re-rendering, checks that the renderer only presents declared bundle evidence, checks the complete execution surface for shared effects, checks methodology mechanics (clustering, robust SEs, sample construction), and reviews interpretation. Identification-design soundness is already gated at step 3; the empirics-auditor focuses on whether the code actually implements the audited plan.
   - If **PASS**: proceed to step 7.5 (data-integrity audit). Do not set the active-analysis pointer yet; downstream auditors still execute code.
   - If **FAIL**: below the 5-attempt audit-fix cap, use the fresh-attempt transition with the audit feedback and fix each flagged defect wherever it occurs, then reset `loops.headline_replication.round` to 0 and run step 6.5 on the new `ANALYSIS_PATH` with `FORCE_ALL_ANALYSES = true` before re-firing the auditor. At the cap, retire the pending receipt with the terminal audit report, then return to Stage 2 with those notes (the theory may be untestable as written).
7.5. **Post-empirics audit triad (data integrity + data selection + method canonical-availability).** `empirics-auditor` PASS verifies (a) the code runs and its with-cache output matches the report, AND (b) every stochastic LOAD-BEARING spec reproduces bit-for-bit when the derived cache is moved aside and the spec is re-run from scratch (issue #56 — same-path determinism, distinct from the headline-replicator's different-path tolerance check) — it does NOT verify the cache *content* is correct against the raw source (that is the data-integrity auditor's job below), nor whether the methods used are textbook-canonical or hand-rolled. Launch THREE auditors **in parallel** (single message, three Agent calls), supplying the current exact `ANALYSIS_PATH` to each: `data-integrity-auditor`, `data-selection-auditor`, and `method-checker`. The integrity auditor re-queries the source database and verifies cached field values against source (Class 1 — content); the selection auditor enumerates candidate identifiers under the documented inclusion rule with relaxed filters and diffs them against the cached universe (Class 2 — sample); the method-checker reads `.claude/skills/canonical-packages/SKILL.md` and flags every place the empiricist wrote custom code for an econometric method that has a canonical author-maintained package (Class 3 — method canonical-availability; see [issue #36](https://github.com/alejandroll10/zeropaper/issues/36)). Each returns PASS / REVISE / FAIL with severity-ranked named failure modes; outputs go to `output/stage3a/data_integrity_audit.md`, `output/stage3a/data_selection_audit.md`, and `output/stage3a/method_check.md` (+ summary JSON for method-checker). **Before aggregating, verify all three output files exist on disk** — `output/stage3a/data_integrity_audit.md`, `output/stage3a/data_selection_audit.md`, `output/stage3a/method_check.md`. If any is absent (typically because the corresponding agent crashed, hit a token limit, or timed out), re-launch only that absent agent and wait for its output before aggregating; do not infer a default verdict from an empty file. A silently-missing method_check.md treated as PASS-by-omission is exactly the issue-36 failure mode this triad exists to prevent. Then aggregate the three verdicts:
   - **All three PASS**: run `python3 code/utils/empirical_input_manifest.py check-all` one final time after all auditors have finished executing code. If its status is not `UNCHANGED`, code or verifier evidence changed during downstream verification: reset `loops.headline_replication.round`, re-enter step 6.5 on the current `ANALYSIS_PATH`, complete its all-analysis gate, and repeat step 7 plus the triad. Only a final `UNCHANGED` may run `results_pipeline.py activate --receipt "$RESULT_RECEIPT"` and then atomically set `pipeline_state.json:stage3a_theory_version = theory_version`, `stage3a_analysis_path = ANALYSIS_PATH`, and `stage3a_result_receipt = RESULT_RECEIPT`; the prior accepted triple stays unchanged until that pointer update succeeds. If this was a replacement, explicitly retire the prior receipt only after the pointer update. Then proceed to the **puzzle-triage entry check** (next section) and reset `pipeline_state.json:loops.data_integrity.round` AND `loops.method_check.round` to 0 (both counters tracked the triad's REVISE loops and are stale once the triad clears).
   - **Any data auditor REVISE (and no FAIL)**: increment `pipeline_state.json:loops.data_integrity.round`, then use the fresh-attempt transition with both data-audit reports; the new attempt repairs data construction, resets `loops.headline_replication.round`, passes step 6.5 with `FORCE_ALL_ANALYSES = true`, then repeats step 7 and all three auditors. The empirics-auditor re-fire does not consume its substantive-fix cap. At the 3-round data cap, route as FAIL rather than editing the candidate in place.
   - **method-checker REVISE only (data audits both PASS)**: increment `loops.method_check.round`, then use the fresh-attempt transition with `method_check.md`; the new attempt either uses the named canonical package or records the accepted (a)–(d) justification, then passes step 6.5 and step 7 before method-checker re-fires. At the 3-round method cap, route as FAIL.
   - **Both data REVISE and method-checker REVISE**: take the data-REVISE fresh-attempt route first and increment only `loops.data_integrity.round`; the rebuilt candidate repeats all three auditors. If method-checker remains REVISE on that new candidate, take the method-only fresh-attempt route and increment `loops.method_check.round` then.
   - **Any FAIL**: (a) for a source outage, retry preflight once; if still unreachable, retire the pending receipt with the outage diagnostic, set `status = "halted_data_audit_unreachable"`, and stop. (b) For substantive data FAIL, preserve the failing data counter, reset `loops.method_check.round`, and use the fresh-attempt transition to redesign/re-source/re-filter the data layer before step 6.5. (c) For method-checker FAIL, preserve its failing counter, reset `loops.data_integrity.round`, and use the fresh-attempt transition to rebuild the flagged sections with canonical packages before step 6.5. No FAIL branch rewrites the current receipt-bound analysis or code.
   - The triad re-fires on Stage 3a re-entry and after any requested cache regeneration. A cache is receipt-bound evidence: regeneration uses the fresh-attempt transition rather than changing the current candidate. Reset `loops.headline_replication.round`, require the new candidate to pass step 6.5 with `FORCE_ALL_ANALYSES = true` and step 7, then re-launch all three auditors. No stored PASS survives regeneration, and there is no mtime-based verdict replay shortcut.
8. Commit: `artifact: headline replication — {PASS/FAIL}; empirics audit — {PASS/FAIL}; data audits — {PASS/REVISE/FAIL × 2}; method check — {PASS/REVISE/FAIL}`

## Puzzle-triage entry check (mandatory after empirics-auditor PASS and both data audits PASS)

Before proceeding to Stage 4, you must check whether the empirical results contradict any prediction in `output/stage3/implications.md`.

1. Read `output/stage3/implications.md` and identify which implications were tested.
2. Read the exact `ANALYSIS_PATH` and the auditor's verification. On a versioned re-fire, this is the self-contained cumulative replacement report; use its declared prior-evidence inputs for lineage and do not assume the canonical first-attempt file exists.
3. For each tested implication: did the data contradict it (sign reversal, magnitude outside the predicted range, condition that should hold but failed)?
4. Write `output/stage3a/contradiction_check.md` with one of:
   - **NONE** — empirics confirm or are silent on every tested implication. Proceed to Stage 4.
   - **CONTRADICTIONS FOUND** — list the contradicted implications and what the data shows. **Proceed to puzzle triage** (`docs/stage_puzzle_triage.md`), not Stage 4.
5. Commit: `artifact: contradiction check — {NONE/CONTRADICTIONS FOUND}`

This step is mandatory and may not be skipped — silently jumping to Stage 4 after empirics PASS bypasses the puzzle-pivot mechanism that exists to extract value from theory-empirics disagreements.

## Re-fire on theory revision

Stage 3a is not one-shot. When the theory revises after the first 3a pass — Gate 3 INCREMENTAL rework, Gate 4 REVISE→Stage 2, Stage 6 Major Revision triggering theory-generator work, or any substantive content change — the original `empirical_analysis.md` becomes stale relative to the current theory. The empiricist must re-run on the revised content before Gate 4 can advance again.

**Trigger.** Any of:
- `stage3a_theory_version` is null or differs from `theory_version` (including after a theory-identity reset).
- `implications.md` is overwritten (Gate 3 INCREMENTAL rework, PIVOT, or any path that re-runs Stage 3) and the new file contains NOVEL or PUZZLE-CANDIDATE implications not present in the prior version.
- A referee identifies an empirical gap that wasn't addressed in the first 3a pass (e.g., "this prediction was deferred" or "the identification doesn't address X").
- Stage 6 Reject verdict triggers a deepen directive (see `docs/stage_6.md` Reject row): the deepen directive's empirics requirements become the focus of the re-fire.

**Procedure.**
