# Stage 3a: Empirical Analysis

This file covers two sub-stages: **Gate 3a-feasibility** (empirical feasibility, runs *before* Stage 3 implications) and **Stage 3a** (full empirical analysis, runs *after* Stage 3 implications). In `pipeline_state.json`, use `"stage_3a_feasibility"` during feasibility and `"stage_3a"` during full analysis.

## Preflight: data-source liveness (before any `empiricist` launch in this stage)

`start_services.sh` ran once at session start and produced `output/data_inventory.md`, but a long Stage 2 iteration may have outlived the WRDS session. Before each `empiricist` launch in this stage (Gate 3a-feasibility, Stage 3a plan, Stage 3a execute, and any re-fire), the orchestrator must verify the WRDS server is still reachable:

```bash
PYTHONPATH=code python3 -c "from utils.wrds_client import wrds_ping; exit(0 if wrds_ping() else 1)"
```

If the ping returns False, first call `wrds_auth_error()`. A non-empty result means authentication was rejected and the server has latched: **do not restart, retry, or call unblock**; halt and escalate under the WRDS skill's credential-rejection rule. Only when `wrds_auth_error()` is empty may you attempt one restart with `bash code/utils/start_services.sh`. If that also fails, halt the stage by setting `pipeline_state.json:status = "halted_wrds_unreachable"` rather than launching the empiricist into a stack of failed queries — re-run when access is restored. This preflight is cheap (sub-second when healthy) and prevents the most common silent stall in empirical runs. The same rule applies to the FIX-EMPIRICS empiricist re-launch in `docs/stage_puzzle_triage.md`, the Stage 6 Reject re-fire in `docs/stage_6.md` (which routes through this stage's "Re-fire on theory revision" section), and any future empiricist launch site.

## Gate 3a-feasibility: Empirical Feasibility (falsify-first)

Quick falsification check: can this theory be calibrated at all? Do the key empirical moments exist? A theory that predicts the wrong sign on a well-measured moment is dead regardless of how elegant the implications are. Check this BEFORE investing in implications.

**Empirical-first caution.** A wrong-sign feasibility result only kills the idea when the moment is well measured by a proxy/design that actually matches the Stage 1 empirical question. If the mismatch is plausibly due to a proxy, sample, merge-key, aggregation-key, coding, or identification-design artifact, do **not** mark the theory FALSIFIED. Route it as a feasibility-fix: document the artifact in `output/stage3a/empirical_feasibility.md`, repair the proxy/design if possible, and rerun feasibility. If the corrected feasible design no longer identifies the selected idea, use the no-design escalation in `docs/stage_1.md` Step 4 rather than puzzle triage.

1. Launch `empiricist` with a focused instruction: "Quick feasibility check only — download the 2-3 key moments this theory needs to match. Report whether the theory's predictions are in the right ballpark. Do NOT run a full analysis."
2. Save to `output/stage3a/empirical_feasibility.md`
3. If the key moments contradict the theory (wrong sign, off by an order of magnitude) **and** the proxy/design passed the caution above: flag as **FALSIFIED** — increment `theory_attempt` and reset `theory_version` to 1, then return to Stage 1 for a new idea (the theory is dead; counter must advance so the "5 theories on same problem → Stage 0" escalation rule in core.md fires correctly). Don't waste time on implications for a theory the data already rejects.

{{SEED_OVERRIDE_STAGE_3A_FALSIFIED}}
4. If moments are roughly consistent: proceed to Stage 3. If the empiricist declares any moment **unavailable**, require a negative-search log at `output/stage3a/data_search_log.md` documenting the query attempts (`list_tables`/`describe_table` for WRDS, provider catalog search for FRED/PWT/OECD/World Bank, canonical alternates tried, WebSearch for renames). If the log is missing or the search is shallow (no alternates tried, no description grep, no WebSearch), the "unavailable" verdict is not substantiated — return to the empiricist for a real search. Only proceed to Stage 3 once the log exists or the moment is confirmed truly absent.
5. Commit: `artifact: empirical feasibility — {OK/FALSIFIED}`

## Stage 3a: Full Empirical Analysis

This is the full empirical analysis — deeper than the feasibility check at Gate 3a-feasibility. Now that implications are developed, the empiricist can design proper tests, calibrations, and portfolio sorts.

2. **Analysis plan.** Launch `empiricist` with instruction: "Write an analysis plan only — do not execute yet." The empiricist reads the theory, implications, data inventory, feasibility results, and (if produced) `identification_menu.md`. If a menu exists, the plan must select a strategy from it or explicitly justify departing from the menu. The empiricist then writes `output/stage3a/empirical_plan.md` describing: what tests to run, what data sources to use — as a `## Source selection` table in `empirical_plan.md` with columns `variable | role | chosen source | alternatives considered | reason chosen dominates | sample cutoff | cutoff citation`. **Load-bearing variables only** (LHS of a headline regression, focal RHS, sort/portfolio-assignment variable, treatment-definition variable, calibration moment): controls and FE buckets get a one-line `source: X` and no further justification. For each load-bearing row, `alternatives considered` lists the finer/longer/more-direct sources from `data_inventory.md` and the wired skills that were checked and rejected; `none — canonical single source` is acceptable for variables with one obvious source (Ken French factors, FRED FEDFUNDS). The `cutoff citation` names the regulation, SEC release, dataset codebook, or prior paper that **defines** the threshold (not merely uses it); intuition-only cutoffs are a fail-loud bug. The `WHY` is the table — do not paraphrase it in prose, what the expected results look like, and what would constitute support vs. rejection of the theory. The plan MUST include a **proxy–theory mapping** section: for each empirical proxy, state (a) which theoretical object it is standing in for, (b) which sub-class / mechanism / scope condition it captures (if the theory has heterogeneous agent types, scope-conditional predictions, or multiple mechanisms), (c) whether the proxy construction is mechanically correlated with the theoretical object (e.g., HHI as proxy for concentration-driven noise variance is mechanical; tracking-error is not), and (d) a non-mechanical alternative proxy. If the theory has multiple sub-classes, the plan must include **at least one proxy per sub-class in the primary analysis** — not deferred to robustness. If the main proxy is mechanically correlated with its theoretical object, the non-mechanical alternative is mandatory in the primary analysis as well.

Reset the counter to 0 on PASS, on FAIL routing to a different strategy from the menu, or on Stage 3a re-fire entry per "Re-fire on theory revision."

7.5. **Post-empirics audit triad (data integrity + data selection + method canonical-availability).** `empirics-auditor` PASS verifies (a) the code runs and its with-cache output matches the report, AND (b) every stochastic LOAD-BEARING spec reproduces bit-for-bit when the derived cache is moved aside and the spec is re-run from scratch (issue #56 — same-path determinism, distinct from the headline-replicator's different-path tolerance check) — it does NOT verify the cache *content* is correct against the raw source (that is the data-integrity auditor's job below), nor whether the methods used are textbook-canonical or hand-rolled. Launch THREE auditors **in parallel** (single message, three Agent calls), supplying the current exact `ANALYSIS_PATH` to each: `data-integrity-auditor`, `data-selection-auditor`, and `method-checker`. The integrity auditor re-queries the source database and verifies cached field values against source (Class 1 — content); the selection auditor enumerates candidate identifiers under the documented inclusion rule with relaxed filters and diffs them against the cached universe (Class 2 — sample); the method-checker reads `.claude/skills/canonical-packages/SKILL.md` and flags every place the empiricist wrote custom code for an econometric method that has a canonical author-maintained package (Class 3 — method canonical-availability; see [issue #36](https://github.com/alejandroll10/zeropaper/issues/36)). Each returns PASS / REVISE / FAIL with severity-ranked named failure modes; outputs go to `output/stage3a/data_integrity_audit.md`, `output/stage3a/data_selection_audit.md`, and `output/stage3a/method_check.md` (+ summary JSON for method-checker). **Before aggregating, verify all three output files exist on disk** — `output/stage3a/data_integrity_audit.md`, `output/stage3a/data_selection_audit.md`, `output/stage3a/method_check.md`. If any is absent (typically because the corresponding agent crashed, hit a token limit, or timed out), re-launch only that absent agent and wait for its output before aggregating; do not infer a default verdict from an empty file. A silently-missing method_check.md treated as PASS-by-omission is exactly the issue-36 failure mode this triad exists to prevent. Then aggregate the three verdicts:
   - **All three PASS**: run `python3 code/utils/empirical_input_manifest.py check-all` one final time after all auditors have finished executing code. If its status is not `UNCHANGED`, code or verifier evidence changed during downstream verification: reset `loops.headline_replication.round`, re-enter step 6.5 on the current `ANALYSIS_PATH`, complete its all-analysis gate, and repeat step 7 plus the triad. Only a final `UNCHANGED` may set `pipeline_state.json:stage3a_analysis_path = ANALYSIS_PATH` and proceed to the **puzzle-triage entry check** (next section). Then reset `pipeline_state.json:loops.data_integrity.round` AND `loops.method_check.round` to 0 (both counters tracked the triad's REVISE loops and are stale once the triad clears).
   - **Any data auditor REVISE (and no FAIL)**: re-launch `empiricist` with the data-audit reports and the named failure modes the empiricist must fix. The empiricist patches the data-construction code (not the identification design — if a finding straddles identification, route to step 3 instead). **Increment `pipeline_state.json:loops.data_integrity.round`.** Because this branch rebuilds empirical data that the input manifest deliberately does not hash, reset `loops.headline_replication.round` to 0 and re-fire step 6.5 on `ANALYSIS_PATH` unconditionally with `FORCE_ALL_ANALYSES = true`; only then re-run step 7 (empirics-auditor) and step 7.5 on the rebuilt cache. **The empirics-auditor re-fire here is a reproduction check on the rebuilt cache, not a substantive audit-fix iteration — it does NOT count against step 7's 5-attempt cap.** This re-fire still includes the cache-bypassed determinism rerun (issue #56) on stochastic LOAD-BEARING specs — patched data-construction code can introduce a fresh unseeded call, so the rerun check must re-run, not be skipped as "already passed." **Hard cap: 3 data-revision rounds.** If `loops.data_integrity.round >= loops.data_integrity.cap` and either data auditor still returns REVISE, treat as FAIL.
   - **method-checker REVISE only (data audits both PASS)**: re-launch `empiricist` with `output/stage3a/method_check.md` and an instruction to either (i) replace the flagged custom implementations with the canonical packages named in the report, or (ii) add the (a)–(d) justification to the script docstring AND the corresponding `output/stage3a/*.json`. **Increment `pipeline_state.json:loops.method_check.round`.** Apply the stored-input guard after the empiricist returns, then re-run step 7 (empirics-auditor — to verify the canonical-package swap reproduces) and re-fire `method-checker` only (the data audits already passed; no cache change). **The empirics-auditor re-fire here is a reproduction check on a canonical-package swap or a docstring/JSON addition, not a substantive audit-fix iteration — it does NOT count against step 7's 5-attempt cap.** This re-fire still includes the cache-bypassed determinism rerun (issue #56) on stochastic LOAD-BEARING specs — a canonical-package swap can change a method's seeding behavior, so the rerun check must re-run. **Hard cap: 3 method-check rounds.** If `loops.method_check.round >= loops.method_check.cap` and method-checker still returns REVISE, treat as FAIL.
   - **Both data REVISE and method-checker REVISE**: handle the data REVISE first (the empiricist patches data construction; re-run empirics-auditor and all three step-7.5 auditors). **Increment `loops.data_integrity.round`** per the data-REVISE branch on this firing; do NOT increment `loops.method_check.round` yet — the method fix has not been attempted. On the next step 7.5 firing, if method-checker still REVISEs (likely, because data fixes do not address method choices), follow the method-checker-only branch and increment `loops.method_check.round` at that point.
   - **Any FAIL**: hard escalation. Three sub-cases. These two data/method sub-cases are **exception 1 (escalation non-reset)** to the generic Audit-loop scoping rule: the FAILing loop is escalating (not being retried on a fresh artifact), so it is left as-is even though the sibling loop's artifact is regenerated and that sibling therefore zeroes. (a) **source-unreachable FAIL** (data auditors could not re-query because WRDS/FRED/etc. is down): retry the preflight at the top of this file once, then if still unreachable set `pipeline_state.json:status = "halted_data_audit_unreachable"` and stop. (b) **substantive data FAIL** (data auditor re-queried and found a load-bearing data problem): re-launch `empiricist` with the FAIL report and an explicit instruction to redesign the data layer (re-source, re-filter, re-construct the universe) and rewrite the current `ANALYSIS_PATH`; then reset `loops.headline_replication.round` to 0 and re-fire step 6.5 on that same path before either audit can run. A substantive data FAIL counts as a re-execution, not a revision round; **do not reset `loops.data_integrity.round`** (it is escalating — leave it) **but reset `loops.method_check.round` to 0** — the data-layer redesign is a fresh execution pass and the method-checker counter from the prior data layer must not bleed across (otherwise the first method-checker REVISE in the new execution could trigger a premature cap-FAIL). (c) **method-checker FAIL** (multiple custom implementations of canonical methods, suggesting systematic disregard): re-launch `empiricist` with `output/stage3a/method_check.md` and an explicit instruction to restart the flagged sections using the canonical packages and update `ANALYSIS_PATH` if its headline changes. Apply the stored-input guard after the empiricist returns and before re-running step 7. A method-checker FAIL counts as a re-execution; **do not reset `loops.method_check.round`** (it is escalating — leave it) **but reset `loops.data_integrity.round` to 0** — the section-restart is a fresh execution pass and the data-revision counter from the prior code structure must not bleed across.
   - The triad re-fires on Stage 3a re-entry (see "Re-fire on theory revision" below) and on any cache regeneration (`mtime` advance on any cached file referenced by the analysis). **Before auditing any regenerated cache, reset `loops.headline_replication.round` to 0, re-fire step 6.5 on the current `ANALYSIS_PATH` with `FORCE_ALL_ANALYSES = true`, and re-run step 7**; cache/data bytes are outside the input manifest, so no stored PASS survives regeneration for any analysis. Then re-launch all three step-7.5 auditors. There is no mtime-based method-verdict replay shortcut: removing that subjective/stale optimization is simpler and ensures every regenerated empirical state receives a fresh triad verdict.
8. Commit: `artifact: headline replication — {PASS/FAIL}; empirics audit — {PASS/FAIL}; data audits — {PASS/REVISE/FAIL × 2}; method check — {PASS/REVISE/FAIL}`

## Puzzle-triage entry check (mandatory after empirics-auditor PASS and both data audits PASS)

Before proceeding to Stage 4, you must check whether the empirical results contradict any prediction in `output/stage3/implications.md`.

1. Read `output/stage3/implications.md` and identify which implications were tested.
2. Read `ANALYSIS_PATH` and the auditor's verification. On a versioned re-fire, also read canonical `output/stage3a/empirical_analysis.md` so the combined evidence—not either file in isolation—drives the contradiction check.
3. For each tested implication: did the data contradict it (sign reversal, magnitude outside the predicted range, condition that should hold but failed)?
4. Write `output/stage3a/contradiction_check.md` with one of:
   - **NONE** — empirics confirm or are silent on every tested implication. Proceed to Stage 4.
   - **CONTRADICTIONS FOUND** — list the contradicted implications and what the data shows. **Proceed to puzzle triage** (`docs/stage_puzzle_triage.md`), not Stage 4.
5. Commit: `artifact: contradiction check — {NONE/CONTRADICTIONS FOUND}`

This step is mandatory and may not be skipped — silently jumping to Stage 4 after empirics PASS bypasses the puzzle-pivot mechanism that exists to extract value from theory-empirics disagreements.

## Re-fire on theory revision

Stage 3a is not one-shot. When the theory revises after the first 3a pass — Gate 3 INCREMENTAL rework, Gate 4 REVISE→Stage 2, Stage 6 Major Revision triggering theory-generator work, or any substantive content change — the original `empirical_analysis.md` becomes stale relative to the current theory. The empiricist must re-run on the revised content before Gate 4 can advance again.

**Trigger.** Any of:
- `theory_version` advances and `stage3a_theory_version < theory_version`.
- `implications.md` is overwritten (Gate 3 INCREMENTAL rework, PIVOT, or any path that re-runs Stage 3) and the new file contains NOVEL or PUZZLE-CANDIDATE implications not present in the prior version.
- A referee identifies an empirical gap that wasn't addressed in the first 3a pass (e.g., "this prediction was deferred" or "the identification doesn't address X").
- Stage 6 Reject verdict triggers a deepen directive (see `docs/stage_6.md` Reject row): the deepen directive's empirics requirements become the focus of the re-fire.

**Procedure.**
Before step 1, establish `ANALYSIS_PATH`. If the caller names an exact output path (for example, Stage 5's claim-specific `output/stage3a/empirical_analysis_v<claim_id>.md`), preserve that path through every step and repair/retry branch below. Otherwise set `ANALYSIS_PATH = output/stage3a/empirical_analysis_v{theory_version}.md`. Never replace a caller-supplied path with the theory-version default.
